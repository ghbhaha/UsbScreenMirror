# UsbScreenMirror

把**安卓手机**或 **iPad / iPhone** 的屏幕，镜像到**另一台安卓设备**（宿主）上，全程走 USB：
手机走 AOA v2 配件协议，Apple 设备走 QuickTime USB 协议。

**两种设备都不需要 adb 授权、不需要开发者选项、不需要 root，也不需要往被投屏设备里推送任何进程。**

宿主是一台安卓设备（本项目实测 BOE P40UCH / Android 14）。装上同一个 APK 后：

- 插**安卓手机** → 走配件模式（AOA v2），带**真触摸回传**；
- 插 **iPad** → 走 QuickTime USB，iPad 上点一次「信任」即可，**连电脑都不需要**。

目标场景是「手边有各种设备，想让它们投到同一块屏上」，而通常的做法（scrcpy / 各种 iOS 投屏工具）
要么要开 USB 调试、要么要装 PC 端软件、要么只支持一种设备——这些在本项目里都省掉。

## 它是什么 / 不是什么

先在开工前把期望对齐，这一节比后面的技术细节更重要。

| | 说明 |
| --- | --- |
| ✅ **省掉的** | adb 授权、开发者选项、USB 调试开关、密钥协商、往手机推送服务端、root |
| ✅ **用到的** | 一根 OTG / 数据线；安卓手机侧用系统自带的 AOA 与 MediaProjection / MediaCodec；iPad 侧用 QuickTime USB（宿主当 USB 主机） |
| ✅ **宿主只需一个 APK** | 插手机走 AOA、插 iPad 走 QuickTime，进哪个页面由选择页按 VID/PID 决定 |
| ⚠️ **省不掉的（手机）** | **Android 14+ 每次投屏仍要点一次录屏授权**——系统取消了 MediaProjection 的"记住选择"，无法绕过 |
| ⚠️ **可能还要点一次（手机）** | 首次插线时系统**可能**弹「是否打开该 App 处理 USB 配件」，勾选默认后此后插线即达 |
| ⚠️ **省不掉的（iPad）** | 首次要在 **iPad 上点一次「信任」**（配对）；之后不再需要。会话开始时 iPad 上的播放会暂停一次，手动再点播放即可 |
| ⚠️ **两端必须同版本** | 手机端与宿主端要一起升级（例如像素开关依赖手机端 10.17 的 `applyOptions`，旧包上切换不会生效）。目前**尚无版本/能力协商**，见路线图 |
| ❌ **本期不做** | 鼠标/键盘输入；iPad 侧的触摸回传（iOS 无 USB 输入通道） |

一句话：**省掉的是"链路的准备工作"，不是"这一次点击"。**

## 工作原理

```
┌────────────────────────┐                        ┌────────────────────────┐
│  宿主 Host             │        OTG 数据线       │  配件 Accessory        │
│  （另一台安卓设备）      │◄──────────────────────►│  （被镜像的手机）        │
│                        │                        │                        │
│  app-host              │  ① AOA 握手 51/52×6/53 │  app-accessory         │
│   UsbAttachRouter ─────┼───────────────────────►│   CaptureService       │
│                        │  ② 手机重枚举为配件     │                        │
│   HostSession ◄────────┼───────────────────────┤   VirtualDisplay       │
│   MediaCodec 解码       │  ③ CNXN / OPEN / OKAY  │   MediaCodec 编码       │
│   SurfaceView 显示      │◄──────────────────────┤                        │
└────────────────────────┘  ④ WRTE 视频帧流       └────────────────────────┘
```

关键点在于**②**：宿主要用 AOA 的 52 号控制请求把「配件身份」写进手机，
手机内核随即把 USB 设备重枚举成配件形态（`VID:PID = 18D1:2D01`），
系统再据此把 `USB_ACCESSORY_ATTACHED` 派发给手机端 App。
**身份写不进去或写得不对，后面一步都不会发生**——这是整个项目最容易踩的坑，
详见 [`docs/排错手册.md`](docs/排错手册.md) 第 3.4 节。

原理与选型的完整推导见 [`docs/配件投屏核心原理.md`](docs/配件投屏核心原理.md)。

### iPad / iPhone：QuickTime USB（角色正好相反）

手机那条路里宿主是**配件**；投 iPad 时宿主是**标准 USB 主机**，去认领平板的私有接口：

```
┌────────────────────────┐   ① lockdown 会话(mux)  ┌────────────────────────┐
│ 宿主 app-host           │◄──────────────────────►│ iPad                   │
│ ios.IosActivity        │   ② 证书配对 → 受信任    │ （不需要装任何 App）     │
│                        │   ③ activate → 重枚举   │                        │
│ QtSession ◄────────────┼───────────────────────┤ QT 接口 0xFF/0x2A       │
│ H264Decoder + 音频      │   ④ FEED(视频) + EAT(音频)│ 0x86 IN / 0x05 OUT     │
└────────────────────────┘◄───────────────────────┘                        │
```

三个和手机那条路**必须区别对待**的点：

1. **配对**：走 lockdown 的 `Pair`，iPad 上点一次「信任」即可。配对记录存在宿主
   `filesDir/ios_pair.properties`，之后不再需要点。
2. **配对会清掉设备侧的采集武装态** ⇒ 配完必须再 `activate` 一次（要让设备真重枚举）。
   判据只能是「配置集里从 4 个变成 5 个」，**不能**用"能不能找到采集接口"——
   扁平接口表永远包含它，会导致 `activate` 一次都不发。
3. **收尾必须做**：`hpa0`/`hpd0` → 等 2 个 `rels`（途中应答 `SYNC stop`）→ 再补 `hpd0`。
   不做这步，设备侧会话一直挂着，**下一次会话只出 3 帧就卡死**。

协议细节、踩坑与验证记录见 [`docs/iOS_USB投屏_安卓实现.md`](docs/iOS_USB投屏_安卓实现.md)。

## 架构

单 Gradle 工程、三个模块，交付为**两个独立 APK**（宿主一个、手机一个）。

| 模块 | 产物 | 职责 |
| --- | --- | --- |
| `:protocol` | 纯 Kotlin/JVM 库 | 报文编解码、常量、连接编排、队列、缩放、**设备分类**、QuickTime 报文与音频解析、证书/配对。**零 Android 依赖** |
| `:app-host` | `app-host-debug.apk` | 宿主：**选择页 + 两个投屏页**（AOA / QuickTime） |
| `:app-accessory` | `app-accessory-debug.apk` | 手机：配件通道 → 虚拟屏采集 → 编码 → 推帧 |

宿主的三个 Activity：

| Activity | 职责 |
| --- | --- |
| `ChooserActivity` | **唯一入口**。两张卡片 + `USB_DEVICE_ATTACHED` 分类直达；按 VID/PID 判断，Apple 设备绝不会被送去走 AOA 握手 |
| `HostActivity` | AOA 投屏页（`UsbAttachRouter` → `LinkCoordinator` → 解码 → 触摸回传） |
| `ios.IosActivity` | QuickTime 投屏页（`MuxLink`/`QtTransport` → `QtSession` → `H264Decoder` + `PcmAudioPlayer`） |

> 原先 iOS 是一条独立的 `:app-ios-qt` 分支（单独 APK）。2026-10-18 合并进 `:app-host`，
> 合并方案见 [`docs/合入host_双协议方案.md`](docs/合入host_双协议方案.md)。

`:protocol` 之所以必须是**纯 JVM 库**，是因为整个项目里唯一能在没有真机时真正验收的部分就是它——
把纯逻辑（`AnnexB`、`AccessoryIdentity.encodeSendString`、`Scale` 等）全部下沉进来，
才能用 JVM 单测把它们钉死。日志走注入式 `Logger` 接口，USB 代码只存在于两端各自的 `ByteChannel` 实现里。

## 命名说明

产品名与技术标识不是同一个东西，**改名前请先看这张表**：

| 名称 | 值 | 能否随意变更 |
| --- | --- | --- |
| 产品名 | **UsbScreenMirror** | ✅ 随意 |
| Gradle 工程名 | `usbscreen` | ✅ 随意（仅影响 IDE 显示） |
| Android 包名 | `com.uav.host` / `com.uav.accessory` | ⚠️ 改了等于换应用，两端必须同步 |
| 配件身份 | `UAV` / `usbscreen` / `1.0` | ⚠️ **这是协议内容**，见下 |

配件身份（`manufacturer` / `model` / `version`）**参与系统匹配**，三处必须逐字一致：
`:protocol` 的 `AccessoryIdentity`、`app-accessory` 的 `accessory_filter.xml`、以及实际握手时发出的字符串。
（XML 无法引用 Kotlin 常量，属**手工镜像**，改一处必须同步另一处。）

## 运行

```bash
# 1) 两个包分别装上（adb 唯一被用到的场景就是这一步）
adb -s <宿主设备>  install -r -g app-host/build/outputs/apk/debug/app-host-debug.apk
adb -s <配件手机>  install -r -g app-accessory/build/outputs/apk/debug/app-accessory-debug.apk

# 2) 打开宿主（也可以直接在桌面上点图标）
adb -s <宿主设备> shell am start -n com.uav.host/.ChooserActivity
```

宿主打开后是**选择页**：两张卡片「安卓手机」/「iPad / iPhone」。插线时系统会带着设备描述符拉起它，
**能分类就直接进对应页面**，分不清才停在选择页让你点。

### 安卓手机（AOA）

1. 手机插上宿主 → 系统**可能**弹「**是否打开该 App 处理 USB 配件**」→ 勾选默认（此后插线即达）
2. 手机弹「**开始录制或投放**」录屏授权 → 允许（Android 14+ 每次都要点）
3. 宿主的 `SurfaceView` 上出现手机画面

### iPad / iPhone（QuickTime USB）

1. iPad 插上宿主 → 自动进入「iPad / iPhone」页，**自动开始**
2. **首次**：iPad 上弹「信任此电脑」→ 点信任（此后永久记住，不用再点）
3. 画面 + 声音自动出来，**不用按任何按钮**

**拔线即停**：拔掉 iPad，界面 1 秒内回到空闲态并提示「iPad 已断开」；
再插回去会自动重新开始，不需要退出重进。

⚠️ **会话一开始，iPad 上的播放会暂停**（设备把音频路由切到 USB 造成的，不是 bug）——
在 iPad 上再点一次播放即可，之后声音由宿主扬声器输出。

宿主界面是**左侧竖栏面板**（深色）—— 面板宽 300dp，横屏宿主下手机竖屏镜像只占中间一条、
两侧都是信箱边，**侧栏正好落在左边黑边里，不挡画面**：

| 控件 | 用途 |
| --- | --- |
| 左上「状态药丸」 | 彩色圆点 + 状态词（空闲 / 连接中 / 投屏中 / 重协商 / 出错）。面板收起后仍可见，**点它就是打开面板** |
| 「扫描 / 重试」 | 手动重新扫描设备。**部分宿主的 USB host 栈在手机重枚举后不发 attach 广播**，此时靠它（App 内已有 2 秒轮询兜底） |
| 「强制重握手」 | 强制走完整 AOA 握手，重写配件身份。用于「手机被别的宿主 App 切成配件模式」 |
| 「回放抓流」 | 调试用：回放 `.uav` 抓流文件，跳过整个 USB 与握手（**仅 debug 包**） |
| 「画质」分段控件 | `1:1 像素` ↔ `高清`，见下「已知限制」。默认 `1:1`，选择本地持久化 |
| 「链路状态」卡片 | 编码尺寸 / 画质口径 / 帧 / 丢帧 / 队列 / 延迟 / 音频电平（**紧凑 4 行**） |

面板在首帧到达时**自动收起**，点**信箱边空白处**或**状态药丸**可再打开，
面板右上角按钮收起。细节见 `docs/实施计划.md` **10.14 / 10.19**。

连不上时**先看 [`docs/排错手册.md`](docs/排错手册.md)**，那里面按「症状 → 根因 → 处置」组织，
并有一条最重要的排错手段：用 `.uav` 回放把问题切成「USB/协议」与「解码/渲染」两半。

### 已知的环境不稳定点

- ⚠️ **「等待重枚举超时」不是 OTG 不稳**（旧结论，已推翻）：真因是我们自己漏掉配件 fd，
  破坏了 `/dev/usb_accessory` 的**独占打开**，于是手机再也切不进配件模式。
  「重插拔即恢复」只是顺带杀掉了持 fd 的进程。**已在 10.8 修掉**（含 3 项回归单测），
  别再靠拔插去"确认"问题，用 `docs/实施计划.md` 10.8 的 fd 计数法。
- **供电与 OTG 常互斥**：手机当宿主时一边给配件供电、一边自己掉电。
  长时使用建议用 **OTG + 充电二合一线（带 PD 口）**。
- ⚠️ **宿主 kernel panic 是"我们的 App 触发的"，已在 10.16 修掉**。
  **旧结论「宿主固件/内核问题，App 层解决不了」是错的**：一天内连续三次 `kernel_panic,bug`
  都被这么归因过，直到拿到 MTK 完整 ramoops（`console-ramoops-0`）才看清现场 ——
  崩溃线程是 `Comm: uav-reader`（宿主端**我们的** bulk 读线程），栈是
  `usercopy_abort ← __check_object_size ← do_proc_bulk ← usbdev_ioctl`：
  协议层读 24B 报文头时把**小于端点包长 512B** 的长度透传给了内核，而 MTK 主机栈不把
  `actual_length` 截到请求长度 —— 设备交付 391B 时就拿 391 去拷 128B 的 bounce buffer
  → 加固 usercopy `BUG()` → 内核崩、设备重启。
  修法见 [`docs/实施计划.md`](docs/实施计划.md) **10.16**（`:protocol/BufferedByteChannel`：
  对内核永远整块 16KB 读 + 残留续读）。**长跑复验仍待做**（短时不崩 ≠ 修好）。
  定性"panic 是谁干的"的正确姿势（别再靠启动原因猜）：读完整 ramoops，
  搜 `kernel BUG` / `usercopy`，**看 `Comm:` 是谁** —— 见 `docs/排错手册.md` 3.9。
- **别随手 `am force-stop` 手机端 App**：App 会进入 stopped 状态，系统此后不再用隐式 intent
  （配件 attach）拉起它，很容易把「链路不通」误判成软件 bug。
- ⚠️ **先后顺序要紧凑：先起手机端、几秒内起宿主端**。手机端有 **12s 空闲看门狗**（判定为「假配件」时只释放不重连），
  间隔拖太久（超过 12s）会让手机端先把配件 fd 释放掉，宿主随即无限等 CNXN —— 很容易误判成链路 bug。
- **Git Bash 下操作 adb 要设 `export MSYS_NO_PATHCONV=1`**：否则 Android 绝对路径会被改写成 Windows 路径。

## 协议速览

### 安卓手机：AOA 上的私有流协议

两端必须逐字一致，完整清单见 [`docs/实施计划.md`](docs/实施计划.md) 第 4 节。

| 项 | 约定 |
| --- | --- |
| 报文头 | **24 字节，全小端**：`command / arg0 / arg1 / data_length / data_check / magic` |
| `magic` | `command xor 0xFFFFFFFF`——**字节流错位的第一道防线**（一旦错位，magic 必然对不上） |
| `data_check` | payload 逐字节无符号累加 |
| 命令字 | `CNXN / OPEN / OKAY / CLSE / WRTE`（裁剪掉 `AUTH` / `STLS`） |
| 流 id | `0=control` / `1=video` / `2=audio`；`WRTE.arg0` 是**唯一的流标识** |
| 流头 | 该流**首条** `WRTE` 的 12 字节 payload：`codecId`(4 ASCII) + `width` + `height` |
| 帧 | 每条 `WRTE` payload = `8B ptsAndFlags` + `4B size` + 码流 |
| `ptsAndFlags` | bit63 = CONFIG、bit62 = KEY_FRAME、bit61 预留方向（本期未启用） |
| 上限 | `data_length` 与帧 `size` 均 ≤ **8 MiB** |
| 超时 | `controlTransfer` **1000ms（严禁 0，0 = 无限等待）**；bulk 读 200ms / 写 5000ms |

另外两个关键约定：

- **CONFIG 帧永不吞掉**：解码器配置依赖它，丢了会导致空参数 `configure`。
- **丢弃 P 帧的代价是花屏**，最长 = I 帧间隔（本项目取 **3s**）。

---

### iPad：QuickTime USB 协议

宿主当 USB 主机，claim 平板的 `0xFF/0x2A` 接口（`0x86` IN / `0x05` OUT），报文格式：

| 项 | 约定 |
| --- | --- |
| 报文 | `u32 长度`（含 4B 头）+ 4B fourcc + 负载；**fourcc 线上是字节反转的**（`fcc()` 必用，禁止字面量） |
| 会话 | `PING` → `CWPA`（音频时钟）→ `CVRP`（视频时钟）→ `FEED`/`EAT` |
| 主机→设备 | 全部是 `RPLY`：`clock` / `afmt` / `skew` / `zero`，另有 `NEED`（要下一帧，带视频时钟） |
| 视频 | `ASYN/FEED`：`CmSampleBuf`，`sdat` 段装 H.264 NAL |
| 音频 | `ASYN/EAT!`：同构 sbuf，`sdat` 段装**裸 PCM**（`fdsc` 里给 ASBD，实机 `lpcm 48k/16bit/2ch`） |
| 收尾 | `hpa0`/`hpd0` → 等 2 个 `ASYN/rels`（途中应答 `SYNC stop`）→ 再补 `hpd0` |
| 启用采集 | `activate`（`0x40/0x52 wIndex=2`）只有在**当前配置为 3** 时才真重枚举；判据是「配置集 4→5」 |

⚠️ 这套协议的坑集中在**字节级**：`lpcm` 写成裸 ASCII、`og! ` 与 `go! ` 搞反，都会让设备
**静默不推音频**（不报错、不崩溃）。所以出站报文一律与真机样本做逐字节断言
（`:protocol` 的 `QtPacketFixtureTest`），排查顺序见 `docs/iOS_USB投屏_安卓实现.md` §三·五。

### 已知限制

#### iPad / iPhone（QuickTime USB）

- **只读投屏，没有触摸回传**：iOS 侧不存在 USB 输入通道，要反过来控制 iPad 得走 BLE HID 或网络，
  本期不做。
- **没有 A/V 同步**：音频按 ~200ms 缓冲直接写 `AudioTrack`，没有和视频 PTS 对齐。
  单看视频或单听音频都正常，长时间连看可能有几十毫秒漂移（手机那条路的 A/V 同步是完整的）。
- **会话开始会让 iPad 上的播放暂停**：设备把音频路由切到 USB，播放器需手动再点一次播放。
  这是设备行为（Windows 上的 iPhoneMirror 同样如此），不是本项目的 bug。
- **首插时可能要唤醒一次**：配对会清掉设备侧的采集武装态，必须让它真重枚举一次。
  正常情况下自动流程里的「激活」会完成这一步；若插上后一直停在「正在建立连接」，
  面板里点一次「**重新唤醒采集通道**」即可（这是唯一保留的手动兜底入口）。
- **不支持同时投两台**：同一时刻只有一条链路（一个 Surface、一个 AudioTrack、一份 USB 带宽）。

#### 安卓手机（AOA）

- **旋转已支持**：手机侧需**开启自动旋转**。虚拟屏全程复用（`MediaProjection` 令牌
  只允许 `createVirtualDisplay` 一次）、编码器按新尺寸重建、新尺寸经**重发 12B 流头**
  告知宿主 —— 宿主会自动按新方向重配解码器。设计与实测见 `docs/实施计划.md` 10.7。
- **延迟已实测**：端到端 p50 **64ms** / p95 **140ms**（fresh 口径，n=300，见 `docs/实施计划.md` 10.6）。
  ⚠️ 该口径**不含最后 1 个 vsync**（约 8~16ms）；按加上界算 p95 ≈ 148~156ms，
  即**正好卡在 150ms 线上**，不能算轻松达标。
- **断链会自动恢复**：拔插或链路抖动后**无需任何人工操作**，约 1.5s 内画面自己回来，
  且**不会重新弹录屏授权**（投影与编码器都保留）。见 `docs/实施计划.md` 10.8。
- **切后台不会断链**：`SurfaceView` 的 Surface 被销毁时只**停渲染、保持链路**，
  回前台用缓存的 CONFIG 重建解码器 —— 全程**不触发 USB 重枚举**，
  也修掉了原先"按 Home 就崩"的问题。见 10.10。
- **HID 触摸注入已探针验证**（宿主 → 手机）：手机上会真的多出一块**触摸屏**
  （`INPUT_PROP_DIRECT` + `ABS_MT_*`），注入的坐标逐字节精确到达 —— **手机端零改动**，
  且走 EP0、不占视频带宽。⚠️ **重枚举会清掉注册**（id 只在连接内有效），必须重新注册。见 10.9。
  （10.9 当时只是 adb 驱动的探针；**正式流程已在 10.11 接通**，见下一条。）
- **触摸可以反向控制手机**（路线图 P1「输入通道」）：直接用**宿主的屏幕当手机的触控屏**
  —— 点、拖都行，手机上同一个位置就发生同一次触摸。走 AOA HID，**手机端零改动**、
  不占视频带宽；**最多 5 指同时**（双指缩放可用）；已处理旋转、重连重注册、残留清理。见
  `docs/实施计划.md` 10.11（单指）/ **10.12（多点）**。
- **有音频（内录）**：Android 10+ 用 `AudioPlaybackCaptureConfiguration` 把手机**正在播放**的
  声音录下来，AAC-LC 128kbps 经 `AUDIO` 流送到宿主播放 —— 是"手机里响什么宿主就响什么"，
  **不是**麦克风（不会把环境噪音也带过去）。真机实测：抖音/游戏的声音两端电平逐拍吻合。见
  `docs/实施计划.md` **10.13**。⚠️ 只能捕获 `USAGE_MEDIA`/`USAGE_GAME`/`USAGE_UNKNOWN`；
  通话、通知、铃声，以及声明了 `allowAudioPlaybackCapture="false"` 的应用（银行/DRM）
  **按设计录不到**。
- **切到后台自动静音**（10.22）：宿主退到后台（或锁屏）时 `AudioTrack.pause()`，
  回前台 `flush()` 掉暂停期间积压的旧 PCM 并**重新锚定音频时钟**后恢复 ——
  后台那几十秒手机一直在采集，不重锚的话音频播放头会与帧 pts 错开几十秒。
  真机实测：长暂停 22s 内 PCM 写出计数**完全冻结**（一字节都没多写），回前台立即恢复出声。
  ⚠️ 暂停期间必须**停止喂帧**：`AudioTrack` 暂停后不消费缓冲，而写出是 `WRITE_BLOCKING`，
  继续喂会把音频消费线程永久阻塞。见 10.22。
- **A/V 已有精细同步**（10.20③）：以**音频播放头**（`AudioTrack` 已渲染帧数）为基准，
  偏晚的帧丢掉、偏早的帧**有界等待**后上屏，并用限幅 EMA 持续吃掉两台设备的时钟漂移。
  能力边界：视频交给 `SurfaceFlinger` 合成，**无法给视频重新定时**，所以只能"丢/等"。
  真机 2.5 分钟 4485 帧：偏移稳定在 **7~20ms**、**一帧未丢**。三道安全门（没有音频 /
  时钟标定不可靠 / 音频播放头停住）任一命中就退回"照旧渲染"，其中"音频停住"最关键 ——
  不兜住就会把视频全丢光（画面黑）。
- **点画面外的空白处可显示/隐藏宿主面板**：视频区内的触摸全部留给"反向控制手机"，
  左/右黑边（信箱边）上的点击才是面板开关；首帧到达时面板自动收起一次，出错/断开时自动展开。
  **面板收起后左上有「状态药丸」**（彩色圆点 + 状态词），**点它就是打开面板** —— 不会"无路可回"。
  见 `docs/实施计划.md` **10.14 / 10.19**。
- **1:1 像素映射**：编码尺寸按**宿主实际显示区**算（不再只看长边），宿主端不做二次缩放。
  实测编码像素从 1.67 Mpx 降到 0.45 Mpx（27%），清晰度不降、编解码工作量大幅降低。
  手机旋转时尺寸**自动重算**（不需要重新协商）；宿主自己旋转会把显示区变化交给**原地重协商**（10.18）。
  见 10.15。
- **像素模式开关**（宿主面板「画质」分段控件）：`1:1`（按宿主显示区编码，省算力）↔
  `高清`（按面板长边编高分辨率、宿主端缩下去 = 效果上超采样，观感更锐）。选择本地持久化。
  切换走**原地重协商**（在同一条连接上重发 `OPEN`，不重连、约 2~3s）。见 10.17 / 10.18。
  ⚠️ 两种模式**码率都固定 8 Mbps** —— 1:1 降的是像素不是字节，高清则是"每像素比特被摊薄"；
  真省流需要按面积缩放码率（见路线图 P1）。
- **切换/重连不再花屏**（10.20②）：手机端在"新会话接入"后先等到下一个 **IDR** 才推帧
  （并向编码器立刻要一个），而不是把缺 IDR 的 GOP 尾巴丢给宿主的新解码器 ——
  那会让画面花到下一个 I 帧（实测周期 3s）。另有 600ms 超时兜底：等不到 IDR 就放行，
  **宁可短暂花屏也不要黑屏**。
- **切后台再回前台不再黑屏几秒**（10.21）：回前台必须新建解码器（`MediaCodec` 的 output
  surface 不能改绑），而新解码器没有参考帧 → 必须先见 IDR。宿主现在会发一条新的
  **`RQID`** 命令字向手机**立刻要一个关键帧**，并在本地先挡住缺 IDR 的 P 帧。
  切后台不属于"新会话"，所以 10.20② 那条门控走不到，必须有这条窄通道
  （⚠️ 绝不能重发流头 + CONFIG，那会把解码器搞乱）。
  **真机实测：黑屏从最长 3 秒降到 40~50ms**（手机端收到 RQID 后 1~2 帧内恢复推流）。见 10.21。
- **面板状态不再自相矛盾**（10.23）：以前状态行是**被事件流无条件覆盖**的，而事件里混着
  「瞬时进度」（`会话已建立，等待视频流…`）与「持久状态」（`投屏中`）两种语义。最典型的是
  **原地重协商**：画面根本没断，`onStatus` 却照旧发"等待视频流"，而 `onFirstFrame`
  不会再来 ⇒ 状态行被永久钉死，同时药丸是绿的 ⇒「药丸说投屏中、状态行说等待视频流」。
  现在改为**显式状态机**（`:protocol/HostUiState`，纯逻辑有单测）+ **主行 / 副行分离**：
  主行只说处于哪个阶段，副行只说刚发生了什么；**进度事件永远不能降级已到达的阶段**。
  见 10.23。
- **`HostActivity` 从 1262 行瘦到 498 行**（10.24）：它原来同时干 6 件事（View 渲染、链路编排、
  画质策略、触摸转发、调试入口、回放），任何改动都要同时维护 6 条线。现在拆成
  `HostPanel`（View）/ `LinkCoordinator`（链路）/ `QualityController`（画质）/
  `TouchForwarder`（输入）/ `DebugIntents`（调试）五层，**层间只汇报事实、不互相决策**；
  `HostActivity` 只剩装配与生命周期。实现语义（阈值、时序、顺序要求）一字未改。
  ⚠️ 代价是复盘出两个只有真机能发现的坑：抽 View 层时把 `findViewById` 放进后置的 `bind()`
  会导致启动即崩（`lateinit`）；而**漏抄 `onNewIntent()`** 会让所有 `am start --ez …`
  调试入口静默失效、且前台时系统派的配件 attach intent 不被处理。见 10.24。
- **宿主前台保持亮屏**（10.25）：宿主这块屏就是显示器，一息屏画面就没了、也没人会去点它唤醒。
  用 `FLAG_KEEP_SCREEN_ON` 而不是 `WakeLock` —— 前者由 WindowManager 按**窗口可见性**自动管理
  （切后台/锁屏立刻失效，不需要手动 release），后者漏 `release()` 就是永远不睡。
  它只阻止息屏、不改亮度，手动按电源键仍能立刻息屏。真机对照：前台 28s 不睡 / 切后台 22s 就睡。
- **面板不再反复"显示→隐藏"**（10.26）：`setMenuVisible(true)` 原先**不幂等** ——
  哪怕菜单已经展开着，也照样把 `alpha` 拉回 0 再淡入一遍。而启动初期链路要重试好几轮，
  `onError` / `onClosed` 连着触发十几次，每次都重播动画 ⇒ 面板一顿乱闪。
  现在 ① 已到位就直接返回；② 区分"系统叫出来报错"（`revealMenu`，画面恢复后自动收回）
  与"用户自己点开"（`toggleMenu`，绝不被首帧抢走）。见 10.26。
- **全屏**（10.27）：隐藏状态栏与导航栏（`setDecorFitsSystemWindows(false)` +
  `BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE`），边缘一划仍能临时调出系统栏。
  ⚠️ 必须**在 `onWindowFocusChanged` 里重新隐藏** —— 切后台回来 / 划出系统栏后它们会赖着不走，
  只在 `onCreate` 设一次是不够的。面板与药丸按 insets 避让刘海/手势条（视频区不避让，画面延伸才正确）。
- **宿主支持到 Android 6.0**（10.28）：`app-host` 的 `minSdk` 从 24 降到 **23**，一行改动、零代码修改
  —— 因为当初选 24 时用到的最高 API 恰好是 23（`AudioTrack.Builder`、`WRITE_BLOCKING`、
  `Context.getColor`、`drawableTint` 都是 23；Material 主题 / MediaCodec 新 buffer API / VectorDrawable 是 21）。
  Android **4.4 则要改 34 处**（lint 实测），Material 主题在 4.4 根本不存在，不建议。
  手机端保持 24（它依赖 `MediaProjection`(21+) 与前台服务类型(29+)，跑在 A16 上）。
- **两端有了自己的图标与中文名**（10.29）：之前 manifest 里**只有 label、没有 `android:icon`**
  （lint 一直在报 `MissingApplicationIcon`），后果比想象的严重 —— 手机上**桌面上根本找不到 App**，
  最近任务里名字也是空的。补上自适应图标后就正常了。视觉上靠**方向 + 颜色**区分两端：
  蓝屏 + 左箭头 =「投屏接收」，绿屏 + 右箭头 =「投屏发送」（白底、内容内缩 86%）。
  英文名对应 `Cast In` / `Cast Out`。见 10.29。
- **画面停了不再装作没事**（10.30）：手机端编码器可能"活着但不产帧"（虚拟屏在、链路也连着，
  就是 `dequeueOutputBuffer` 一直 `TRY_AGAIN`）。以前宿主界面照旧写「投屏中」，用户只看到画面冻住，
  无从判断原因。现在两端各加一道：宿主用 `:protocol/StreamHealth` 按"最后帧距今多久"分
  **健康 / 可疑(3s) / 已停(10s)** 三档（可疑只进副行，避免闪烁），停摆时主行显示「手机无输出」+ 黄色药丸；
  手机端 8 秒没有产出就主动 `CLSE("编码器 N 秒没有输出画面")`，比宿主的 10 秒更早，
  让"自报"先发生。见 10.30。
- **延迟从 143ms 降到 71ms**（10.31）：两端原来**一个低延迟参数都没设**，编解码器全走默认档，
  而默认档为了吞吐会在内部攒 5~7 帧（≈100ms @60Hz）。现在编码器请求 `priority=0`、`latency=0`、
  **`max-bframes=0`**（B 帧要等后续帧才能编，天然多 2~3 帧），解码器请求 `low-latency=1`。
  ⚠️ 副作用：视频提速后音频没跟上，`avsync offset` 从 `+7~20ms` 变成 **-117ms**
  （画面比声音早约 0.12 秒）。"操作手机"场景无感，放视频时口型会对不上。见 10.31。
- **停止投屏是"双向"的**（10.32）：手机端点「停止投屏」会发 `CLSE("用户停止投屏")`，
  宿主立刻知道是**人为停止**而不是链路故障 —— 主行显示"正在建立连接…"，副行把原因
  **钉住**（「手机端已停止投屏 —— 在手机上点「授予录屏权限」即可恢复」），不会被后续
  重连进度刷掉；同时宿主**继续自动重连**，用户点完授权就能接上，无需拔插。
  以前 `close()` 一个报文都不发，宿主只能靠读超时发现，且在"停止 → 再授权"这条路上
  会永久卡死（详见 10.32 的 7 处修复）。
- **停止/重连不再崩、不再 ANR**（10.33）：手机端 `AudioPipeline.stop()` 原先"先停编码器再
  join 线程"，编码线程正好走到 `getInputBuffer()` 就撞 `Invalid to call during stop()`，
  未捕获 ⇒ `uav-audio` 线程 FATAL；现在改成"先让线程自己退出，最后才释放编码器"，并把
  每个 MediaCodec 调用逐个兜住。宿主侧 ANR 的根因是 `BufferedByteChannel.close()` 去抢
  **读线程正在阻塞 USB 读**的那把锁（主线程堵 5 秒），现在 `close()` 只置 `@Volatile` 标志，
  且关会话整体搬到后台单线程队列。
  ⚠️ 顺带挖出两个**只在验证时才现形**的坑：`stopCapture()` 写成调自己导致无限递归
  （一直被 `runCatching` 吞掉），以及"会话断了就销毁编码器"会让重连再也建不出虚拟屏
  （`MediaProjection` 令牌只能 `createVirtualDisplay` 一次）。见 10.33。
- **每帧少一次分配、少一次拷贝**（10.34）：`WRTE` 帧的载荷是「12B 元数据 + 码流」，
  以前先整包读进一个 `ByteArray`、再由 `decodeFrame` 把码流 `arraycopy` 一份 ——
  每帧两次分配、两次拷贝。现在**读的时候就拆开**：元数据进 12B 复用缓冲、码流直接读进
  它自己的数组，每帧省掉 1 次 ~30~50KB 分配 + 1 次整包拷贝。同时把宿主读块
  **16KB → 64KB**（一帧 30~50KB 原来要 3 次 `bulkTransfer`）。
  ⚠️ 这不等于"变快"：码率 8Mbps ≈ 1MB/s，两次 memcpy 只占 0.02% 个核，
  真正的成本在内核 `usbfs` 与驱动调度上 —— 也正因如此**评估过不写 JNI**（见 10.34）。
- 无鼠标/键盘输入。
- 无传输加密——安全性完全依赖**物理接触**。
- 静态画面下约 **10 fps 属正常**（`KEY_REPEAT_PREVIOUS_FRAME_AFTER=100ms` 兜底送帧），不是性能问题。
