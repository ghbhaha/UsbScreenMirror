# USB Accessory（AOAv2）投屏项目 · 分步实施计划

> 依据：`docs/配件投屏核心原理.md`
> 目标：**在无 USB 调试、无 adb 授权、零推送的前提下，宿主 Android 设备经 OTG 线接收手机端实时投屏。**
> 版本：**v2.1（动工前优化版 + 选型确认）** —— 相对初版的改动见 [附录 A](#附录-a-相对初版计划的优化点)；v2.1 补入四项已确认决定（宿主设备 / 交付形态 / 首期姿态 / 联调节奏）与由此推出的 `max_size`、`video_bit_rate` 参数修正，见 0 节与 0.1 节。

## 0. 选型与范围（已确认）

| 项 | 决定 |
| --- | --- |
| 语言 | Kotlin |
| UI | View 体系（`SurfaceView` + `MediaCodec` 原生 API），不引入 Compose |
| 工程结构 | 单 Gradle 工程 · 三模块：`:app-host` / `:app-accessory` / `:protocol` |
| **`:protocol` 形态** | **纯 Kotlin/JVM `java-library`（零 Android 依赖）** —— 见 1.1，这是"JVM 单测全绿"能真正验收的前提 |

| **交付形态** | **两个独立 APK** —— 宿主装 `:app-host`、手机装 `:app-accessory`，职责与权限声明互不污染，调试时两个 logcat 互不干扰。后期可用 source set / flavor 合并为单包 |

| **姿态（v2.2）** | **已支持旋转**（P0 落地，见 10.7）：虚拟屏复用 + 编码器重建 + 重发流头 |
| **联调节奏** | **先做离线回放通道，再上真机**（见第 7 节 —— 已确认为阶段 4 的第一步，不是可选项） |
| SDK 路径 | `<你的 SDK 路径>`（需含 `platforms`、`build-tools`、`platform-tools`（含 `adb.exe`）、`cmdline-tools`） |
| JDK | `<你的 JDK 路径>`（需 **JDK 17+**，AGP 的下限）—— 注意别让 PATH 里的更高版本 JDK 劫持构建 |

### 0.1 期望管理：开工前必须先讲清的三件事

这三条不是"实现问题"，而是**做成了也改变不了的现实**。先说清，免得验收时预期错位：

**1）Android 14+ 每次投屏都要点一次授权，省不掉。**
Android 14（API 34）起取消了 MediaProjection 的"记住选择"，且投影 token 一次性（`createVirtualDisplay` 只能调一次）。所以"插线即投"在现代系统上仍会多一次「开始录制 / 共享屏幕」的点击。
**但这不影响核心价值**：被省掉的是 **adb 调试授权 + 开发者选项 + RSA 密钥协商 + 服务端推送**，这部分依然是完全零配置的。
→ 待确认两台手机的 Android 版本；若确定只跑 Android 13 及以下，3.4 的兼容分支可以简化。

**2）姿态：已支持旋转（v2.2）。** 首期曾要求手机姿态固定并锁定方向；现在旋转已落地 —— 虚拟屏全程复用（令牌只允许 `createVirtualDisplay` 一次）、编码器按新尺寸重建、新尺寸经重发流头告知宿主。手机侧需**开启自动旋转**。设计与实测见 **10.7**。

**3）手机当宿主时，「供电」与「OTG」常常互斥。** 宿主手机要经 OTG 给配件手机供电、自身持续掉电；而多数手机在 OTG 工作模式下**无法同时从充电口取电**。长时联调需要 **OTG + 充电二合一线（带 PD 供电口）**，否则 5 分钟压测会变成"电量压测"。已加入第 6 节准备清单。

## 1. 目标架构与模块划分

### 1.1 关键设计决策：三层分离

协议层要能在 JVM 单测里跑通（不依赖真机），就必须把**平台相关的字节搬运**与**协议逻辑**彻底切开：

```
        ┌──────────────────────────────────────────────┐
        │  :protocol  —— 纯 Kotlin/JVM，零 Android 依赖       │
        │                                              │
        │  Connection     读线程状态机 / 写侧串行化        │
        │       │                                      │
        │  Transport      readFully / write / 统计       │
        │       │         ★ 凑满读、丢弃 0 字节完成(ZLP)   │
        │  ByteChannel    纯接口：read/write/close       │
        │  (interface)    ← 可能短读、可能 0 字节完成      │
        └───────┼──────────────────────────────────────┘
                │ 两端各自实现（各约 30~60 行）
      ┌─────────┴──────────┐
      │                    │
┌─────▼──────────┐  ┌──────▼─────────────┐
│ :app-host      │  │ :app-accessory     │
│ BulkByteChannel│  │ FdByteChannel      │
│ (bulkTransfer) │  │ (accessory fd)     │
│ FileByteChannel│  │                    │
│ (离线回放/调试)  │  │                    │
└────────────────┘  └────────────────────┘
```

**为什么这样切**：
- **ZLP 容错只写一次**，且能在 JVM 里被测（注入一个"偶尔返回 0 字节"的假 `ByteChannel`）。
- 两端字节语义**并不对称**，但不对称性被 `ByteChannel` 这一个接口吃掉：

  | 侧 | 底层 | 语义 | `ByteChannel` 实现要处理 |
  | --- | --- | --- | --- |
  | 手机（accessory） | accessory fd 的 `FileInputStream/OutputStream` | 近似**流**，但 `read()` 可能短读，也可能 0 字节完成 | 包 `ParcelFileDescriptor`；`close()` 用于打断阻塞写 |
  | 宿主（host） | `UsbDeviceConnection.bulkTransfer` | **包**语义，需自己拼成流 | 循环收包拼满；写时按 `maxPacketSize` 整数倍分片并补 ZLP；短超时便于检查退出标志 |
  | 离线回放 | 本地文件 | 纯流 | 读一个 `.uav` 抓包文件（见第 7 节） |

**契约（必须严格遵守）**：
```kotlin
/** 平台层字节搬运。read 允许短读、允许返回 0；返回 -1 表示断开。 */
interface ByteChannel : Closeable {
    /** 返回实际读到的字节数，可能 < len，可能 == 0；-1 = 对端关闭。允许超时后返回 0（非致命）。 */
    fun read(dst: ByteArray, off: Int, len: Int): Int
    fun write(src: ByteArray, off: Int, len: Int)
    override fun close()
}

/** 协议层。上层只依赖它，永不感知 USB。 */
class Transport(private val ch: ByteChannel, ...) {
    /** 阻塞直到凑满 len。内部：丢弃 0 字节完成并重试；凑满才返回。 */
    fun readFully(dst: ByteArray, off: Int, len: Int)   // 失败抛 IOException
    fun write(src: ByteArray, off: Int, len: Int)       // 可中断
    /** 一次读取一小块交给状态机用（避免为 24B 报文头做 32KB 凑满）。 */
    fun readAtMost(dst: ByteArray, off: Int, len: Int): Int
}
```

> ⚠️ **`Transport.readFully` 永不返回 0（除 EOF/异常）**。ZLP 处理封在 `Transport` 内部，上层状态机拿到的永远是有效字节。初版把 ZLP 写在"阶段 1.6"、与 Transport 平级，职责边界是错的。

### 阶段 1 · 协议层（`:protocol`）—— 不依赖真机即可验证

| # | 动作 | 关键点 |
| --- | --- | --- |
| 1.1 | `ByteChannel` 接口 + `Transport` | **ZLP / 凑满读 / 0 字节完成丢弃全部封在 `Transport`**，上层永不接触 |
| 1.2 | `AdbMessage`：24B 小端头编解码 | `magic = command xor 0xffffffff`；`data_check` = payload 逐字节无符号累加（u32 截断）；**`data_length` 上限 8 MiB**，超限判协议错误（防伪造头导致 OOM）；magic/checksum 不符必须抛错，**不静默跳过** |
| 1.3 | `Command` / `StreamId` / `CodecId` / `Flags` 常量 | 与第 4 节冻结清单逐字一致 |
| 1.4 | `Connection` 读写线程模型 | **单读线程**：`readAtMost` → 喂状态机 → 按 `WRTE.arg0` 投递到对应流的**有界队列**；**单写线程**：所有写（含流头、帧、OKAY、CLSE）经同一写队列串行化，避免多线程交错写入 |
| 1.5 | `FrameQueue` + 丢帧策略 | 容量 4 帧；满时丢最旧非关键帧（见 4.7）；`CLSE`/异常时唤醒所有等待者 |
| 1.6 | `FrameCodec` | 12B 流头（`codecId`+`width`+`height`）；帧 = 8B `pts+flags` + 4B `size` + payload；**`size` 上限 8 MiB** 同样校验 |
| 1.7 | `Options` | `newScreen<videoId>:<audioId> <参数键值对>` 的构造与解析，两端**共用同一实现**，杜绝手写字符串不一致；未知参数忽略而非报错 |
| 1.8 | `Logger` 接口 + `Hex` | 日志走注入（JVM 库不能用 `android.util.Log`）；`Hex.dump` 用于联调打前 64 字节 |
| 1.9 | 统计 | 每流累计字节/帧数/丢帧数，`Connection.stats()` 供两端定期打印 |

**单测清单（纯 JVM，`protocol/src/test`）**

| # | 用例 | 目的 |
| --- | --- | --- |
| 1 | 报文往返编解码一致 | 基础正确性 |
| 2 | magic 错 / checksum 错被拒绝 | 防静默错位 |
| 3 | 报文头被拆成 3 段投喂，状态机仍正确 | 跨边界读 |
| 4 | **注入"偶尔返回 0 字节"的假 `ByteChannel`，`readFully` 仍凑满且不越界** | ★ ZLP 容错（这是初版无法测的点） |

| 6 | flags：`1<<63`=CONFIG、`1<<62`=KEY_FRAME；普通 PTS（含秒级大值）不误判 | 位复用安全 |

| 8 | 有界队列满 → 丢最旧非关键帧、关键帧被保留 | 背压策略 |
| 9 | `WRTE.arg0` 分流：混投 control/video 帧，各自队列内容正确 | ★ 分流正确性 |

### 阶段 2 · 宿主端 AOA 握手（`:app-host`）

| # | 动作 | 关键点 |
| --- | --- | --- |
| 2.1 | Manifest：投屏 Activity `launchMode="singleTask"` + `exported="true"` + `USB_DEVICE_ATTACHED` **空过滤** + `onNewIntent` 复用实例 | 空过滤 `<usb-device />` 才能覆盖"手机仅充电、无 MTP 接口"的插线场景 |
| 2.2 | 经 intent 入口启动时系统**自动授予 USB 权限**；同时保留 `hasPermission` 门控 + `requestPermission()` 兜底 | `requestPermission` 的 `PendingIntent` **必须带 `FLAG_IMMUTABLE`**（API 31+ 否则崩） |
| 2.3 | `AoaHandshake`：`controlTransfer(0xC0, 51, 0, 0, buf, 2, timeout)` 取协议版本 | **timeout 传 1000（ms），绝不传 0** —— 0 表示无限等待，与"所有阻塞等待必须带超时"自相矛盾。直接 `openDevice()` 后发控制请求，**不要先 claimInterface** |
| 2.4 | `SEND_STRING`(52) × 6：index 0..5 = manufacturer / model / description / version / **URI** / serial | 字符串必须 **UTF-8 且含结尾 `\0`**（★ 初版写的是 UTF-16LE，**已被真机推翻，见 10.4**），单段 ≤255 字符；manufacturer/model/version 三者要与手机端 `accessory_filter.xml` 完全一致 |
| 2.5 | `START_ACCESSORY`(53) → 立即关闭旧 `UsbDeviceConnection` | 手机将重枚举，旧 handle 失效 |
| 2.6 | 等待重枚举：**200ms × 25 次（共 5s）** 轮询 `UsbManager.deviceList`，按 **PID `0x2D00`（配件）/ `0x2D01`（配件+ADB）** 识别；超时转 `onError` | **不要按 interface class 识别**（配件接口与 adb 接口 class/subclass/protocol 同为 255/66/1） |
| 2.7 | **重枚举后重新检查权限**：新设备是"新设备"，`hasPermission` 可能为 false → `requestPermission()` 并在回调中继续；UI 提示"等待授权" | 这是常被忽略的一步：只靠 2.2 的自动授权在部分机型上不够 |
| 2.8 | `BulkPair`：新设备 `claimInterface(0)`，遍历 `UsbInterface.getEndpoint()` 按 `direction/type==BULK` 选定 in/out（通常 `0x81`/`0x02`），**并打日志** | 端点地址写死前先看日志确认；不同机型可能不同 |
| 2.9 | `BulkByteChannel`：读侧 `bulkTransfer(inEp, buf, 0, chunk, 200ms)` 循环；写侧 `bulkTransfer(outEp, src, off, len, 5000ms)` 并处理 ZLP | 读超时取 200ms 是为了让循环能检查退出标志；chunk = 16384B |
| 2.10 | 断连与异常收敛：`DETACHED` 广播 + 读写异常双路径统一到 `onError`；释放顺序：**停读线程 → 停写线程 → `releaseInterface` → `connection.close()`** | 释放资源里不要写 HID（MVP 无 HID） |
| 2.11 | 线程约束：**所有 `controlTransfer` / `bulkTransfer` / `openDevice` 一律在 worker 线程** | 在 UI 线程做 USB 操作会 ANR |
| 2.12 | UI：`SurfaceView` 占位 + 状态文本（扫描中 / 等待授权 / 握手 / 已连接 / 错误码） | 联调全靠它看进度 |

**验收**：宿主插线 → 日志出现 `AOAv2 version=2` → `START_ACCESSORY sent` → `re-enumerated PID=0x2D01`（实测；规范 0x2D01=配件+ADB）→ `permission=ok` → `interface claimed, in=0x81 out=0x01`。

> 旁证手段：把手机接到 PC 上，用 Windows 设备管理器 / USBView 观察 VID/PID 是否变为 `18D1:2D01`（Google 配件 VID；纯配件为 `2D00`）。**这一条已被真机实测推翻过一次**，见 10.4 的更正表。

## 4. 协议冻结清单 v2（两端必须逐字一致）

### 4.1 报文头（24 字节，全小端）

```c
struct message {
    unsigned command;       // 命令字
    unsigned arg0;          // 参数 0（语义见 4.2 表）
    unsigned arg1;          // 参数 1（语义见 4.2 表）
    unsigned data_length;   // payload 长度，上限 8 MiB
    unsigned data_check;    // payload 逐字节无符号累加（u32 截断）
    unsigned magic;         // command ^ 0xffffffff
};
```

命令字：`CNXN / OPEN / OKAY / CLSE / WRTE`。**裁剪掉 `AUTH / STLS`**（配件模式物理上即认证）。

### 4.2 命令语义表 ★（初版缺失，是最大的空白）

**流 id 固定为常量、不再区分 local/remote**（两端都是我们的代码，固定 id 可消除整整一类错位 bug）：

| 流 | id |
| --- | --- |
| `STREAM_CONTROL` | `0` |
| `STREAM_VIDEO` | `1` |
| `STREAM_AUDIO` | `2`（MVP 不启用） |

| 命令 | 方向 | `arg0` | `arg1` | payload |
| --- | --- | --- | --- | --- |
| `CNXN` | 双向 | **协议版本**（MVP = `1`，要求 ≥1） | `0` | **≥8B**：小端 `width` + `height`。**16B**（4.10 起）：再追 8B **本端单调时钟读数**（ns），用于两端时钟标定 —— 两端都只读前 8B，故**向后兼容** |
| `OPEN` | 宿主→手机 | `STREAM_CONTROL`(0) | `0` | 服务串，**必须以 `\0` 结尾**（服务串见 4.3） |
| `OKAY` | 手机→宿主 | `STREAM_CONTROL`(0) | `0` | 空 |
| `CLSE` | 双向 | 流 id；`0xFFFFFFFF` 表示整条连接关闭 | `0` | UTF-8 原因串（≤128B，可为空） |
| `WRTE` | 双向 | **流 id**（★ 接收端据此分流） | `0` | 该流的数据（流头或一帧，见 4.4） |

要点：
- **`WRTE.arg0` 是唯一的流标识**，接收端按它把 payload 投递到对应队列。初版只说"按命令字分发到对应流"，但 `WRTE` 是三流共用的命令字，**不定义 arg0 就无法分流**。
- `AUTH` 已裁剪，收到即视为协议错误。
- 控制流（id 0）在 MVP 中**只承载会话级报文**，不承载数据；`WRTE` 出现在控制流上属非法（二期 ping 才用）。
- 未知命令字 / 未知流 id → 记日志并忽略该条报文，**不中断连接**（向前兼容）。

### 4.3 OPEN 服务串

```
newScreen<videoId>:<audioId> max_size=<宿主算出的值>&video_bit_rate=8000000&max_fps=30&audio=false
```

- `videoId` = `1`、`audioId` = `2`（固定值，与 4.2 的流 id 常量一致）。
- `audio=false` 表示不启用音频流 → 宿主**不等待、不读取** `STREAM_AUDIO`。
- **`max_size` 由宿主计算后下发**（不是两端各自写死的常量）：CNXN 交换完成后宿主已知**两边**的屏幕长边，取
  `max_size = align8( min(手机屏幕长边, 宿主屏幕长边) )`。
  理由：宿主设备就是另一台安卓手机，两边分辨率相近 —— 这样取值的直接结果是**编码尺寸≈宿主可显示尺寸，宿主端不做任何放大**，画面最清晰且不浪费码率。
  例：手机与宿主同为 1080×2400 → `max_size = 2400` → 编码输出 1080×2400，接近 1:1 镜像。
- 参数以 `&` 分隔、`key=value` 形式；未知 key 忽略而非报错。
- 服务串末尾的 `\0` 由 `Options` 统一负责（易漏点）。

### 4.4 流内格式与「尺寸权威来源」★

```
一条流的数据全部装在若干条 WRTE 里，arg0 = 该流 id：

WRTE #1 (首个)   payload = [12B 流头：codecId(4 ASCII) + width(4) + height(4)]
WRTE #2..N       payload = [8B ptsAndFlags] [4B size] [size 字节 码流数据]
```

- **流头每条流仅发一次**，且必须是该流的第一条 `WRTE`。
- `codecId` 取值：`avc1`（H.264）/ `raw` / `aac` / `opus` / `flac`。
- **`width`/`height` 是唯一的尺寸权威来源**，即编码器实际输出尺寸（例：`720×1600`）。
  宿主 `MediaCodec.configure` 的 `width`/`height` 取此值；`SurfaceView` 的宽高比也取此值。
- **尺寸不来自 SPS 位流解析**。MVP **不需要**解析 H.264 SPS 语法——初版"抽 SPS/PPS → 更新本地布局尺寸"的表述会误导实现方向。
- 帧元数据标志位（`ptsAndFlags`，u64 小端）：

| 位 | 含义 |
| --- | --- |
| `1<<63` | `CONFIG`：payload 是编解码器配置数据（H.264 的 SPS+PPS），驱动解码器 configure |
| `1<<62` | `KEY_FRAME`：关键帧（IDR） |
| `1<<61` | **预留**：方向标志（MVP 不启用；方向信息由流头/新 CONFIG 带来的宽高变化隐含表达） |
| 其余 | 普通 PTS（微秒） |

- **CONFIG 帧 payload 的构造与消费（冻结）**：手机端从 `INFO_OUTPUT_FORMAT_CHANGED` 的 `csd-0`/`csd-1` 拼接产出；宿主端**整体作为 `csd-0` 注入**，失败再回退按 `00 00 00 01` 起始码切分。
- CONFIG 帧**永不吞掉**：即使已有配置，收到 CONFIG 也必须重新解析并 re-configure（旋转后重发 CONFIG 复用此路径）。

### 4.5 参数默认值

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `max_size` | **由宿主计算下发** | `align8(min(手机屏幕长边, 宿主屏幕长边))`。宿主也是安卓手机、两边分辨率相近，故多数情况下等于两边原生长边 → 宿主端零放大、画面最清晰。性能弱者由宿主下调 |
| `video_bit_rate` | **8 Mbps** | 由 6 Mbps 上调：既然多数情况不做下采样（如 1080×2400 原生编码），6 Mbps 对高动态画面偏紧。USB2 实测约 30MB/s，带宽余量极大，可放心给到 8~12 Mbps |
| `max_fps` | 30 | 映射到 `KEY_MAX_FPS_TO_ENCODER`（float） |
| **I 帧间隔** | **3 s** | ★ 初版取 10s 的前提是"从不丢帧"。引入 4.7 丢帧策略后，P 帧被丢会造成花屏，**花屏时长 = I 帧间隔**；缩短到 3s 以限制最坏观感。带宽代价可忽略 |
| 协议版本 | 1 | `CNXN.arg0` |

### 4.6 超时、缓冲与上限总表 ★（初版数值分散在各处，此处集中冻结）

| 场景 | 参数 | 值 | 理由 |
| --- | --- | --- | --- |
| AOA 控制传输（51/52/53） | `controlTransfer` timeout | **1000 ms（严禁用 0）** | 0 = 无限等待，会挂死线程 |
| 重枚举轮询 | 间隔 × 次数 | 200 ms × 25 = 5 s | 超时转 `onError` |
| 端点 bulk 读 | `bulkTransfer` timeout | 200 ms | 短超时便于循环检查退出标志 |
| 端点 bulk 写 | `bulkTransfer` timeout | 5000 ms | 大帧不拆包断流 |
| 手机侧 fd 写 | 看门狗线程 | 5000 ms → `close()` 打断 | fd 无法直接设超时 |
| OPEN 应答等待 | 等待上限 | 5000 ms | 超时转 `onError` |
| 读 chunk（宿主） | 单次 `bulkTransfer` 长度 | 16384 B | ≥ `maxPacketSize` 整数倍 |
| 流读缓冲 | 每流队列深度 | **4 帧** | 背压上界 |
| 报文 `data_length` | 上限 | 8 MiB | 防伪造头 OOM |
| 帧 `size` | 上限 | 8 MiB | 同上 |
| 单次 `readFully` 请求 | 上限 | 64 KiB | 同上 |

### 4.7 背压与丢帧策略 ★（初版缺失）

**问题**：没有上界时，任何一次瞬时卡顿都会把延迟**永久**推高（队列越积越多），最终"5 分钟压测延迟不增长"无法达标。

**策略**（两端对称）：
- 每流一条**有界队列，深度 4 帧**。
- 队满时：**丢弃队内最旧的、非关键帧**的那一帧；关键的 `CONFIG`/`KEY_FRAME` 优先保留。
- 丢帧计数上报（日志 + UI），便于判断链路是否健康。
- 解码器 `dequeueInputBuffer` 超时不忙等。
- 效果：延迟有硬上界（≈ 4 帧 ≈ 130ms@30fps），不会随时间增长。

**代价**：丢弃 P 帧会让后续引用它的帧短暂花屏，花屏最长时间 = I 帧间隔 → 因此 4.5 把 I 帧间隔从 10s 收紧到 **3s**。这两项是一组联动决定，不能只改一个。

### 4.8 性能优化（阶段 1/3/4 落实）

| 优化 | 做法 |
| --- | --- |
| 跳过停等 | 不逐包收发 `OKAY`（noWait） |
| 合并写 | 帧元数据(12B) + 帧数据合并为**一次** `write` |
| 大缓冲 | 读 chunk 16 KB / 队列 4 帧 / 写超时 5 s |
| 带偏移写 | `ByteChannel.write(src, off, len)` 重载，免合并前拷贝 |
| 单写线程 | 所有出站报文经同一写队列串行化，避免交错写坏报文 |
| 持续送帧 | `KEY_REPEAT_PREVIOUS_FRAME_AFTER`=100ms，静止画面链路不空转 |

| 风险 | 根因 | 对策 | 归属 |
| --- | --- | --- | --- |
| **两端实现不一致** | 初版未定义 `WRTE` 的 arg/payload 语义 | 冻结 4.2 命令语义表，`Options` 两端共用一份实现 | 4.2 / 1.7 |

## 7. 联调提速：离线回放 ★（初版无，强烈建议纳入）

真机联调最痛的是"画面没出来，但不知道坏在哪一段"。加一个回放通道可把问题域切两半：

1. 手机端 `StreamDump` 把发出的 `WRTE` 原始字节落盘成 `.uav`（或只是"流头 + 全部帧"的简化格式，配合 `Hex.dump` 可读）。
2. 宿主端加 `FileByteChannel`，把同一个 `.uav` 喂进 `HostSession`，**跳过整个 USB 与握手**。
3. 判定：
   - 回放能出画面 ⇒ USB 握手 / 协议 / 传输已通，剩余问题全在实时链路（超时、背压、线程）。
   - 回放也出不了画面 ⇒ 用第 1 节单测直接查协议解析与解码器配置，完全不占真机。
4. 副产品：这段录制数据同时也是 `:protocol` 单测的**回归夹具**——协议一改，回放用例自动告警。

### 10.2 实现过程中发现并修正的点（相对计划文本的偏差，均已落地）

| # | 计划原文 | 实现时的修正 | 原因 |
| --- | --- | --- | --- |
| 1 | 4.6「单次 `readFully` 请求上限 64 KiB」 | `readFully` **内部自动分块**，每次向底层请求 ≤64 KiB；`readFully` 本身可一次读完 8 MiB 大帧 | 照字面实现会导致 8 MiB 的帧根本读不进来 |
| 2 | 1.9「每流累计字节/帧数/丢帧数」 | **`frames()` 只算媒体帧**，CONFIG 单独计数 `configFrames()`；`bytes()` 为链路口径（含 CONFIG） | 把 CONFIG 算作帧会让 4.10 的帧率压测系统性偏大，旋转重发 CONFIG 时更明显 |
| 3 | 2.2 权限广播取 `EXTRA_PERMISSION_GRANTED` | **改为收到广播后用 `usbManager.hasPermission(device)` 复核** | 计划要求 PendingIntent 带 `FLAG_IMMUTABLE`（否则 API 31+ 直接崩），而 IMMUTABLE 的 PendingIntent 在系统 `send()` 填充 extras 时会被拒绝填充，该 extra 可能取不到 |
| 4 | Annex-B 切分写在宿主模块 | 下沉为 `:protocol` 的 `AnnexB` | 纯字节运算放 Android 模块里无法 JVM 单测，只能真机试 |
| 5 | `SEND_STRING` 编码写在宿主模块 | 下沉为 `AccessoryIdentity.encodeSendString` | 同上：编码方式这条红线必须能被单测钉死（**实测正确编码是 UTF-8，见 10.4**） |
| 6 | 目录树把 `Scale.kt` 放在 `:app-accessory` | 放到 `:protocol` | 宿主算 `max_size`、手机端做缩放，**两端都要用**；共用一份实现才能保证口径一致 |
| 7 | 3.4 只说「先 registerCallback」 | 冻结完整顺序：`startForeground(mediaProjection)` → `getMediaProjection()` → `registerCallback()` → `createVirtualDisplay()` | Android 14+ 要求**先以前台服务类型启动**才允许 `getMediaProjection()`，顺序写反直接抛异常 |
| 8 | — | `createVirtualDisplay` 返回值显式判空 | API 34 起该方法标注 `@Nullable`，不判空会 NPE |
| 9 | 4.2 只说「手机回 OKAY」 | 冻结为**收到 OPEN 立即回 OKAY**，采集授权被拒/编码失败改发 `CLSE(原因串)` | 录屏授权是异步的（用户要点系统弹窗），等它就绪会先撞上宿主 5s 应答超时 |

**新增（计划未列但价值高）**：`:protocol` 的 `SessionFlowTest` —— 两端各跑一个真实 `Connection`，
经内存管道完整走一遍 `CNXN → CNXN → OPEN → OKAY → 流头 → CONFIG → 普通帧`。
**通过 ⇒** 命令语义表 / 流分流 / 帧编码 / Options 协商 / CONFIG 传递全部自洽，真机联调只剩 USB 层与编解码层变量；
**失败 ⇒** 一定是冻结清单被改坏，**不必上真机**。

### 本轮真机暴露并修复的 6 个缺陷

| # | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | 手机 `dumpsys` 里配件身份变成 `manufacturer=U model=u version=1`（只剩首字符）→ 系统不派发 → `openAccessory` 无权限 → 宿主永远等不到 CNXN | **计划的红线写错了**：`SEND_STRING` 要的是 **UTF-8 + 单个 `\0`**，不是 UTF-16LE。AOSP `UsbDeviceManager.getAccessoryStrings()` 按 `\u0000` 切分字节串 | 改为 UTF-8；单测断言"除结尾外不得出现 NUL 字节" |
| 2 | `StreamHeader(乱码 8x466)` —— 解码器被**静默配错** | 上一次会话残留在 USB FIFO 的帧数据被"首个 WRTE 即流头"的约定误解析 | 宿主 claim 后 `drainStaleInput()`；`StreamHeader.decode` 严格校验（可打印 ASCII + 尺寸 16..8192）；`Connection` 把非法首个 payload 当杂散丢弃并继续等真流头 |
| 3 | 手机端在新会话上**先发帧、后发流头** | 复用编码器时（配件重新接入），编码器在 `resendStartup()` 之前就已在推帧 | 手机端用 `headerSent` 把帧**关在流头后面**（源头堵住，而不是靠宿主的杂散丢弃兜底） |
| 4 | 宿主重枚举后**只发 DETACHED、不发 ATTACHED** ⇒ "插线即投"完全失效 | 该宿主设备的 USB host 栈行为 | 前台轮询兜底（2s/次，同设备最多重试 3 次）；候选设备按"含 BULK IN/OUT 端点对"筛选，避免误选内建面板的 HID 触摸控制器 |
| 5 | 配件重新接入后宿主收到「等待 CNXN 超时」 | 手机端仍握着**已失效的旧 fd** | `onNewIntent` 触发 forceRestart 重建传输会话；因 `MediaProjection` 令牌只允许 `createVirtualDisplay` 一次，**保留投影与编码器**，只重发流头 + 缓存的 CONFIG |
| 6 | 回放时 `dropped=4310/4316`（连关键帧一起丢），解码器随即报错 | 配速放错了层：读线程是**磁盘速度**灌进深度 4 的队列，消费端再慢也没用 | 配速移到 **`FileByteChannel`（字节进入管线的地方）**，按帧 PTS 节流；回放实测 `dropped=1` |

另有两处"预期之内、但值得记下"的观察：

- **静态画面下帧率约 10 fps**，不是 30 —— 这是 `KEY_REPEAT_PREVIOUS_FRAME_AFTER=100ms` 的设计效果
  （静止时兜底送帧、不让链路空转），**不是性能问题**。要测帧率必须让画面动起来。
- **OTG 链路偶发不稳**：出现过两次"等待重枚举超时"，**重插拔即恢复**。
  这印证了第 6 节准备清单里"部分 OTG 线只供电不传数据 / 需实测"的提醒。

## 10.5 MVP 收尾（阶段 5）

### 5.2 release 调试门控：把"能改链路行为 / 会写盘 / 会刷屏"的入口集中关掉

**为什么必须做**：调试期加的入口如果留在发布包里，会有两个真实后果——
宿主能被 `--es replay_path` 读**任意本地文件**，手机端会**持续写出 28MB+ 的抓流**
（实测 110 秒 ≈ 28 MB）却对用户完全不可见。

做法：两端各加一个 `DebugTools` 对象集中判断（而不是把 `if (BuildConfig.DEBUG)`
散落到十几处，那样漏关一个都看不出来）。

| 端 | 入口 | release 行为 |
| --- | --- | --- |
| 宿主 | `--es replay_path`（回放抓流） | 忽略 |
| 宿主 | `--ez scan` / `--ez force_handshake`（adb 驱动） | 忽略 |
| 宿主 | 界面 **Replay** 按钮 | `View.GONE`（不显示） |
| 宿主 | `FileByteChannel` 回放通道 | 不构造（`startReplay` 双保险拦截） |
| 宿主 | 周期 `STATS` 日志（每 5 秒） | 关闭 |
| 配件 | 抓流落盘 `DumpByteChannel` | 不构造，直接 `FdByteChannel -> Transport` |

**刻意保留的三项**（它们是**功能**而非调试入口，release 必须有）：

- 界面 **Scan / Retry** —— 手机被别的宿主 App 占用时的自救手段
- 界面 **Force handshake** —— 同上（强制改写配件身份）
- 前台轮询兜底 —— 绕开"部分宿主只发 DETACHED 不发 ATTACHED"的设备缺陷

**⚠️ 实现时踩到的坑（值得记）**：`BuildConfig.DEBUG` 不能用 `const val` 接。

```kotlin
// 编译期直接报错：Const 'val' initializer must be a constant value
const val ENABLED: Boolean = BuildConfig.DEBUG
```

原因是 AGP 生成的不是字面量，而是 `Boolean.parseBoolean("true")`：

```java
public static final boolean DEBUG = Boolean.parseBoolean("true");
```

Kotlin 只承认字面量形式的 Java `static final` 常量，所以必须写成 `val`。
运行时语义完全相同，但**也意味着 R8 之外没有编译期死代码消除** ——
若要让这些分支真正从 release 包里**被删掉**（而不只是"运行时走不到"），
需要给 release 打开 `isMinifyEnabled`。**当前未开**（依赖只有 `core-ktx` + `:protocol`，
无反射/序列化，开启风险低，但属独立改动，留作后续决定）。

## 10.6 端到端延迟实测（2026-10-16）

### 为什么放弃了"屏显时钟 + 摄像头"

计划里原本设想的旁证手段（手机屏显毫秒时钟 + 摄像头同框）有硬伤：靠人眼读数、
分辨率受快门与屏幕刷新率限制，**量不出 p95/p99**，而投屏体感恰恰由尾部决定。

改为**在链路内直接测**。核心难点是**两端时钟起点不同**（单调时钟各自从开机起算），
直接相减只能得到"延迟 + 未知偏移"。

### 方法

1. **时钟标定**：`CNXN` 的 payload 由 8B 扩到 16B，各带本端 `System.nanoTime()`。
   宿主发 CNXN 记 `t0`、收应答记 `t3`、读手机带回的 `tr`，按 NTP 思路得

   ```
   offset = tr − (t0 + rtt/2)        含义：本机 = 对端 − offset
   ```

   实现在 `:protocol` 的 `ClockSync`（纯逻辑，7 项单测）；不确定度为 `rtt/2`。

2. **逐帧采样**：手机侧帧的 PTS **就是采集时刻** —— MediaCodec 在 surface 输入模式下
   把帧进入编码器的时间写进 `presentationTimeUs`，时基同 `System.nanoTime()`。
   宿主在 `releaseOutputBuffer` **之前**记 `now`，于是

   ```
   延迟 = now − (pts × 1000 − offset)
   ```

3. **统计**：滚动窗口 300 帧，输出 avg / p50 / p95 / p99 / max
   （`LatencyStats`，11 项单测）。

### 口径（必须先看这条）

- 测的是「**手机采集 → 宿主提交给 SurfaceFlinger 合成**」。
- **不含最后的上屏延迟** —— SurfaceFlinger 还要等下一个 vsync 才点亮像素
  （60Hz 下约 8~16ms）。**真实观感延迟 ≈ 表内数值 + 一个 vsync**。
- 标定不确定度 = `rtt/2`，本机实测 rtt 6~24ms → **±3~12ms**。
- **回放模式不测**：没有对端时钟可标定，此行显示 `delay=(回放，非实时链路)`。

### 为什么要分「全量」与「fresh」两个口径

静止画面下编码器会按 `repeat-previous-frame-after = 100ms` **反复送出上一帧**
（这是刻意设计，让链路不空转），而这些重复帧的 PTS 停在旧值上，会把读数系统性拉高：

| 场景 | 全量 p50 | fresh p50 |
| --- | --- | --- |
| 静止（几乎全是重复帧） | 140.5 ms | 143.2 ms（**仅 5 个样本**，无统计意义） |
| 运动（连续新内容） | 66.9 ms | **63.6 ms** |

**观感只由"内容真的变了"的帧决定** —— 所以 `fresh`（PTS 间隔 < 50ms 的连续帧）
才是有意义的口径；全量那份留作对照与定位。

### 实测数据

宿主 BOE P40UCH / Android 14，配件 HONOR MAA-AN10 / Android 16；
编码输出 872×1920 @ 8 Mbps；用 `input swipe` 持续滚动制造连续新内容，采样 60 秒。

| 口径 | avg | **p50** | **p95** | p99 | max | n |
| --- | --- | --- | --- | --- | --- | --- |
| **fresh（新内容帧）** | **68.9** | **63.6** | **140.2** | 158.9 | 174.3 | 300 |
| 全量（含重复帧） | 104.9 | 66.9 | 166.9 | 424.3 | 567.8 | 300 |

单位 ms。**两次独立测量结果一致**（fresh p50 分别为 56.5 / 63.6 ms），
差异主要来自标定不确定度（±3ms vs ±12ms）。

### 结论

- ✅ **4.10 的「≤150ms」在 p95 口径下达标**（140.2ms）。
- ⚠️ **p99 与 max 略超**（158.9 / 174.3ms）—— 约 1% 的帧会摸到 160~175ms。
- ✅ 中位延迟 **63.6ms**，远优于目标。
- ⚠️ 上述数字**不含**最后 1 个 vsync（约 8~16ms）。**加上界**后
  p95 ≈ 148~156ms —— **正好卡在 150ms 线上**，不能宣称"轻松达标"。
- 全量口径里的 424 / 568ms 尖峰来自**重复帧的旧 PTS**，不是真实观感（见上文口径说明）。

### ⚠️ 本轮修掉的一个严重缺陷：`LatencyStats` 的并发读会崩

最初为了不给每帧的解码路径加锁，`snapshot()` 直接读内部的 `ArrayDeque`，
注释还写着"最坏只是读到几帧偏差"。**这个假设是错的** —— `ArrayDeque` 的并发读
不是"读到旧值"，而是可能读到**未初始化的 `null` 槽位**，于是 `sorted()` 在
`Long.compareTo(null)` 上直接 NPE，把宿主 App 打崩：

```
FATAL EXCEPTION: main
java.lang.NullPointerException: Attempt to read from field 'long java.lang.Long.value'
on a null object reference in method 'int java.lang.Long.compareTo(java.lang.Long)'
    at java.lang.Long.compareTo(Long.java:1660)
    at java.util.ComparableTimSort.countRunAndMakeAscending(ComparableTimSort.java:320)
    at kotlin.collections.CollectionsKt___CollectionsKt.sorted(_Collections.kt:1042)
    at com.uav.protocol.LatencyStats.snapshot(LatencyStats.kt:107)
    at com.uav.host.session.HostSession.latencyLine(HostSession.kt:446)
    at com.uav.host.session.HostSession.stats(HostSession.kt:453)
    at com.uav.host.HostActivity$statsTicker$1.run(HostActivity.kt:75)
```

**触发条件是常态而非偶发**：写是**解码线程每帧一次**，读是 **UI 线程每秒一次**。

修法：
1. **所有**内部状态访问进锁；
2. 排序这类 O(n log n) 的操作**先复制、在锁外做**，把持锁时间压到最短；
3. `snapshot` **一次加锁取齐**「样本 + 求和 + 异常计数」，避免分次读取自相矛盾。

补了两个并发单测：一个复现这个崩溃（修复前偶发失败），一个查内部一致性。

## 10.7 屏幕旋转（P0「旋转三件套」，2026-10-16）

### 硬约束决定了整个改法

`MediaCodec` 的尺寸在 `configure` 时固定、**不可修改**，所以旋转必须**重建编码器**；
但 `MediaProjection` 令牌**只允许 `createVirtualDisplay` 一次**，虚拟屏**不能重建**
（重建就得重新弹一次录屏授权，对用户是明显倒退）。

于是把两者的生命周期**拆开**：

| 对象 | 生命周期 |
| --- | --- |
| `VirtualDisplay` | 全程只创建一次，旋转时 `resize()` + `setSurface()` **复用** |
| `MediaCodec` / input surface | 可随旋转反复重建 |

### 新尺寸怎么告诉宿主（不动 CONFIG 的语义）

宿主 configure 解码器用的是**流头**的宽高，所以旋转后必须让它知道新尺寸。

方案：**重发 12B 流头**。判据是**载荷长度**，而不是"内容像不像流头"：

- 帧的 payload 长度 = `12 + size`（`size ≥ 1`）→ **≥ 13 字节**
- 所以**恰好 12 字节的 payload 只可能是流头**，不存在歧义

为什么不让 CONFIG 帧顺便带尺寸：CONFIG 的 payload 要**整体作为 `csd-0`**
注入解码器，在它前面垫字节会破坏这个前提。

实现落在 `:protocol` 的 `Connection.dispatchWrite`：12B payload 且与当前不同 →
更新 `headers`、计入 `stats.sizeChanges`、回调 `sink.onHeader`。
**尺寸相同时不重复回调** —— 否则宿主的解码器会被无谓重建一次，画面闪一下。

### 配套：队列里的旧尺寸帧必须丢掉

`FrameQueue.onHeader` 在尺寸变更时**清空队列**。否则旧尺寸的帧会被新解码器按新 SPS
解码 —— 解错（花屏）或直接报错。不会因此丢关键帧：编码器重建后第一帧必是 IDR。

### 手机端时序

`DisplayListener` 回调**只置标志**（计划 4.2 的要求），重建在编码器自己的线程做：

```
停旧编码器 → 建新编码器 → 虚拟屏 resize + 换面 → 启动新输出线程（首件事是重发流头）
```

### 实测（真机）

| 环节 | 日志 |
| --- | --- |
| 手机检测到旋转 | `旋转：源 1224x2700 -> 2700x1224，编码 872x1920 -> 1920x872` |
| 重建完成 | `旋转完成：编码 1920x872，已重发流头等待宿主重配解码器` |
| 新 CONFIG 产出 | `CONFIG 帧产出：2 段拼接，共 32 字节（1920x872）` |
| 确实采到画面 | `编码帧 #300（1920x872, 520B, key=false）` |
| 宿主收到新尺寸 | `stream[video] 流头更新（尺寸变更）: 872x1920 -> 1920x872` |
| 解码器重配 | `decoder configured 1920x872 (csd-0 = 32B 整体注入)` |
| 持续运行 | `video=avc1 1920x872 frames=535 config=2 bytes=662386` |

### ⚠️ 踩到的坑：旧 Surface 的释放时机

第一版在 `stopEncoderOnly()` 里直接 `release()` 旧的 input surface，结果：
**CONFIG 帧出来了，但一个视频帧都出不来。**

原因是此刻**虚拟屏还持有那个面**，提前释放会让它的输出管线失效。而 CONFIG 是
编码器 `start()` 时自己产生的（不需要任何输入），所以它出现**并不代表**采到了画面 ——
这个"半成功"现象很容易把人往错误方向引（一度怀疑是 USB 或协议问题）。

修法：
1. `stopEncoderOnly()` 改为**返回**旧 surface，由调用方决定何时释放；
2. 换面顺序改成 **`setSurface(null)` → `resize()` → `setSurface(new)`** ——
   先断开、再改尺寸、最后接入，全程没有"屏尺寸与面尺寸不匹配"的窗口；
3. 这些都做完**之后**才 `release()` 旧面。

另外给 `emitFrame` 加了低频日志（首帧 + 每 300 帧）：**这是判断"旋转后到底有没有帧"
的唯一直接证据**，别再靠猜。

### 使用前提

- 手机需要**开启自动旋转**（或由应用 / 系统切换方向）；
- `ProjectionActivity` 已声明 `configChanges="orientation|screenSize|screenLayout|keyboardHidden|density"`，
  旋转**不会重建 Activity、不会重新弹录屏授权** —— 这点很关键。

### 复现

```bash
# 关掉自动旋转后强制切横屏（等价于物理旋转）
adb -s <acc> shell settings put system accelerometer_rotation 0
adb -s <acc> shell settings put system user_rotation 1

adb -s <host> logcat -s UAV-Host  | grep -E "流头更新|decoder configured"
adb -s <acc>  logcat -s UAV-Video | grep -E "旋转|CONFIG|编码帧"
```

宿主 `STATS` 里的 `sizeChanges` 就是旋转次数；不动它说明手机端根本没上报旋转。

### 顺带：界面文案统一为中文

旋转落地后，界面上那句 `rotation is not supported in MVP` 直接变成了错误信息，
于是把文案一起收拾了：**默认用简体中文**（`values/`），英文放 `values-en/`，
系统按语言自动选择。

为什么默认是中文而不是英文：文档与**运行时状态文本**（`HostActivity.onStatus`、
`AccessoryStatus.set` 传进去的那些字符串）本来就是中文，只有布局里的静态文案曾是英文 ——
界面上长期是「中文状态 + 英文按钮」的混搭。默认中文顺便消除了这个不一致，
也让中文设备无需任何额外配置。

## 10.8 自动重连（P0 最后一项，2026-10-16）

目标：**拔插 / 链路抖动之后不需要用户做任何事**，画面自己回来。

### 两端各自做了什么

| 端 | 改动 | 为什么 |
| --- | --- | --- |
| 宿主 | `onError` 时清掉会话，让前台轮询重新接管；连续失败时**指数退避**（2s→4s→8s→16s→30s 封顶）；断链时**重置**「同设备最大尝试次数」 | 原来链路错误后 `session` 不复位，而轮询的接管条件是 `session == null` —— 于是**再也不会自动重试**；且尝试配额被几次偶发抖动耗光后就永久放弃 |
| 手机 | 链路断开**不再 `stopSelf()`**，改为进入重连循环；重建时**保留投影与编码器** | 原来 `onClosed` 直接自杀并释放投影 —— 投影令牌是一次性的，释放就意味着**下次必须重新点一次录屏授权**，那自动重连就失去意义了 |

### ★ 关键发现：真正的拦路虎是一个 **fd 泄漏**，不是重连逻辑

自动重连写完之后真机仍连不回来：宿主一直刷 `等待重枚举超时`，手机端
`openAccessory` 连试 6 次全失败（`无权限或配件已被占用`）。对照实验把根因钉住了：

| 条件 | 结果 |
| --- | --- |
| 手机 App 运行、持着上一个会话的 fd | 怎么握手都不切配件模式（连 `svc usb setFunctions` 强制重枚举也没用） |
| `force-stop` 掉手机 App（释放 fd） | **下一次握手立刻成功**，链路完整跑通 |

根因在 `:protocol` 的 `Connection`：

```kotlin
private fun fail(cause: Throwable) {
    if (closing.getAndSet(true)) return
    ...
    // ← 旧代码到这里就结束了：没有 transport.close()
}
override fun close() {
    if (closing.getAndSet(true)) return   // ← closing 已被 fail() 置 true，直接 return
    ...
    transport.close()
}
```

`fail()` 把 `closing` 置为 `true` 却**没有关闭底层通道**；而 `closing` 已为 true
又让之后任何 `close()` 调用**立即返回** —— 于是 fd **永远关不掉**。
`notifyClosed()`（EOF 路径）有同样的毛病。

**在 Android 上后果极重**：底层通道就是 `/dev/usb_accessory`，而它是**独占打开**的。
漏掉的 fd 会让手机端**再也切不进配件模式**，宿主侧表现为无限「等待重枚举超时」。

> ⚠️ **这条推翻了本项目此前的一条经验**：我们曾把
> 「等待重枚举超时 → 重插拔即恢复」归因于 *OTG 链路偶发不稳*。
> 实际原因是**自己的 fd 泄漏**，拔插之所以"有效"，只是因为它顺带杀掉了持 fd 的进程。
> （同理，"`am force-stop` 之后连不上"也有一部分是这个原因。）

修复分两层：

1. **`:protocol`**：`fail()` 与 `notifyClosed()` 都补上 `transport.close()`（抽成
   `closeTransportQuietly()`，`close()` 一并复用）。3 项回归单测钉住
   （出错关通道 / EOF 关通道 / 出错后再 `close` 也不漏）。
2. **`:app-accessory`**：把"只把引用置 null"改成真正 `releaseTransport()`
   （会话 + fd + 抓流一起关，保留投影与编码器）；
   并新增**空闲看门狗** —— 会话起来后 12s 内宿主一条报文都没有，
   就判定为**假配件**并主动释放，**只释放不重连**（硬重连只会再次拿到同一个假配件、
   把互锁继续维持下去）。

### 真机实测（两轮，均零人工干预）

```
16:09:46.873 宿主  detach（触发断链）
16:09:46.893 手机  accessory-fd(161) closing (rx=137 tx=152480)   ← fd 真正被关闭
16:09:46.894 手机  传输层已释放（链路错误: read failed: EIO）
16:09:47.205 宿主  attached: id=2012 PID=0x107d（普通模式）→ 自动重握手
16:09:47.819 宿主  re-enumerated as accessory: 18D1:2D01 deviceId=2013
16:09:47.824 宿主  link ready: aoaVersion=2
16:09:47.955 手机  new accessory: usbscreen/UAV
16:09:48.073 手机  OPEN: max_size=1920 bitrate=8000000 → 已回 OKAY
16:09:48.074 手机  ★ 复用既有编码器，已重发流头与 CONFIG(32B)
16:09:53.666 宿主  首帧已输出 872x1920
```

- **恢复耗时约 1.5 秒**，全程不碰任何按钮、不重启 App；
- **编码器被复用** ⇒ **没有重新弹录屏授权**（这正是自动重连的意义）；
- 第二轮同样自动恢复（`re-enumerated as accessory` → `link ready` → `首帧已输出`），
  最终 `frames` 持续增长、`dropped=0`；
- 顺带一个副产品：本轮 `CNXN` 往返只有 **3ms**，标定不确定度 **±1ms**
  （对比 10.6 里一度出现的 `rtt=237ms / ±118ms`）—— 标定质量取决于
  `CNXN` 交换时链路是否干净，读数本身要连同 `skew` 一起看。

### fd 泄漏回归检查（真机上随时可复跑，建议改动连接层后都跑一遍）

因为这次的根因是"fd 关不掉"，所以最有说服力的验证不是"画面回来了"，而是
**直接盯着 fd 数**。debug 包可用 `run-as` 读 App 自己的 `/proc/<pid>/fd`：

```bash
ACC=<acc>
# 当前 App 持有的配件 fd 数（正常恒为 1：唯一那条活动会话）
adb -s $ACC shell "pidof com.uav.accessory"          # 先拿 pid
adb -s $ACC shell "P=\$(pidof com.uav.accessory); \
  run-as com.uav.accessory ls -l /proc/\$P/fd | grep -c usb_accessory"
```

连续 4 轮「断链 → 自动恢复」的密集采样结果：

```
触发前    fd=1        ← 旧会话
t+2s      fd=0        ← ★ 旧 fd 被真正释放（修复生效的直接证据）
t+3s      fd=1        ← 新会话已建立
t+4~7s    fd=1        ← 稳定，从不累积
```

- fd 数**始终 ≤ 1**，多轮断链**无累积** —— 这正是本条修复要保证的性质；
- 整个过程中 App **pid 不变**（进程没死、投影令牌没丢）⇒ 不会重新弹录屏授权；
- 宿主侧每轮都出现 `re-enumerated as accessory`（deviceId 递增）+ `首帧已输出`。

> ⚠️ 采样时不要只取"断开后 3s"这一个点：恢复只要 ~1.5s，
> 那时看到的 `fd=1` 已经是**新**会话的 fd，容易误判成"没释放"。
> 要看到 `0` 这个中间态，得在断链后 **1~2s 内密集采样**。

### 复现命令

```bash

# 观察自动恢复

```

> 排查手机端**必须先按 PID 抓**：`adb logcat -d --pid=$(adb shell pidof com.uav.accessory)`。
> 厂商 ROM 的噪音很大，按 TAG 过滤时缓冲常常已经把我们的行挤掉了（本轮就踩到过，
> 一度误以为"手机端一条日志都没有"）。

## 10.9 AOA HID 触摸注入（P1 输入通道 · 探针阶段，2026-10-16）

> 方向是 **宿主 → 手机**：把宿主的触摸反向送进手机，最终让手机把宿主当成一块**外接触摸屏**。
> 本轮只做到「**探针**」：确认这条路在这台机器上通不通，以及一个**会直接影响重连设计**的性质。
> **手机端零改动** —— HID 全程在手机内核/框架里处理（与 51/52/53 握手一样），所以这是宿主端单独可做的功能。

### 机制（AOA 2.0 规范 + 内核 `f_accessory.c`）

内核把配件给的描述符交给 HID 核心（`hid_parse_report()`）、把每条报告交给
`hid_report_raw_event(..., HID_INPUT_REPORT, ...)` —— 于是系统里**就"多出一个 USB 触摸屏"**，
与插一个真实外接触摸屏走的是**同一条路径**。请求语义：

| 请求 | `value` | `index` | `data` |
| --- | --- | --- | --- |
| 54 `REGISTER_HID` | 自分配的 HID id | **描述符总长度** | 无 |
| 55 `UNREGISTER_HID` | id | 0 | 无 |
| 56 `SET_HID_REPORT_DESC` | id | **该块在描述符里的偏移** | 描述符分块（**必须按偏移顺序**发） |
| 57 `SEND_HID_EVENT` | id | 0 | **一条完整的 input report**（无封装） |

★ 全部走 **EP0 控制传输**：不新增 USB 接口，**不占视频的 bulk 端点**（`0x81/0x01` 完全不受影响）。
★ **单向**：内核 `acc_hid_raw_request` 是空实现 → 拿不到输出报告，别指望力反馈 / 键盘 LED。

### 实现

- `:protocol/AoaHid.kt` —— 请求常量 + 描述符分块（纯逻辑，可 JVM 单测）。
- `:protocol/HidTouchPanel.kt` —— **单点绝对坐标触摸屏**的描述符与报告编码。
  ⚠️ 两者必须严格对应（报告的字段位宽完全由描述符决定），所以放同一个文件，长度由单测钉死
  （描述符 **76B**、报告 **7B**）。
- `app-host/.../usb/HidInjector.kt` —— `controlTransfer` 执行器；EP0 单次长度不猜 64，
  读设备描述符的 `bMaxPacketSize0`（读不到才退回 64）。
- 坐标空间取 **CNXN 里手机上报的屏幕尺寸**（`HostSession.peerWidth/peerHeight`），
  **不是**编码后的视频尺寸（`max_size` 是缩放过的，拿它会让落点整体偏移）。

## 10.10 Surface 生命周期：切后台会崩、把会话停掉会死锁（2026-10-16）

> 起因是一个真机崩溃，触发动作平淡到不能再平淡：**在宿主上按 Home / 打开最近任务**。
>
> ```
> FATAL EXCEPTION: uav-decode
> android.media.MediaCodec$CodecException: rendering to non-initialized(obsolete) surface
>   at com.uav.host.video.VideoDecoder.drainOutput(VideoDecoder.kt:181)
>   at com.uav.host.video.VideoDecoder.feed(VideoDecoder.kt:159)
>   at com.uav.host.session.HostSession.consumerLoop(HostSession.kt:287)
> ```

### 崩溃的时间线（真机日志，因果链完整）

```
16:47:47.711  WindowManager: Task 347 (com.uav.host) → TO_BACK   ← 宿主被切到后台
16:47:48.398  RecentsController.screenshotTask: taskId=347
16:47:48.509  FATAL EXCEPTION: uav-decode                          ← 111ms 后崩
```

### 根因

`surfaceDestroyed` 只把 `surfaceReady` 置 false，**而 `stopSession()` 原先只在 `onDestroy` 里调**。
`surfaceDestroyed` **先于** `onDestroy`，所以这段窗口里解码线程仍在往**刚失效的 Surface** 上渲；
而 `drainOutput` 里只有 `dequeueOutputBuffer` 有 try/catch、**`releaseOutputBuffer` 没有**
→ 异常穿透 `feed` → `consumerLoop` → `uav-decode` 线程无人接住 → **整进程 FATAL**。

### ★ 第一版修法（Surface 一没就把会话停掉）引出了第二个坑：重连死锁

先在 `surfaceDestroyed` 里加 `stopSession()`。真机只撑过一轮：

| 后台时长 | 结果 |
| --- | --- |
| 8s | ✅ 回前台自动恢复 |
| 60s | ❌ 回前台后无限 `等待手机 CNXN 超时`，永远黑屏 |

因为链路一断，手机端就释放配件 fd；**超过它 12s 的空闲看门狗后就不再重开**（本意是躲开"假配件"），
而手机此刻**本来就在配件模式** —— `START_ACCESSORY` 不会重新枚举、系统也不会重新派发 attach
→ **没人再打开那个 fd**。实测到的死锁态：`手机 fd=0 但 config=accessory,adb`，
宿主侧 `link ready` 反复出现却始终等不到 CNXN。

> 这也解释了为什么"拔插即恢复"：只有**真正重枚举**才会重新派发 attach。
> 另外这一版还让**每次切后台都触发一次 USB 重枚举**，纯属折腾手机。

### 最终方案：只停渲染，保持链路

1. `surfaceDestroyed` → `HostSession.suspendRendering()`：**不动链路**，只释放解码器。
2. `surfaceCreated` → `HostSession.resumeRendering()`：用**缓存的 CONFIG** 重建解码器。
   - MediaCodec 的 output surface 在 `configure` 时固定、**无法改绑**，"换 Surface"只能新建解码器，
     而它的 csd 只能来自同一份 CONFIG → `HostSession` 记住 `lastConfig` / `lastConfigSize`。
   - 重建放在**消费线程**做（一个 `pendingRebuild` 标志），不在 `surfaceCreated` 回调里做：
     既保证"重建 → 喂帧"的顺序，也避免与 `handleConfigFrame` 并发 configure。
   - 重建后新解码器没有历史参考帧，画面最多到下一个 I 帧（3s）才干净 —— 已知且可接受。
3. `VideoDecoder` 最内层兜底：`releaseOutputBuffer` 包 try/catch，命中即置 `surfaceLost` 并停止渲染
   —— 任何 Surface 竞态都退化成"画面停住 + 一行日志"，**而不是整进程崩溃**。
4. `handleConfigFrame` 在挂起期间只**缓存** CONFIG、不报错（原先会 `fail` → 又走向停会话）。
5. 前台轮询加 `surfaceReady` 门槛：没有 Surface 时不握手（每次握手都会让手机重新枚举）。

### 真机实测（HONOR MAA-AN10 / Android 16）

| 场景 | 结果 |
| --- | --- |
| 切后台 60s（远超 12s 看门狗） | ✅ `等待手机 CNXN 超时` **0 次**；frames 147→824 持续增长；手机配件 fd 恒为 1 |
| 回前台 | ✅ `解码器已在新 Surface 上重建（872x1920，csd=32B）`；frames → 1097 |
| 快速切换 ×3（各 12s） | ✅ 3/3 重建成功，frames 1513→1826→2091 持续增长 |
| USB 重枚举次数 | ✅ **0** —— 后台/前台完全不碰 USB |
| FATAL / 两端 pid | ✅ **0 条**；宿主 pid 17178、手机 pid 18560 全程不变 |
| 留证 | `docs/verify/surface-recreate-recovery.png` |

复现命令：

```bash

sleep 60
adb -s <host> shell am start -n com.uav.host/.HostActivity   # 回前台

### ⚠️ 一个仍需注意的固有边界（本轮暴露，未解决）

「**手机已在配件模式** + **手机端已放弃（fd=0）**」这个组合下，宿主自己救不回来：
只有真正重枚举（拔插 / `svc usb setFunctions`）才会重新派发 attach。

或让宿主能请求手机切回普通模式 —— 留到 P1/P2。

## 10.11 触摸转发：宿主屏幕 → 手机（P1「输入通道」正式落地，2026-10-16）

> 在 10.9 的探针基础上做成**功能**：**直接拿宿主的屏幕当手机的触控屏**。
> 手指在宿主上点/拖，手机上同一个位置就发生同一次触摸 —— 点图标、开关、打字都行。
> **手机端零改动**（HID 全程在手机内核/框架）。

### 分工：算坐标的是纯逻辑，管状态的是控制器

| 模块 | 职责 |
| --- | --- |
| `:protocol/TouchMapper.kt` | **纯逻辑**：画面显示矩形（居中信箱式）、触点 → 手机像素、旋转后坐标空间。**有单测** |
| `:protocol/HidTouchPanel.kt` | 描述符与报告编码（10.9） |
| `app-host/input/HidTouchController.kt` | 状态与**串行发送**：注册时机、空间变化时重注册、断链重发、残留清理 |
| `app-host/HostActivity.kt` | 只做接线：`MotionEvent` → `TouchMapper` → 控制器 |

### 坐标怎么算

1. 画面宽高比被 `max_size` 缩放过（屏幕 1224x2700 → 编码 872x1920），
   而 HID 的逻辑范围声明的是**手机屏幕像素**，所以必须换算；
2. 视图里是**居中信箱式**适配（与 `AspectRatioSurfaceView.onMeasure` 同一套公式）。
   **落在信箱边上的触摸直接忽略** —— 那里没有画面，映射过去等于点到手机上看不见的地方；
3. 显示区用**半开区间**判定（`x ∈ [left, right)`），所以坐标永远不会落到 (width, height)
   这种"屏幕外一格"；
4. ★ **旋转**：手机屏幕物理尺寸只在 `CNXN` 报一次，旋转后不会重报。
   但视频方向必然与手机屏幕方向一致（视频是手机屏幕等比缩放来的），
   所以用**视频方向**推出当前方向的长宽：横屏视频 → 手机屏幕也是横的（长宽互换）。
   空间变了必须**重新注册**（描述符里的 Logical Max 就是空间尺寸，改不了）。

### 什么时候注册

**不在"链路就绪"时注册** —— 那时还不知道手机屏幕尺寸（要等它 `CNXN`）。
改在**拿到视频尺寸**时（解码器 `configure` 成功 → `onVideoSize`），此刻
"手机屏幕尺寸 + 视频方向"两个信息都齐了。旋转时 `onVideoSize` 会再次触发，自动重注册。

### 三条规则（都是踩出来的）

1. **没有 DOWN 的 MOVE/UP 一律不发** —— 否则手机上会出现幽灵触摸（没按下去却响应）。
   手指拖出显示区 → 立刻等价于抬起。
2. ★ **`REGISTER_HID` 挂不住**：HID 注册活在手机的**配件功能**上，
   **只有真正的 USB 重枚举才会把它拆掉**。而实际运行里大量路径**不重枚举**
   （宿主 App 重启后走"已是配件"快路径）→ 每次重连往手机多留一个**幽灵触摸屏**。
   实测：`9 → 10 → 11…`。
   **修法**：新连接建立时、注册之前，先对 `1..12` 逐发 `UNREGISTER_HID` **扫一遍残留**
   （不存在的 id 会失败，属正常、不打警告）。实测 `清理了 2 个残留` → 设备数回到 9。
   > 为什么扫描有效：不重枚举时**是同一个 gadget function**，旧 id 在新连接上仍然存在。
3. ★ **断链时手指还按着 → 重连后必须重发"按下"**（否则手机上手指"卡住"不抬）；
   反过来若断链期间已抬起，就不能再重发（逻辑状态由控制器持有，不是"最后一帧发出去的"）。

## 10.12 多点触摸（P1 输入通道收尾，2026-10-16）

> 在 10.11 的单指转发之上做到**最多 5 指同时**：宿主上双指缩放/多指点击，手机上就是同一次多点手势。
>
> 这一节的**主要价值是"哪些写法是错的"** —— 描述符的形状（字段顺序、`Report Count`、
> `Contact Count` 的语义）错一点，现象都只是"少一个触点"或"按一下就释放"，极难反推。

### ★ 三次尝试，前两次都没多点（记录下来避免重犯）

| 写法 | 现象 |
| --- | --- |
| 单个 Finger collection + 各字段 `Report Count = N` + `Contact Count` 放在**最前**、填**按下的触点数** | 手机只出来 **1 个触点**，且**同一时刻就释放**（`TRACKING_ID 0` 紧跟 `ffffffff`），第二指完全不见 |
| 同上，但 `Contact Count` 改成"帧内记录数" | 未单独测（见下面正确形状的说明，两处都得改） |
| **N 个【独立】Finger collection**（各含一组 Tip Switch / Contact Identifier / X / Y） + `Contact Count` 放在**所有手指之后**、填**帧内记录数** | ✅ **双指同时按下**，两个槽各自独立 tracking id |

诊断上面那两次时还有个"误导性线索"：错误形状会让内核多映射出
`ABS_MT_TOOL_X/ABS_MT_TOOL_Y`（正确形状下没有）—— 可以当成"形状被误解了"的信号。

### 正确的形状（照 AOA HID 的多点 profile）

```
Collection (Application)   Usage Page Digitizers / Usage Touch Screen
  × N 个【独立】Usage(Finger) / Collection(Logical)，每个只含一组：
      Usage(Tip Switch) 1 bit + 7 bit 补齐
      Usage(Contact Identifier) 8 bit        ← 固定 = 槽位下标
      Usage(X) 16 bit      Usage(Y) 16 bit
  Usage(Contact Count) 8 bit                   ← 必须在**最后**
End Collection
```

三条硬性约定：

1. **每指一个独立 collection**，不是"一个 collection + `Report Count = N`"；
2. **`Contact Count` 放在所有手指之后**，不在开头；
3. ★ **`Contact Count` = 本帧里 contact **记录**的数量（含 `Tip=0` 的记录）**，
   **不是**"按下的触点数"。多点协议是**按帧重组**的：首报告带总数、续报告带 0。
   我们每帧固定发 N 条记录（未按下的槽也发 `Tip=0`），所以它**恒等于 N**。

> 依据：`libaoahid`（https://github.com/nemarpuc/libaoahid）的 `docs/PROFILES.md`
> —— AOA HID 的多点输入 profile，已在真机验证多点触摸。**详见附录 B.1**。
> 原文两句关键话："Contact Count is the number of contact records in the frame, including
> Tip = 0 records …… This is how Linux `hid-multitouch` (`mt_touch_report`) reassembles a frame."
> 以及 "the default Linux `hid-multitouch` class **does not treat an unseen contact as lifted**"。

### ★ 必须显式发 `Tip = 0`

**默认的 `hid-multitouch` class 不会把"报告里没出现的触点"当成抬起**，
所以抬手指时必须再发一条 `Tip Switch = 0` 的记录（带最终坐标），不能靠"从报告里消失"。
我们的报告每帧都带全部槽位，天然满足这一点。

### 描述符变大了，要分块发

从单指的 76B 变成 **334B**（5 组手指集合），超过 EP0 单次长度 → 注册时
`SET_HID_REPORT_DESC` **分 6 块顺序发送**（10.9 的分块逻辑正好用上）。
报告也从 7B 变成 **31B**：`N ×(1 按下位+补齐 + 1 标识 + 2 X + 2 Y) + 1 触点数`。

### ⚠️ 一处**未能真机验证**的链路（如实记录）

**宿主"真双指手势"这一段没能在硬件上跑通**，只验到了它两端：

- 宿主侧**造不出**真正的双指针事件流：
  - `sendevent` 直接写宿主自己的触摸屏 → **SELinux 拒绝**（`shell` 虽在 `input` 组，
    但 `u:r:shell:s0` 无写权限）；
  - 并发两条 `adb shell input swipe` → 实测是**两条独立事件流、各自 `pointer=0 (共 1)`**
    （宿主日志已打印 `pointer=N (共 M)` 可直接确认），会被当成"同一根手指被移动"。
- 因此 `HostActivity` 里 `ACTION_POINTER_DOWN/POINTER_UP` 这两条分支**只有代码审查与单元测试覆盖**
  （tracker 的分配/回收有 10 项单测，字段顺序与报告编码有单测），**没有硬件实测**。
- **验收方法（10 秒）**：人用**两根手指**按住宿主视频区并向内捏一下，
  手机上对应位置应出现两个触点并跟随缩放。

> 顺带记一个边界：**两路独立事件流若 pointerId 相同会被认成同一根手指**。
> 真机单面板不会出现（一条流里 pointerId 唯一）；用 adb 并发 `input` 才会。

### 10.13 音频内录（Android 10+ playback capture → AAC → 宿主播放）

**结论：打通了，而且是真机实测的端到端证据。** 手机内录 → AAC → `AUDIO` 流 → 宿主解码 →
`AudioTrack`，两端电平逐拍吻合。

#### 为什么必须用「内录」而不是麦克风

投屏要的是"手机里响什么、宿主就响什么"。麦克风录的是**环境声**，投屏时等于开了个窃听器。
Android 10（API 29）起提供 `AudioPlaybackCaptureConfiguration`：把**系统正在播放的声音**复制一份
给本应用 —— 这正是投屏需要的语义。

#### 内录的硬约束（全部无法绕过，官方文档 + 实测）

| 约束 | 说明 |
| --- | --- |
| API 29+ | Android 10 以下没有这个 API。低于 29 直接降级为「只投屏」 |
| `RECORD_AUDIO` | 运行时权限，必须授予 |
| `MediaProjection` 令牌 | 必须是**用户批准**的投影令牌（好在录屏本来就要了） |
| usage 白名单 | **只有 `USAGE_MEDIA` / `USAGE_GAME` / `USAGE_UNKNOWN` 可被捕获**。通话、通知、闹钟、铃声**一律录不到** |
| 被捕获方 | 不能声明 `allowAudioPlaybackCapture="false"`，且 `targetSdk` ≥ 29（否则要自行 opt-in） |
| 同用户 | 捕获方与被捕获方必须在同一 user profile |

★ 最后两条意味着：**银行/DRM/部分流媒体会静默退出捕获 —— 录到的是静音，不是 bug。**
排错时不要把它当故障（见排错手册 3.8）。

#### ★★ 最反直觉的一条：前台服务类型要并上 `microphone`

查 AOSP `ForegroundServiceTypePolicy` 的清单可以看到：

```
mediaProjection 类型的 runtimePermissions = [ CAPTURE_VIDEO_OUTPUT, OP_PROJECT_MEDIA ]   ← 没有 RECORD_AUDIO
microphone      类型的 runtimePermissions = [ ..., RECORD_AUDIO ]                        ← RECORD_AUDIO 只在这里
```

而 `RECORD_AUDIO` 属于**"使用时权限"**（Android 11 起）：应用退到后台后，只有当前台服务带了
**覆盖该权限的类型**才允许使用。所以：**只声明 `mediaProjection` 类型是不够的，
必须同时带上 `microphone` 类型 + `FOREGROUND_SERVICE_MICROPHONE` 权限。**

漏掉它的后果不是报错，而是**录到全 0** —— 最难查的那种失败形态（帧数一直在涨、
宿主也在播放，就是没声音）。

反向风险同样要防：`microphone` 类型要求**先拿到 `RECORD_AUDIO`**，没授权就传这个类型会直接
`SecurityException`，把整个前台服务（也就是投屏）打掉。所以实现里层层设限
（见 `CaptureService.canDeclareMicrophoneType`）：宿主没要音频不加、没授权不加；
且因为"要不要音频"是收到 `OPEN` 才知道的，还要**再调一次 `startForeground` 把类型并上去**
（官方文档明确支持）。

#### 线格式：音频复用同一个 12B 流头

```
codecId(4 ASCII, "aac ") + sampleRate(4, LE) + channels(4, LE)
```

刻意**不新增长度**：接收端识别"流头"靠的是 **payload 恰为 12 字节**（帧 payload = `12 + size`，
size ≥ 1 ⇒ ≥ 13）。给音频换一个不同长度的头会让这条判据失效。
代价是两个字段名（`width`/`height`）在音频语义下是采样率/声道数 —— 已在
`StreamHeader` 里用 `audioSampleRate`/`audioChannels` 显式命名，`toString()` 也单独渲染
（避免日志里出现误导人的 `48000x2`）。

校验也随之分流：视频用 `MIN_DIM..MAX_DIM` 校验宽高；音频必须换成采样率/声道数的范围校验
（48000 Hz 会被视频的规则判成非法），见 `StreamHeader.decodeAudio`。

#### 固定参数（`protocol/AudioSpec.kt`）

| 参数 | 值 | 理由 |
| --- | --- | --- |
| 采样率 / 声道 | 48000 Hz / 2ch | 内录的常见输出格式；AAC-LC 在该组合下通用可解码 |
| 位深 | 16 bit（`ENCODING_PCM_16BIT`） | 内录的唯一可选格式 |
| 每次读取 | 1024 样本（4096 B） | 等于 AAC-LC 的帧长，一次读取=一次入队，少一层缓冲 |
| 编码 | AAC-LC / 128 kbps | `MediaFormat.KEY_AAC_PROFILE = AACObjectLC` |
| 码流标识 | `CodecId.AAC`（`"aac "`） | `OPEN` 服务串里叫 `aac ` |
| `OPEN` 参数 | `audio=true&audio_bit_rate=128000` | `DEFAULT_AUDIO` 由 `false` 改为 **`true`** |

这些数字**同时**出现在四处（`AudioRecord`、手机编码器、宿主解码器、`AudioTrack`），
任何一处不一致都不报错、只表现为"音调不对/只有一边声道"，所以集中成常量并用单测钉住。

#### 实现结构

| 位置 | 职责 |
| --- | --- |
| `:protocol/AudioSpec.kt` | 上表的常量 + 范围校验（纯逻辑） |
| `:protocol/AudioLevel.kt` | PCM 电平（dBFS）—— **判定"到底有没有声音"的唯一客观手段** |
| `app-accessory/audio/AudioPipeline.kt` | 内录 + AAC 编码，**单线程闭环**（读→入队→排空），无中间队列 |
| `app-accessory/audio/TestTonePlayer.kt` | 调试用测试音（`USAGE_MEDIA` 1kHz 正弦），只在 debug 包 |
| `app-host/audio/AudioPlayer.kt` | AAC 解码 + `AudioTrack` 流式播放 |

玩法要点：

- 音频**独立一条线程 + 独立队列**（宿主侧 `AUDIO_QUEUE_DEPTH=8`）。与视频共用会让视频的
  丢帧/重建把音频带停，听感上就是咔哒声。
- 播放节奏**交给 `AudioTrack`**（`write(..., WRITE_BLOCKING)` 在缓冲满时阻塞，天然锁到采样率），
  不自己再叠一层 pts 配速（那只会引入重采样伪影）。
- 音频**不随 Surface 消失而停** —— 与显示无关，切后台时声音继续（像普通播放器）。
- 音频任何失败都**只降级不掐会话**：没权限、ROM 阉割、编码器出错，都只让"没有声音"。
- 重连复用：与视频同样只在会话层重发**流头 + CONFIG**，不重建管线（宿主的音频解码器是按连接新建的，
  不给它 `AudioSpecificConfig` 就永远 configure 不出来）。

#### A/V 同步：只做了「起播时刻」的粗补偿

音频管线比视频**少一段**（不经 SurfaceFlinger 合成、无 vsync 等待），所以音频天然领先。
实现是**一次性**延迟首段 PCM 的写出（`HostSession.DEFAULT_AUDIO_DELAY_MS = 60`）。

⚠️ **60ms 是推理出来的起点，不是测出来的值**：扣掉音频自身管线后差值落在几十毫秒量级。
现场可用 `--ez scan true --ei audio_delay_ms N` 调。**精细同步（以及音频时钟主导的配速）
仍未做**，见「未做」。

#### 真机实测（HONOR MAA-AN10 / Android 16 → BOE P40UCH / Android 14）

验证手段是**电平**：`AudioLevel` 算 RMS/峰值（dBFS），两端各打一条心跳日志。
这是必需的 —— 内录失败最典型的样子是"帧数一直在涨、宿主也在播放，但录到的是全 0"，
只有电平能把它和正常情况分开。

| 场景 | 手机端（内录） | 宿主端（解码后 PCM） |
| --- | --- | --- |
| 手机无任何播放 | `rms=-120.0`（静音下限） | `最大rms=-120.0` |
| 测试音 1kHz（幅度 0.5） | `rms=-9.0 / 峰值=-6.0 dBFS` —— 与设计的正弦幅度**精确吻合** | — |
| 王者荣耀（`USAGE_MEDIA`） | `rms=-8.2 / 峰值=0.0`，有声帧 1508 | `最大rms=-4.7 最近rms=-10.6 dBFS` |
| **抖音** | rms 在 -7.4 ~ -23.3 之间起伏 | `最近rms` **逐拍跟随**（-18.7→-11.5→-9.3→-5.7…），`最大rms=-4.6` |

抖音那一轮的完整行（`docs/verify/audio-verify-stats.txt`）：

```
audio=aac 48000x2 frames=13720 config=1 bytes=4683254
audioQueue=FrameQueue(audio size=2/8 dropped=0)
audio 48000Hz/2ch frames=13714 pcm=54856KB 最大rms=-4.6dBFS 最近rms=-22.0dBFS 输入超时=0
```

同时刻手机端 `音频帧 #13700 ... rms=-20.8dBFS` —— **两端读数吻合**。
留证截图 `docs/verify/audio-douyin-host.png`（宿主机画面上抖音在播，统计行实时显示音频电平）。

A/B 很干净：回桌面 → 两端同时掉回静音下限；启动抖音 → 两端同时点亮。

#### 本轮踩到并修掉的坑

1. ★★ **`am start` 到手机端 Activity 会白白释放配件 fd**：`ProjectionActivity.onNewIntent`
   原先**无条件** `forceRestart = true`，于是任何一次 `am start`（例如调试入口）都会走
   `teardownSessionOnly()` 释放 fd；而重开不一定成功（实测 `openAccessory` 连试 6 次全败），
   结果落进 **`config=accessory,adb` 但 `fd=0` 的死锁态**（10.10 那个"宿主救不回来"的状态）。
   修法：**只有携带 `UsbManager.EXTRA_ACCESSORY` 的真配件派发才重建会话**。
   → 教训：**探测手段绝不能扰动被测对象。**
2. **探测入口不能放在未导出的服务里**：`CaptureService` 是 `exported=false`，`am startservice`
   被系统直接拒掉（`Error: Requires permission not exported from uid ...`）。
   最终放在 Activity（它必须 exported 才收得到配件 intent），并由第 1 条的修复保证安全。
3. ⚠️ **`svc usb setFunctions mtp` 在"配件模式已锁"时无效**（`svc usb getFunctions` 返回 `accessory`）：
   连 `none`/`adb`/`mtp,adb` 都试过，`config` 不动。**只有物理重插拔能出来。**
   这与 10.8 那条"软件拔插线很好用"的结论**部分冲突** —— 那条在"宿主仍连着、只是要断链"时成立，
   但在"配件功能被锁住"时不成立。
4. ⚠️ **宿主反复 kernel panic 重启** —— 这一条**被连续误判过两次**（先归因"重插拔的供电扰动"，
   再归因"设备固件问题、App 层解决不了"），**两次都错**；真凶是**我们自己的 App**，
   已在 **10.16** 修掉（下面保留当时的排查过程，末尾有"作废"标记）。
   先用启动原因历史定性"是内核崩还是掉电"：

   ```bash
   adb -s <host> shell getprop persist.sys.boot.reason.history
   # kernel_panic,bug,1792147809     ← 18:50:09
   # kernel_panic,bug,1792146459     ← 18:27:39
   # kernel_panic,bug,1792146348     ← 18:25:48
   ```

   **连续三次启动全是 `kernel_panic,bug`**，而且 18:25 那次只活了 **111 秒**就再次崩。
   配合 `ro.boot.bootreason = kernel_panic`、内核日志里的
   `ipanic_die` / `mrdump_common_die`（`die()` ← `bug_handler` ← `brk_handler`）
   ⇒ 内核里踩着 `BUG_ON`(BRK) 挂了，**不是掉电**（电量 99%、`AC powered: true`）。

   ★ **对照实验**：同一时刻手机端（HONOR）的启动原因历史**全是正常的**
   （`reboot,honor_reboot` / `reboot,ota` / `shutdown,longstandby`，无 panic），
   uptime 2.2 天。

   🚫 **下面这句当时的结论已被 10.16 推翻，保留在此只为记录"我们错过一次"**：
   ~~「这是宿主那台设备自己的问题（BOE P40UCH / MT8781V / 内核 5.10.226，
   `Tainted: G W O`）。App 层解决不了，排查时绝不能把它误判成我们的 bug。」~~
   **真相**：panic 就是**我们的 App** 触发的（宿主端 `uav-reader` 线程发起了小于端点包长的
   bulk 读 → usercopy `BUG()`），已修。**教训**：只看"启动原因 + 手机端正常"就下"设备问题"的
   结论是不够的 —— 必须读完整 ramoops 看 `Comm:` 是谁（见排错手册 3.9 的"重大更正"）。

   ⚠️ 归因纪律：18:27 那次 panic **发生在用户重插拔之前**，
   所以"重插拔搞崩了宿主"这条因果**不成立** ——
   当时只凭 `up 0 min` + 端口变化就下了结论，是又一次"现象相似就当因果"的误判。

   ⚠️ 已知关联（**未确证，只作线索**）：三次 panic 都发生在我执行
   `adb install` / `am start` 之后的 1 分钟内。不排除巧合（安装会带来 IO/CPU 突发 +
   同时 8 Mbps USB bulk 满载 + OTG/充电同时在位）。要定性需要专门的 A/B，
   见排错手册 3.9 末的观测法。
5. 手机端 **12s 空闲看门狗**要求"先起手机、起宿主"这个顺序必须紧凑（本次因间隔过久触发过一次，
   直接落进上面第 1 条的死锁态）。建链脚本要把两端启动压在几秒内。

#### 未做（明确记下，别当成已实现）

- **精细 A/V 同步**：只做了起播时刻的常量补偿，没有长期漂移校正，也没有以音频时钟主导视频配速。
- **音量/静音跟随**：宿主端固定音量；手机端把音量调到 0 时，内录拿到的**可能也是衰减后的信号**
  （捕获点在混音之后），未实测。
- **`USAGE_MEDIA` 之外的音频**：通话、通知、铃声按设计**不可捕获**（框架限制）。
- **多声道 / 非 48k 源**：不做重采样，固定按 48kHz 立体声协商。
- 手机扬声器**仍在出声**（`AudioMix` 用 `ROUTE_FLAG_LOOP_BACK | ROUTE_FLAG_RENDER`，
  回送捕获方的同时正常播放）—— 两台设备放一起会听到"双重声音"，这是预期行为。

### 10.14 宿主菜单：点画面外的空白处 显示 / 隐藏

画面占满时，顶部那块菜单（状态 + 统计 + 三个按钮）会挡住手机内容（⚠️ **10.19 已把面板改为左侧竖栏**，本节的坐标/形态是当时的记录）。原先是**一直显示**，
没法隐藏看全屏。

#### 为什么选"画面外的空白处"作为开关区

宿主布局是 `FrameLayout`（黑底）里放一个按视频宽高比自适应的 `AspectRatioSurfaceView`
（居中），于是左右（竖屏视频在横屏宿主上）会留下**信箱边**。关键点：

- 信箱边上的触摸**本来就不转发**给手机（10.11 的规则：落在显示区外一律忽略）；
- 而**画面内的触摸必须留给触摸转发**，不能拿来当 UI 开关。

所以"点空白处切换菜单"与"触摸转发"**天然不冲突**，不需要任何额外手势或长按。

#### 实现（宿主端，约 40 行）

| 位置 | 内容 |
| --- | --- |
| `activity_host.xml` | 根 `FrameLayout` 加 `@+id/root`；面板 `LinearLayout` 加 `@+id/overlay` |
| `HostActivity.setupMenuToggle()` | 在 `root` 上装触摸处理：命中显示区 → **`return false` 不消费**（事件继续流向 `surfaceView`，走 10.11 的转发路径）；落在显示区外 → 消费该事件并切换菜单 |
| `setMenuVisible(show)` | `alpha` + `View.GONE/VISIBLE` 的 160ms 过渡（`MENU_ANIM_MS`） |

显示区判定**直接复用 `TouchMapper`**（与触摸转发同一套几何、半开区间），
不做第二份实现 —— 否则"哪里算画面内"会出现两个可能不一致的定义。

#### 三处自动行为（都是"别让用户困惑"）

- **首帧到达 → 自动收起一次**（`menuAutoCollapsed` 一次性标志）：画面一出来就让视频干净地占满。
  之所以是**一次性**而不是"每次首帧都收"，是因为会话重启/重建解码器也会走 `onFirstFrame`，
  每次切后台回来都收一遍会让人没法调参数。
- **出错 / 断开 / USB 拔出 → 自动展开**：错误信息就写在面板里，
  面板收着的话用户只能看到"画面不动"，无从判断是拔线还是授权被拒。
- **面板内加了一行提示文案**（中英各一份，`host_menu_hint`），否则"界面很干净但再也点不出按钮"
  一定会被当成 bug。

#### 真机验证（宿主窗口 1920x1080；视频区 x∈[728,1192] y∈[36,1059]）

| 操作 | 结果 |
| --- | --- |
| 基线（首帧后） | `overlay` 节点数 **0** ⇒ 菜单已自动收起 ✅ |
| 点左信箱 (200,540) | **展开**，UI 树里出现 `投屏中（首帧已输出）` + 三个按钮 ✅ |
| 原地再点一次 | **收起** ✅ |
| 点右信箱 (1700,540) | **展开**（两侧都行）✅ |
| 点视频区内 (960,300) | 菜单**保持隐藏**，日志为 `触摸转发 → 手机 (612,695)` ✅ |
| 同上，手机侧 `getevent` | 收到 `ABS_MT_TRACKING_ID` + `BTN_TOUCH DOWN/UP` ✅ |

全程宿主 `uptime` 持续增长（**无重启**），链路 `dropped=0`。
留证：`docs/verify/host-menu-expanded.png`、`docs/verify/host-menu-collapsed.png`。

#### 已知不足

**提示文案放在面板里** ⇒ 面板收起时恰好看不到"怎么叫回来"。
最省事的改法是把那行提示放到面板外（常驻底部一行暗色小字），
或首帧后先显示几秒再淡出。**尚未改**（属 UI 取舍，先按现状记录）。

### 10.15 1:1 像素映射（编码尺寸 = 宿主实际显示尺寸）

**问题**：原先 `max_size = align8(min(手机长边, 宿主**面板**长边))` —— 只看"长边"，**不看宿主到底把画面铺多大**。
宿主横屏时画面是竖的，只能占中间一条（实测显示区 464x1023 = 0.47 Mpx），而编码却是 872x1920
（1.67 Mpx）⇒ **多编 3.5 倍的像素**，码流、编码、解码全按这个尺寸付钱，最后在宿主上又被缩回去。

**改法**（核心就一句）：让**编码尺寸 = 画面在宿主显示区里适配后的尺寸**。

```
显示区    = 宿主根视图尺寸（不是面板尺寸；扣掉状态栏/导航栏）
适配后尺寸 = Scale.fitInside(显示区, 手机尺寸)          ← 信箱式，与视图用同一函数
max_size  = align8(min(长边(手机), 长边(适配后尺寸)))    ← 再夹在 [240, 手机长边] 之间
```

三个要点：

1. **几何只有一份实现**：`Scale.fitInside` 同时被 `AspectRatioSurfaceView.onMeasure`（真正决定视图多大）
   与上面的尺寸协商调用。以前视图里手写了一份，"预测的显示尺寸"和"真实视图尺寸"是会漂移的。
2. **把显示区下发给手机，而不是只给一个 `max_size`**：`OPEN` 新增
   `display_width` / `display_height`。原因见第 3 点。`max_size` 仍保留（老宿主/显示区未知时回退）。
3. ★ **1:1 的目标尺寸随画面比例变化 ⇒ 必须"现算"**：同一块显示区，手机竖屏时算出 992、
   旋转成横屏时算出 1920（横屏画面能铺满整宽）。所以手机端在**每次要用时**调
   `ParsedOpen.encodeMaxSize(当前手机尺寸)`：
   - **手机旋转** → 重建编码器时重算，**不需要重新协商**（实测 `max_size 992 -> 1920`）；
   - **宿主旋转** → 显示区变了，宿主**重启会话**去重新协商（见下）。

**宿主自己旋转为什么要重启会话**：`HostActivity` 声明了
`configChanges=orientation|screenSize|screenLayout|density` ⇒ 旋转**不重建 Activity**，
旧的 `max_size` 就会过期（典型症状：画面变糊，因为手机按旧尺寸编、宿主放大显示）。
所以在根视图的 layout 监听里核对"按当前显示区该编多大"，偏差 > **10%**（`AREA_RENEGOTIATE_RATIO`）
就 `stopSession()` + 重新扫描 —— 走已经验过的自动重连路径（约 1.5s，不重新弹录屏授权）。

#### 真机实测（宿主 P40UCH**034** / 横屏；配件 HONOR MAA-AN10 / 竖屏 1224x2700）

| | 改动前 | 改动后 |
| --- | --- | --- |
| 协商口径 | 宿主面板长边 1920 | 宿主显示区 1920x987（根视图） |
| `max_size` | 1920 | **992** |
| 手机编码 | 872x1920（1.674 Mpx） | **456x992（0.452 Mpx，27%）** |
| 宿主显示 | 464x1023 | 453x987（编码/显示 = **0.9937 ≈ 1:1**） |

手机旋转后（**宿主动都没动**）：

```
UAV-Video: 旋转：源 1224x2700 -> 2700x1224，max_size 992 -> 1920
           （1:1(宿主显示区 1920x987)），编码 456x992 -> 1920x872
宿主视图   bounds=[0,93][1920,965] = 1920x872   ← 与编码尺寸完全一致
```

链路指标无退化：`dropped=0`、`skew=±1ms`。原文见 `docs/verify/one-to-one-stats.txt`，
截图 `docs/verify/one-to-one-landscape-host.png`。

#### ⚠️ 关于"省了多少带宽"，要说准确

码率仍是固定 **8 Mbps**，所以**字节数没有下降**（CBR 下每秒还是那么多）。这次改变的收益是：
同样的码率现在只喂 **0.45 Mpx** 而不是 1.67 Mpx ⇒ **每像素比特数涨了 3.7 倍**（画质余量更大），
同时编码/解码/GPU 的像素工作量降到 27%。**想真正省带宽，得把 `video_bit_rate` 一起按面积缩小**
（未做，见"未做"）。

#### 已知边界（都记下来，别当成完美）

1. **宿主旋转后的自动重协商没能在真机验证**：那台 P40UCH(034) 在我改旋转设置的瞬间就掉线
   （当天连续三次 `cold,powerkey` 冷启动，端口反复变化）。代码 + 单测在，端到端没跑通。
2. **`OPEN` 时刻读到的显示区可能比最终布局小几十 px**：实测 987 而稳定后是 1023（差 36 ≈ 状态栏），
   于是编码只覆盖可用区的 ~96.5%（代价是画面略小一圈，**不会放大模糊**）。
   10% 的阈值故意不追这 3.6% —— 否则每次建链都会自己重启一次。
3. **短边对齐 8 会引入最多 ~1.4% 的宽高比误差**（显示区小、尺寸小时更明显：理想 449.7 → 实际 456）。
   这个误差以前就有（当时只有 0.2%，因为帧大），是 `align8` 规则的固有代价，不是本次引入的。
4. **宿主侧仍可能"一个画面两种尺寸"**：`STATS` 里的 `maxSize=` 是**协商时**的值，
   手机旋转后会变（真实尺寸看同一行的 `video=avc1`）。别只看 `maxSize` 下结论。

#### 未做

- **按面积缩放码率**（见上，"收益是画质不是省流"）。
- **宿主窗口尺寸变化的其他形态**：分屏、悬浮窗、外接显示——都靠同一个 layout 监听覆盖，
  但没有逐个真机验证。
- **不整数倍的缩放**：1:1 只保证"没有二次缩放"，宿主显示区若比手机大，宿主仍会放大（无解，源就那么大）。

### 10.16 ★ 宿主内核 panic 的真凶：sub-packet bulk 读（已修）

**现象**：宿主（BOE P40UCH / MT8781V / 内核 5.10.226）反复 `kernel_panic,bug` 重启，
之前（3.9 旧版）错误归因为"设备固件/内核问题"。MTK 完整日志包（`APLog_*` 的 `last_kmsg`
= `/data/debuglogger/console-ramoops-0` 持久化 ramoops）给出决定性现场：

```
usercopy: Kernel memory exposure attempt detected from SLUB object 'kmalloc-128' (offset 0, size 391)!
kernel BUG at mm/usercopy.c:99!                Internal error: Oops - BUG
CPU: 7  PID: xxxxx  Comm: uav-reader           ← 宿主端我们的 bulk 读线程
  usercopy_abort <- __check_object_size <- do_proc_bulk+0x374 <- usbdev_ioctl
```

**机制**：`USBDEVFS_BULK`（`bulkTransfer`）读时，内核按**请求长度** kmalloc 一块 bounce buffer
再 `copy_to_user`。协议层读报文头(24B)/小帧末段(65~128B)时，`BulkByteChannel.read()` 的
`max = minOf(len, readChunkSize)` 把同样小的长度透传给了内核 —— **小于端点包长 512B**。
这台 MTK 主机栈**不把 `actual_length` 截到请求长度**：设备交付更大的包（实测 391B）时，
内核拿 391 去拷 128B（kmalloc-128）的缓冲 → 加固 usercopy 直接 `BUG()` 崩内核、设备重启。
kmalloc-128（而非 32）说明这次命中的是 65~128B 的那次小读，但 24B 头读同属一类。

**修法（两层）**：

- `:protocol/BufferedByteChannel.kt`（新）：`ByteChannel` 装饰器。对底层**永远整块
  `scratchSize`（= readChunkSize 16KB，端点包长的整数倍）读**；一次到货多于上层所需时，
  **多余字节压入残留缓冲**供下次 `read` 续上（绝不能丢 —— 丢了是字节流错位，
  表现为"流头乱码/解码器配错"，比 panic 更隐蔽）。0（ZLP/超时）与 -1（EOF）原样透传；
  `discardBuffered()` 供"丢弃上次会话尾巴"的时机同步清残留。
- 宿主 `HostActivity`：`BulkByteChannel` 包进 `BufferedByteChannel` 再交给 `Transport`。
  协议层 24B 头/小帧读法**零改动** —— 让 USB 层去 absorb。

**单测**（`BufferedByteChannelTest`，+8）：① 复现 panic 场景（上层要 24 底层一次到 391，
只给 24 且 367B 不丢、底层只被申请一次且长度恒 16384）；② 残留续读期间底层零调用；
③ 0/-1 透传且不清残留；④ `discardBuffered`；⑤ close 契约；⑥ 边界；⑦ 经 `Transport`
混合尺寸 `readFully` 5 万字节序严格不乱。协议层 229 → **237 项全绿**。

#### 未做 / 边界

- **真机复验**：修复后需长时间投屏（控制/音频小帧密集场景）确认不再 panic ——
  panic 是概率性命中小读 × 大包到货的交错，短时间不崩不代表修好，以 ramoops 无新增为准。
- **手机端（accessory）fd 流读法未动**：`/dev/usb_accessory` 是流语义，不存在此问题。
- **写侧**：MTK 对**写**路径（`do_proc_bulk` 的 OUT 方向）未观察到同类 panic，
  暂不改；若未来出现 `copy_from_user` 版 usercopy panic，再对写侧做同样缓冲。

### 10.17 像素模式开关：1:1 ↔ 高清（宿主菜单可切）

**动机**：1:1 虽省算力，但**观感偏软** —— 它按显示区尺寸编码（如 456x992），宿主 1:1 显示、
**没有超采样**；而旧口径按面板长边编高分辨率（872x1920）、宿主端缩下去，效果上等于超采样，
细节反而更锐。用户要能在两者间切，于是加开关。

**关键设计：手机端本来就有回退，所以"关掉 1:1"是纯宿主行为**

`ParsedOpen.encodeMaxSize(phoneW, phoneH)` 在**拿不到显示区**时会退回 `max_size`。于是宿主只要：
不下发 `display_width/height`、并把 `max_size` 换回 `Scale.computeMaxSize(...)`（旧口径），
手机端就自动按高分辨率编码。开关状态用 `SharedPreferences` 持久化（`HostPrefs`）。

- 宿主 `HostSession`：新增 `oneToOne: Boolean`；为 `false` 时不取显示区、走旧口径、不下发显示区。
- 宿主 `HostActivity`：菜单新增「画质」按钮，切换后**重开会话**（`stopSession()` + `scanAndAttach()`）——
  `max_size` 只在 `OPEN` 时协商一次，改了必须重发 `OPEN`。

**★ 真机踩到的坑：手机端"重连复用编码器"让开关不生效**

第一次实现后实测：宿主已按 `max_size=1920` 重开会话，但手机端**照旧编 456x992**。手机日志给出答案：

```
UAV-Accessory: OPEN: max_size=992 ... 已回 OKAY，启动屏幕采集…
UAV-Video: 新会话接入：已重发流头 456x992 与 CONFIG(31B)
UAV-Accessory: 复用既有编码器与内录，已重发两条流的流头与 CONFIG   ← 复用，不看新尺寸
```

手机端为"重连快"在 `CaptureService.startCaptureInternal` 里**无条件复用**既有编码器
（因为投影令牌只允许 `createVirtualDisplay` 一次，重建要重新授权），于是 `max_size` 变了却不重配。

**修法（手机端）**：复用前先比尺寸 —— `VirtualDisplayEncoder.applyOptions(newOptions)`
更新 `negotiatedOptions` 后走 `rebuildForSizeChange(srcW, srcH, reason="像素模式变更")`：
尺寸不同就重建（复用虚拟屏与投影令牌，代价小），相同则原样复用。
⚠️ 重建时新输出线程**已重发流头 + CONFIG**，所以此时**不能再 `resendStartup()`**（会多发一份流头）。

**真机验证（宿主 P40UCH 034 + HONOR）**：

| 操作 | 宿主 `OPEN options` | 宿主解码 | 结论 |
| --- | --- | --- | --- |
| 默认（1:1） | `max_size=992 display_area=1920x987` | `video=avc1 456x992` | ✅ |
| 切高清 | `max_size=1920 display_area=-` | `video=avc1 872x1920` | ✅ 手机真的重编了 |
| 切回 1:1 | `max_size=992 display_area=1920x987` | `video=avc1 456x992` | ✅ |

⚠️ 初版实现走的是"断开 + 重连"，实测 **15~25s** 才生效、偶发一次 `bad magic` 重试
（已由 10.18 的**原地重协商**取代：约 2~3s、不重连、不重试）。证据 `docs/verify/`。默认保持 **1:1**。

#### 未做
- **码率不随模式变**：高清模式编 3.7 倍像素但码率仍 8 Mbps（每像素比特数被摊薄）——
  观感更像"超采样带来的锐"而非"更高码率"。按面积调码率仍列 P1。

### 10.18 原地重协商：改尺寸不再断开重连（切换从 15~25s 降到 2~3s）

**问题**：10.17 的像素开关走"`stopSession()` + `scanAndAttach()`"。而**手机端此刻仍在推流**，
宿主重连后第一个握手偶尔读到帧字节（`bad magic` / 握手超时）→ 报一次 ERROR →（还可能触发
onError 里的"快路径失败 → 强制 AOA 重握手"，把一次画质切换升级成**真 USB 重枚举**）→ 自动重试
才能成功，**耗时 15~25s**。

**关键发现：根本不必重连** —— 两端本来就具备"会话中途改尺寸"的能力：

| 端 | 现成机制 | 结论 |
| --- | --- | --- |
| 手机 | `AccessorySession` 的命令循环**无状态门槛**，`Command.OPEN -> handleOpen()` 任何时候都处理；`handleOpen` → `capture.startCapture` → `VirtualDisplayEncoder.applyOptions`（10.17）**先停旧输出线程 → 复用虚拟屏按新尺寸重建 → 新输出线程重发流头+CONFIG** | ✅ 天然支持 |
| 宿主 | `Connection` 已支持**中途重复流头**（`updated != headers[streamId]` 会更新并回调）→ `FrameQueue.header` 更新 → `handleConfigFrame` 释放旧解码器、按新尺寸新建 —— **这正是"手机旋转重建"在线上跑的机制** | ✅ 天然支持 |

**改法（宿主侧，手机端不需要改）**：

- `HostSession`：把 `sessionFlow()` 里的 OPEN 段抽成 `sendOpen(): Boolean`；新增 `fun renegotiate()`
  —— 在**现有连接**上直接 `sendOpen()`（不发 CNXN）。`openAckLatch` 由 `val` 改 `@Volatile var`
  并在每次 `sendOpen()` 换新闩（`CountDownLatch` 一次性）。
- `HostActivity`：新增 `requestRenegotiate()` —— **优先原地重协商，失败回退断开重连**；
  丢到后台线程（`renegotiate()` 会等 OKAY，不能卡主线程）；`AtomicBoolean` 防布局回调连发。
  像素开关与"宿主旋转导致的显示区变化"都改走它。
- ⚠️ **`oneToOne` 必须由"构造时捕获的布尔值"改成回调**：原地重协商在同一条会话里重新下发 OPEN，
  必须取**此刻**的模式 —— 用捕获值会一直按会话创建时的口径算（真机踩到：用户切到 1:1 后，
  重协商仍下发 `max_size=1920 display_area=-`，画面纹丝不动）。
- 切换期间仍保留 `expectingRestart` 抑制（10.17b）：只在**回退**到断开重连时才可能用上；
  尺寸（重）配置成功（`onVideoSize`）或首帧到达即清除。

**真机实测（宿主 P40UCH 034 + HONOR，双向）**：

```
23:18:55.284  像素模式切换 → 1:1（按显示区编码）
23:18:55.288  原地重协商：在同一条连接上重发 OPEN
23:18:55.293  OPEN options: max_size=992 display_area=1920x987   ← 新参数正确
              → 约 2~3s 内 video: 872x1920 → 456x992；无 host session stopped / 无 bad magic / 无 ERROR
（反向 1:1 → 高清同样 ~3s，max_size=1920 display_area=-，video → 872x1920）
```
丢帧 `dropped=0`、`skew=±2ms`。会话未重建（帧计数连续）。

#### 未做 / 边界

- **回退路径未真机触发过**：`renegotiate()` 失败才会走断开重连，实测未出现失败。
- **手机端必须是含 `applyOptions` 的包**（10.17）；旧包上原地重发 OPEN 也不会改尺寸（需同时升级两端）。
- 宿主旋转导致的显示区变化现在也走原地重协商，但**仍未在真机上单独验证**（当前宿主自动旋转）。

### 10.19 宿主 UI 产品化：左侧竖栏面板 + 紧凑统计

**问题**：界面是"深色底 + 一排框架灰按钮 + 一整行塞满的统计文本"，观感很糙；而且面板横在**顶部**，
手机竖屏镜像（实测视频视图 448x987）在横屏宿主上只占中间一条，顶部面板正好压在画面上。

**改法**：

- **面板移到左侧、做成竖栏**（`overlay`：宽 300dp、`layout_height=match_parent`、只圆右两角）。
  横屏宿主 1920x1080 下视频居中占 448x987，两侧各留 ~735px 信箱边 ——
  **300dp ≈ 450px 正好落在左边黑边里，完全不挡画面**（截图 `docs/verify/ui-host-side-live.png`）。
  操作按钮因此改为**竖排**（`HostTileRow`：图标在左、文字在右）；底部用 `Space(weight=1)` +
  分隔线把提示推到底，侧栏形状才成立。
- **常驻状态药丸**（左上角，`status_chip`）：彩色圆点（空闲灰 / 连接中黄 / 投屏中绿 / 出错红）+ 短文案。
  面板收起后仍有状态可看，**且它是"再次打开面板"的显式入口** —— 收起后不会"无路可回"。
- **画质改成分段控件**（`1:1 像素` / `高清`）：当前模式一眼可见，比"点按钮才知道现在是哪种"清楚；
  点**已选中**的那段是 no-op（不触发重协商）。
- **统计拆成两套形状**：日志仍用 `HostSession.stats()`（一整行、什么都不漏，压测读首末对比）；
  面板用新增的 `statsCompact()`（4 行短句、刻意控制在 300dp 不折行）。
- 标题栏强调竖条、内嵌统计卡片、收起按钮（左箭头）、面板改从左侧滑入（`translationX`）。
- 资源：新增 `colors.xml` / `styles.xml` / `drawable/`（面板、卡片、药丸、磁贴、分段、圆点、强调条）
  与 5 个矢量图标；无 appcompat/material 依赖，全部用框架控件 + 自定义 drawable

  加按下鼓包、被 88dp/48dp 最小尺寸撑变形）。

**★ 顺带修正一个"看起来像真问题"的读数**：面板上的延迟曾显示 `p50 1478ms`，而历史口径是 64ms。
查明是**时钟标定不可靠**：CNXN 交换若撞上"手机端正在启动会话"，往返可达 ~2.8s，
时钟偏移不确定度就是 ±1.4s（`skew=±1354ms`）—— 此时 p50 是**假数**。
新增 `CLOCK_TRUSTWORTHY_NANOS`（200ms）阈值：超过就**不显示 p50**，只显示
`标定不可靠（skew ±Nms）`。宁可说"测不准"，也不给一个会被当真的数。

### 10.20 路线图 P1（三件）：码率按面积缩放 / 整 GOP 尾部丢弃 / 音频精细 A/V 同步

#### ① 码率按编码面积缩放（宿主侧，手机零改动）

**问题**：1:1 把编码面积从 1.67 Mpx 降到 0.45 Mpx（27%），但码率仍固定 8 Mbps
⇒ **每秒字节数一点没降**，只是把同样的码率摊到更少像素上（这正是 10.15 里"诚实记录"的那一条）。

**改法**：

- `:protocol/Scale.videoBitRate(baseBitRate, maxSize, srcW, srcH, referenceMaxSize)`（纯函数 + 单测）：
  `bitrate = base × area(maxSize) / area(referenceMaxSize)`，夹在 `[MIN_VIDEO_BIT_RATE=1 Mbps, base]`。
- **面积按"长边 = m"估算**（`m × m×短长比`），参考面积取 `computeMaxSize`（旧口径 / 面板长边）。
  这么算的三个好处：① 高清口径面积 = 参考面积 ⇒ **高清保持 8 Mbps 不变**；
  ② **与手机方向无关** —— 旋转手机不会让码率跳变；③ 不会因某一方向更扁而"省"过头。
- 宿主 `HostSession.sendOpen` 计算后覆盖 `options.videoBitRate`；`STATS` 与面板统计都带上码率。
  **手机端零改动**（它本来就读 `options.videoBitRate` → `MediaFormat.KEY_BIT_RATE`）。

**真机验证（宿主 P40UCH 034 + HONOR，手机 1224x2700 / 面板 1920x1080）**：

| 模式 | `OPEN options` 里的 bitrate | 说明 |
| --- | --- | --- |
| `1:1`（max_size=992） | `2137931`（2.14 Mbps，= 8M 的 26.7%） | 面积比 445,408 / 1,670,400 = 26.7% ✅ |
| `高清`（max_size=1920） | `8000000`（8.00 Mbps） | 面积 = 参考面积 ⇒ **不变** ✅ |

单测 +5（`:protocol:test` 237 → **242**）：1:1 实测值落在 2.0~2.3 Mbps、方向无关、
面积不小于参考时回基准、下限保护、对 `maxSize` 单调不减。

⚠️ **实测吞吐未能做受控 A/B**：用滑动制造画面运动时两次的内容不同
（1:1 那次反而更高：0.80 vs 高清 0.13 Mbps），不能据此说"省了多少带宽"。
要量化需要**播放视频类内容**（恒定高运动）再对比两种模式的 `bytes/s`。

#### ② 整 GOP 尾部丢弃：新会话先等 IDR 再推帧（手机端）

**问题**：编码器是一条**连续**的 GOP 序列（IDR + 一串 P/B）。宿主每逢"新会话接入"
—— 首次建链、重连、原地重协商、编码器重建 —— 都会新建一个从零开始的解码器。
这时手机若照旧推当前 GOP 的中间帧，新解码器手里**没有它依赖的那个 IDR**，
于是花屏到下一个 I 帧（实测 I 帧周期 **3s** ⇒ 最长 3 秒花屏）。

**改法**：

- `:protocol/GopTailGate`（纯逻辑、可单测，时钟可注入）：
  `arm()` 开始等 IDR；`shouldEmit(isKeyFrame)` 在见到 IDR 时放行并解除等待；
  **超时兜底 600ms 强制放行** —— 等不到 IDR 时，宁可短暂花屏也不要一直黑屏。
- `VirtualDisplayEncoder`：
  - `startOutputLoop()`（新建编码器）与 **`resendStartup()`（复用既有编码器接新会话）** 都 `arm()`；
  - `resendStartup()` 额外**向编码器立刻要一个 IDR**
    （`setParameters(Bundle{ PARAMETER_KEY_REQUEST_SYNC_FRAME = 1 })`，API 26+），
    有它等待通常只要 ~1 帧；
  - 输出循环里非关键帧直接 `releaseOutputBuffer` 丢弃（⚠️ **CONFIG 不受门控** ——
    它走 `INFO_OUTPUT_FORMAT_CHANGED` 分支，丢了必然黑屏）；
  - 计数 `gopTailDropped` 进 `stats()`，并打一条"等 IDR 期间丢掉 N 帧"的恢复日志作为现场证据。

**踩坑记录**：`MediaCodec.getParameters()` 是**隐藏 API**（编译期就不存在，
报 `Unresolved reference 'parameters'`），公开的只有 `setParameters(Bundle)` + 常量，
所以要自己 `new Bundle()` 再 `putInt`。

**真机验证（宿主 034 + HONOR，456x992）**：

```
I/UAV-Video: 整 GOP 尾部丢弃：等 IDR 期间丢掉 1 帧，拿到关键帧后恢复推流（456x992）
I/UAV-Video: 编码帧 #1（456x992, 9359B, key=true）
```

单测 +9（`:protocol:test` 242 → **251**）：未 arm 一律放行、arm 后丢 P 帧、IDR 放行并解除、
超时兜底（599ms 仍等 / 600ms 放行）、计时从 arm 起算、disarm、连续 arm、默认值。

#### ③ 音频精细 A/V 同步：以音频播放头为准，丢掉/等待偏晚偏早的帧

**原先**：只在起播时刻做一次**常量补偿**（`AudioPlayer.applyStartupDelay`，第一段 PCM 前睡 60ms）。
那只对齐了起点，之后两端时钟的漂移没人管（两台设备晶体不同）⇒ 看得越久越跑开。

**能力边界（先说清）**：视频是 `releaseOutputBuffer(index, true)` 交给 `SurfaceFlinger` 合成的，
**没法给视频重新定时**。所以只能靠两种手段纠正：**丢帧**（晚太多，播出去只会跳一下）与
**有界等待**（早太多，先睡一小会儿再交上去）。

**改法**：

- `:protocol/AvSyncGate`（纯逻辑、时钟由调用方传入 ⇒ 单测确定）：
  - 每帧观测 `measured = 音频已播到的时刻 − 帧的采集时刻`，里面混着**系统性的渲染管线延迟**与
    **真实漂移**。用**限幅 EMA**（α=0.08，单步 ≤4ms）让 `offset` 慢慢吃掉系统性延迟，
    剩下的残差才拿来纠偏；
  - 判定：晚 > 容差(30ms)+阈值(60ms) → **丢**；早 > 阈值(30ms) → **等**（单帧封顶 40ms）；
  - **预热 60 帧只学习、不干预** —— 否则开局 `offset` 还没收敛会把前几十帧误丢。
- `AudioPlayer`：暴露 `playedUntilNanos()` —— 用 `AudioTrack.getPlaybackHeadPosition()`
  （已渲染到输出的帧数，屏蔽符号位处理 12 小时绕回）而不是"已写入"（后者含缓冲，会算得偏前几帧）。
- `VideoDecoder`：新增可选 `frameGate(ptsUs, atNanos) -> Boolean`，在 `releaseOutputBuffer(true)`
  **之前**调用；`false` = 不渲染。门内允许短暂阻塞（跑在解码线程，故只做几十毫秒级等待）。
- `HostSession.avSyncFrame`：喂两个时钟、按决策丢/等；**三道安全门**（缺任一条就退回"照旧渲染"）：
  1. 没有音频 / 音频还没起播 → 没有音频时钟可依据；
  2. **时钟标定不可靠**（`skew > 200ms`）→ 帧 pts 换算本身就带 ±1.4s 噪声，拿噪声纠偏只会疯狂丢帧；
  3. **音频播放头连续 60 帧不前进**（上游没数据）→ 每一帧都会被判成"偏晚"⇒ 全丢 ⇒ **画面黑**。
     这是最危险的边界，单独计数兜底 + 只告警一次；播放头恢复就自动复位重学。
- 读数进 `STATS`：`avsync=offset=Nms drop=N hold=N frames=N`、解码器侧 `gateDropped=N`。

**★ 自测抓到的设计缺陷**：最初把"管线延迟容差"**双向**相减，结果 `lateError=0`（正好同步）
的帧被算成"早 30ms"，于是**每一帧都去等 30ms** —— 画面反而一顿一顿。
改成容差**只吸收"晚"的方向**后消失（单测 `正好同步的帧不会被误判成偏早` 专门盯这条）。

**真机验证（宿主 034 + HONOR，高清模式 872x1920，手机正在出声 rms=-7.7dBFS，skew=±142ms）**：

| 时刻 | offset | drop | hold | frames | 队列丢帧 |
| --- | --- | --- | --- | --- | --- |
| t+25s | 20ms | 0 | 5 | 1046 | 0 |
| t+75s | 18ms | 0 | 8 | 2266 | 0 |
| t+150s | 7ms | 0 | 33 | 4485 | 0 |

解读：offset **稳定在 7~20ms 不跑飞**，**一帧都没丢**（`drop=0` / `gateDropped=0` / 队列 `dropped=0`），
`hold` 缓慢累积（0.7%）—— 正是它在**吸收缓慢漂移**；不修的话偏移会持续跑开。
单测 +11（`:protocol:test` 251 → **262**）。

#### 未做 / 边界

- **不能给视频重新定时**，所以只能丢/等；音频侧不做重采样微调（会click）。
- `hold` 会给那几帧加最多 40ms 延迟（实测 0.7% 的帧受影响，延迟读数未见恶化）。
- 阈值（30/60/30/40ms）是按 30fps 估的，**没有在 60fps 或高刷屏上调过**。

### 10.21 修复「切后台→回前台黑屏好几秒」：新增 `RQID` 反向通道

**现象**：宿主按 Home 键切到后台，再回前台，画面黑屏好几秒才出来。

**根因（10.20② 修不掉的同一个病根，但触发路径不同）**：

```
surfaceDestroyed → suspendRendering() → 释放解码器（必须，见 10.10）
      ↓ 手机照旧编码、照旧推流（宿主只是不喂解码器，链路不动）
回前台 surfaceCreated → resumeRendering() → 用缓存 CONFIG **新建**解码器
      ↓ ★ 新解码器手里没有任何参考帧
继续喂当前 GOP 的 P 帧 → 必须等下一个 IDR → I 帧周期 3s ⇒ 黑屏最长 3 秒
```

`MediaCodec` 的 output surface 在 `configure` 时固定、**无法改绑**，所以"换 Surface"
只能新建解码器 —— 这条 10.10 就定下了，改不了。

关键在于：**10.20② 的 `GopTailGate` 只在"新会话接入"时 arm**（`startOutputLoop` /
`resendStartup`），而**切后台不是新会话**（链路没断、没重协商、流头与 CONFIG 都还有效），
所以那条门控路径根本走不到 ⇒ 手机完全不知道宿主的解码器已经换人了。

**改法：给宿主一条"主动开口要关键帧"的反向通道。**

协议原本是**单向**的：只有 `OPEN`/`CLSE` 是宿主→手机，没有"会话级请求"这个概念。
新增一个命令字：

| 项 | 值 |
| --- | --- |
| 命令字 | `RQID`（ASCII `RQID` 的小端 u32 = `0x44495152`） |
| 方向 | 宿主 → 手机（单向，手机发出无意义） |
| payload | 无（空） |
| 语义 | 「我的解码器重建了，请立刻吐一个 IDR」 |

- `:protocol/Command`：新增 `RQID`。
  ⚠️ **必须放进 `Connection.dispatch` 的 `notifyMessage` 那一支**
  （`CNXN, OPEN, OKAY, RQID`）—— 漏了的话它会掉进 `dispatchWrite` 的流数据路径，
  被当成"未注册流的杂散 payload"丢掉，手机**永远收不到**（单测专门盯这条）。
- 手机端 `AccessorySession`：`Command.RQID` → `CaptureController.requestKeyFrame()`
  → `VirtualDisplayEncoder.requestKeyFrameForHost()`：
  - 先 `gopGate.arm()`（在 IDR 到来之前不推 P 帧）；
  - 再 `setParameters(Bundle{ PARAMETER_KEY_REQUEST_SYNC_FRAME = 1 })` 立刻要一个 IDR。
- 宿主 `HostSession.rebuildDecoder()` 成功后：**arm 本地 `GopTailGate` + 发 RQID**。
  消费线程在 `d.feed(frame)` **之前**过门控，缺 IDR 的 P 帧一律不进解码器。

**★ 为什么绝不能走 `resendStartup()`**：那条路会**重发流头 + CONFIG**，
而这里链路与流头都还有效，多发一份流头会把宿主解码器搞乱（10.17 已踩过同类坑）。
必须是一条"只影响关键帧节奏、不碰流头"的窄通道。

**双门控的分工**：

| 位置 | 作用 | 兜底什么 |
| --- | --- | --- |
| 手机端 `gopGate` | **不推**缺 IDR 的 P 帧（省带宽） | 正常路径 |
| 宿主 `resumeGate` | 即使 P 帧到了也**不喂**解码器（不花屏/不报错） | 手机端是旧版本 App、或 RQID 在 USB FIFO 里丢了 |

两边都是 `GopTailGate`（600ms 超时兜底）⇒ 最坏情况是短暂花屏 600ms，
而不是黑屏 3 秒。计数 `resumeTailDropped` 进 `STATS`。

单测 +4（`:protocol:test` 262 → **266**）：wire 值 = ASCII 小端、magic 规则一致、
编解码往返（过 magic/长度/checksum 三道校验）、端到端投递（手机端 3s 内收到）、
三条连发不被当流数据丢弃。

**★ 真机验证（宿主 034 + HONOR，高清 872x1920，两端 Debug 装机实测）**：

宿主侧（`UAV-Host` / `UAV-Video`）：
```
surface destroyed → Surface 已销毁：已释放解码器、停止渲染（链路保持）
surface created  → Surface 已恢复：准备用缓存的 CONFIG 重建解码器
decoder configured 872x1920 (csd-0 = 32B 整体注入)
解码器已在新 Surface 上重建（872x1920，csd=32B）—— 已 arm 等 IDR 门控并向手机请求关键帧（RQID 已发出=true）
```
手机侧（同一次，`UAV-Accessory` / `UAV-Video`）：
```
08:37:40.635 RQID received：宿主请求关键帧（切后台恢复渲染）
08:37:40.643 宿主请求关键帧：已 arm GOP 门控，requestKeyFrame=true
08:37:40.687 整 GOP 尾部丢弃：等 IDR 期间丢掉 2 帧，拿到关键帧后恢复推流（872x1920）
```

| 次数 | 手机收到 RQID | 恢复推流 | 耗时 |
| --- | --- | --- | --- |
| 1（屏幕熄灭→亮起） | 40.635 | 40.687 | **52ms** |
| 2（屏幕再翻转） | 43.746 | 43.788 | **42ms** |
| 3（**用户按 Home → 回前台**） | 20.430 | 20.473 | **43ms** |

宿主 `STATS` 里 `resumeTailDropped=2`（本地门控确实挡掉了 2 帧无主 P 帧，
说明这道兜底也在工作），恢复后 `decoded` 持续递增、`gateDropped=0`、无 FATAL。

⇒ **黑屏从"最长 3 秒"降到"约 40~50ms"（1~2 帧）**，且不产生花屏。

### 10.22 退到后台暂停声音

**原先**：音频消费线程**刻意**不随 Surface 停（注释里写着"音频与显示无关，切后台时声音继续，
像普通播放器"）。现在改为**后台静音**。

**跟着 Surface 生命周期走，而不是 `onPause`**：`surfaceDestroyed` 是"真的没画面可画了"这个
事实的**权威信号**，而且它已经在驱动 `rendering`；再挂一份 `onPause` 就会出现
"有时暂停、有时不暂停"的双状态。代价是**屏幕熄灭也会静音** —— 这与系统行为一致，
且比"锁屏后手机声音继续外放"更符合预期。

**改动**：

- `AudioPlayer` 新增 `pauseForBackground()` / `resumeFromBackground()` / `isPaused`：
  - **用 `pause()` 而非 `release()`** —— `MediaCodec`（AAC）没有视频那种
    "output surface 不能改绑"的限制，配置还在，不值得为静音重建整条输出。
  - 恢复时 **`flush()`** —— 暂停期间上游一直在解码/送数据，`AudioTrack` 里可能压着
    几十毫秒的**旧** PCM；直接 `play()` 会先播出去（能听出一小段延迟）。`flush()` 顺带把
    `playbackHeadPosition` 归零，与下面重设起点配套。
  - 恢复时**重锚 `playbackStartedAtNanos`** —— A/V 同步把"音频已播到哪一刻"算成
    `起点 + 播放头帧数/采样率`。后台那几十秒里手机**一直在采集编码**，回前台后新帧的 pts
    已经跳到当前时刻，而播放头还停在暂停处 ⇒ 两者错开几十秒，门控会把每帧都判成"早几十秒"。
- `HostSession`：新增 `audioPaused`（与 `rendering` **分开记** —— 前者是"不喂解码器"，
  后者是"不喂音频"，将来要只静音不黑屏时改一处即可）；
  `suspendRendering()`/`resumeRendering()` 里驱动暂停与恢复；
  `audioLoop` 在暂停期间**只消费不喂**；恢复后重置 `AvSyncGate` 学习状态
  （与"播放头恢复前进"时已有的处理一致）。
- `stats()`/`statsCompact()` 增加 `audioPaused`；UI 在暂停时显示「已暂停（宿主在后台）」
  而不是报**暂停前的残留电平**（那会让人以为还在放声）。

**★ 两条关键约束（都是"看起来能省掉、实际会出事"的）**：

1. **暂停期间必须停止喂帧。** `AudioTrack` 暂停后不再消费缓冲，而 `feed()` 里是
   `write(..., WRITE_BLOCKING)` —— 继续喂，缓冲写满后**音频消费线程会被永久阻塞**。
   调用方（`audioLoop`）拦一道，`feed()` 内部再兜一道，防止将来漏改。
2. **必须先置 `paused` 标志、再调 `pause()`。** 反过来的话，写线程可能正好在 `write()`
   中途撞上 track 变暂停 → 返回 0 → 走进 warn 分支。真机上每次切后台必现一条 warn，
   纯噪音。（返回错误码而不是阻塞，正是靠这条顺序保证的。）

**真机验证（宿主 034 + HONOR，48000Hz/2ch）**：

| 场景 | 观测 | 判读 |
| --- | --- | --- |
| 前台 | `frames=1352` 递增，电平 -18dBFS | 正常有声 |
| **长暂停 22s** | 连续 5 条 STATS 全部 `frames=3142 pcm=12568KB` | **一字节 PCM 都没再写出 ⇒ 真的静音了** |
| 回前台 | `frames` 3142 → **3575**，电平 -10.4dBFS | 线程没被钉死，恢复出声 |
| 3 轮快速切后台 | 暂停/恢复日志严格一一配对，**零 warn、零 FATAL** | 幂等 |

A/V 侧：恢复后 `offset` 收敛到 **-130ms** 稳态、`drop=0`、`hold` 0.35%，
无异常丢帧（负偏移 = 视频略早于音频，是 `flush` + 补偿重置带来的一次性暂态，
EMA 会吃掉，不影响稳定性）。

### B.1 `libaoahid`（AOA HID 的**同题**参考实现，强烈建议先读它的 `docs/PROFILES.md`）

**https://github.com/nemarpuc/libaoahid** ｜ MIT ｜ C++20 + 稳定的 C ABI，经 **libusb** 驱动

> "C++20 host library and C ABI for sending HID input (keyboard, mouse, gamepad,
> touchscreen, pen) to Android over USB via AOA 2.0 — **no root, no ADB, no accessibility
> service** required on the device."

**它与本项目的关系**：解决**同一个问题**（"让宿主端把输入注入到手机"），只是宿主换成了 PC、
语言换成了 C++/libusb；我们这边宿主是**另一台安卓手机**、走 Java `UsbDeviceConnection`。
所以**不能直接当依赖**，但**描述符与协议层的结论可以整段搬**。

**我们实际拿走的东西**：

| 拿走的东西 | 用在哪 |
| --- | --- |
| `docs/PROFILES.md` 的**多点触摸 profile**：N 个*独立* Finger collection、`Contact Count` 放在最后且 = **帧内记录数**、必须**显式发 `Tip=0`**（默认 `hid-multitouch` 不把"没出现的触点"当抬起） | 10.12 多点触摸（前两次描述符都写错，靠这份规格才对） |
| 描述符**按 64 字节分块**发送（超 EP0 包长） | 10.9 的 `AoaHid.chunkDescriptor`（实测 334B → 6 块） |
| "**没有退出 accessory 模式的 API**，只能拔线或 `svc usb setFunctions`" | 与我们的实测**完全一致**（10.10 的重连死锁）：互相印证 |
| 只用 AOA **51/52/53**、**从不用 58（audio）** | 我们的握手裁剪决定（4.2） |
| 报告状态机必须维护（触点、接触计数、Tip=0 释放记录） | `MultiTouchTracker` + 每帧全量槽位 |

**已在他们真机上验证过的 profile**（可作为"这条路本身可行"的证据）：
touchscreen 多点触摸、touchpad、keyboard(NKRO)、mouse、gamepad、媒体键、pen、digitizer；
raw report 尚未验证。（机型：Samsung Galaxy Tab S11、POCO F6 Pro）

**已知限制（对我们的启发）**：

- 传输被 STALL 后**由调用方重发**，库从不重试 —— 与我们"出错即作废注册、等重建"的思路一致；
- **Windows 上需用 Zadig 把整机驱动换成 WinUSB**，且**同一设备同时只能被一个进程打开**
  （`adb` 与它不能共存）—— 又一次印证"设备是独占的"，我们踩的 fd 泄漏（10.8）正是这条的另一种表现；
- macOS 未真机验证；2.0.0 的十条假设**全部未在硬件上验证**；
- ⚠️ 仓库自述**大部分代码/测试/文档由 AI 编码助手编写**（架构、硬件验证与审查由人做）
  → 引用其结论时按"参考实现"看待，关键点仍要自己在真机复核（我们就是这么做的）。
