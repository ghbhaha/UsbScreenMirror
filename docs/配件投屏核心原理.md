# 07 - USB Accessory（AOAv2）投屏核心原理

> 本方案的核心思路：**一台 Android 设备（宿主）通过 USB Accessory 协议（AOAv2）让另一台 Android 设备（手机）切换为"配件"角色，反向为宿主工作**——手机本地采集屏幕并编码，经 USB 直接把音视频流推给宿主，全程无需 USB 调试、无需 adb 授权、无需向手机推送任何服务端。

## 1. 一图总览

```
┌─ 宿主 App（USB Host 侧）────────────────┐        ┌─ 手机端配套 App（USB Device→Accessory）─┐
│  投屏页面（SurfaceView 渲染）            │        │  采集服务（MediaProjection 前台服务）    │
│  ├─ AOAv2 握手（control transfer 52/53）─┼───────►│  （系统层切换为 Accessory 模式）         │
│  ├─ 应用层传输（ADB 风格报文）            │        │  同款报文传输层                          │
│  │   └─ OPEN("newScreen 参数") ─────────┼───────►│  解析参数 → 启动采集/编码                │
│  ├─ 视频流 ◄════ H.264 帧流 ═════════════╪════════│  MediaProjection → MediaCodec 编码      │
│  ├─ 音频流 ◄════ PCM / 编码帧 ═══════════╪════════│  AudioRecord 采集 → 直通/编码            │
│  ├─ 解码器 → Surface 渲染                │        │  旋转：resize 虚拟屏，不重建             │
│  └─ HID 鼠标报告（control transfer 57）──┼───────►│  系统层指针注入（不经应用层）            │
└─────────────────────────────────────────┘        └─────────────────────────────────────────┘
```

与标准 ADB 投屏（scrcpy 类）方案的关键差异：

| 对比项 | ADB over OTG 方案 | 本方案（AOAv2） |
| --- | --- | --- |
| 手机端前提 | 开 USB 调试 + 弹窗授权 | 仅需安装配套 App |
| 认证 | RSA 密钥协商 | **无** |
| 推送服务端 | sync 推送 jar + shell 启动 | 编码逻辑内嵌手机 App，**零推送** |
| 通道建立 | adb reverse + TCP | 一条 OPEN 命令复用多条流 |
| 屏幕尺寸来源 | shell `wm size` | CNXN 握手帧携带 |
| 输入注入 | scrcpy 控制消息 → InputManager | **HID 报告 → 系统层注入** |

核心动机：目标场景是"手机插上就能投"，不能依赖用户打开开发者选项。AOAv2 是 Android 官方 USB 配件协议（Android 3.1+，HID 部分 4.3+），手机切换到配件模式后不需要任何用户态授权。

## 2. AOAv2 握手原理

### 2.1 四步握手（宿主 → 手机系统层，均为 USB control transfer）

1. **探测**（request 51，GET_PROTOCOL）：查询手机支持的配件协议版本。
2. **自报身份**（request 52，SEND_STRING ×6，index 0~5）：依次发送 manufacturer、model、description、version、**URI**、serial 六段字符串。URI 用于引导装机——手机识别到该配件后可跳转下载配套 App。
3. **启动配件模式**（request 53，START_ACCESSORY）：手机 USB 栈**重新枚举**，PID 变为 `0x2D00`（配件）/ `0x2D01`（配件+ADB）。
4. **（AOAv2 扩展）注册 HID**（request 54 REGISTER_HID / 56 SET_HID_REPORT）：挂载自定义 HID 设备描述符，供后续系统级输入注入（见第 6 节）。

### 2.2 双端识别机制

- **手机侧**：重枚举后系统广播 `USB_ACCESSORY_ATTACHED`，注册了对应 intent-filter（meta-data 指向 `usb-accessory` 过滤器，按 manufacturer/model 匹配）的配套 App 被系统拉起或弹窗询问。
- **宿主侧**：手机以新 PID 出现后，`UsbManager` 设备列表中按 **PID 0x2D00/0x2D01** 识别配件（不要按 interface class 识别——配件接口与 adb 接口的 class/subclass/protocol 取值相同，均为 255/66/1）。
- **插线即达**：宿主 App 的投屏 Activity 可注册 `USB_DEVICE_ATTACHED` intent-filter。要点：过滤器需用**空匹配**（`<usb-device />`）——手机处于"仅充电"模式时没有任何 MTP 接口（class 6 匹配不到），空过滤才能像系统文件管理器一样覆盖所有插线场景；经此入口启动时系统还会自动授予该设备 USB 权限，省一次授权弹窗。代价是插入任何 USB 设备都会弹打开选择框，专用设备可接受。

## 3. 应用层传输协议（简化版 ADB）

两端共用一套 **ADB 风格报文格式**：24 字节小端头 + payload。

```
struct message {
    unsigned command;       // 命令字：CNXN/AUTH/OPEN/OKAY/CLSE/WRTE/...
    unsigned arg0;          // 参数 0
    unsigned arg1;          // 参数 1
    unsigned data_length;   // payload 长度
    unsigned data_check;    // payload 校验和（逐字节无符号累加）
    unsigned magic;         // command ^ 0xffffffff
};
```

复用 ADB 报文的好处：有成熟的状态机可参考（OPEN/OKAY/WRTE/CLSE 流管理）、抓包工具链通用。在此基础上做三点裁剪与定制：

1. **砍掉 AUTH/STLS**：配件模式物理上即认证（线在手里），无密钥协商。
2. **CNXN payload 携带屏幕尺寸**：标准 ADB 的 CNXN payload 是固定字符串；本方案把手机屏幕宽高（小端 8 字节）放进 CNXN payload——因为不走 ADB，宿主没有 `wm size` 可用，屏幕尺寸必须由握手帧带过来。
3. **一条 OPEN 复用多条流**：OPEN 的服务名形如 `newScreen<videoId>:<audioId> <参数键值对>`（参数含 max_size、码率、fps 等 scrcpy 风格选项），一次握手得到 control / video / audio 三条流（下标约定 `[0]=control、[1]=video、[2]=audio`）。标准 ADB 每条流要独立 OPEN。

### 3.1 性能关键优化

| 优化 | 做法 | 收益 |
| --- | --- | --- |
| 跳过停等 | 不逐包收发 OKAY（noWait） | 消除每包一个 RTT 的串行等待 |
| 合并写 | 帧元数据(12B)+帧数据合并为一次 write | 省一次完整报文封装（头+checksum） |
| 大缓冲 | 流读缓冲 ≥32KB；写超时放大到 5s | 大帧不拆包断流 |
| 带偏移写 | write(offset, length) 重载 | 避免合并前的数组拷贝 |

### 3.2 稳健性关键点

- **ZLP 容错**：当发送方 payload 恰好是 USB 最大包长（512B）整数倍时，协议要求补发零长包（ZLP）。该 ZLP 会让接收端下一次排队的读请求以 **0 字节完成**——必须识别并丢弃重排，否则空缓冲直接解析会越界（典型症状：投屏间歇性断流）。
- **读写线程模型**：读侧单线程状态机（解析报文→按命令字分发到对应流），写侧 HandlerThread 串行化或 bulkTransfer 加锁；流的读队列用 `ReentrantLock/Condition` 实现阻塞凑满读。
- **超时**：所有阻塞等待（OPEN 应答、写传输）必须有超时，否则对端授权被拒/被杀时本端线程永久挂起。

## 4. 手机端：采集与编码

配套 App 以 `mediaProjection` 前台服务装配两条管线：

### 4.1 视频：MediaProjection → H.264

```
MediaProjection.createVirtualDisplay(name, w, h, dpi, AUTO_MIRROR, encoderInputSurface)
        │
        ▼
MediaCodec（surface 输入模式，H.264，I 帧间隔 10s，repeat-PS 100ms）
        │  每帧附带方向标志（竖屏/横屏）
        ▼
video 流
```

- 虚拟屏尺寸 = 按 maxSize 等比缩放（scrcpy 同款算法：对齐 8 字节、短边等比）。
- `KEY_REPEAT_PREVIOUS_FRAME_AFTER=100ms` 保证静止画面持续送帧，链路不空转、首帧必达。

### 4.2 旋转处理（核心机制）

**目标：旋转不重建虚拟屏，无黑屏间隙。**

```
旋转事件（RotationWatcher 回调，仅置标志）
    → 编码循环在安全点跳出内层
    → virtualDisplay.resize(新宽, 新高, dpi)          ← 同一个虚拟屏实例
    → MediaCodec 重新 configure(新尺寸) + createInputSurface + setSurface
    → 新 SPS/PPS CONFIG 帧（携带新方向标志）发出
```

**为什么必须"三件套"配套**：

- MediaCodec surface 输入模式的**输入缓冲几何在 configure 时固定**——只 resize 虚拟屏，画面会被拉伸到旧比例、分辨率不变；
- 不重建编码器就无法改变输出分辨率；
- 但完整重建虚拟屏（MediaProjection 资源）开销大、中断长。

因此 `resize（调整虚拟屏尺寸）+ setSurface（切换输出）+ 编码器重配置`配套执行：虚拟屏实例全程复用，旋转间隙只剩几十毫秒的编码器重配置，且重配置必然产生新 SPS/PPS CONFIG 帧，天然通知了接收端。

### 4.3 音频

- `AudioRecord`（MIC 或 REMOTE_SUBMIX 内录）采集 48kHz/16bit/立体声。
- **PCM（RAW）没有 MediaCodec 实现**：`createEncoderByType("audio/raw")` 会抛 `NAME_NOT_FOUND` 崩溃——RAW 必须走直通记录器直接发帧；AAC/OPUS/FLAC 才走编码器。协议层用 4 字节 ASCII codecId 区分（`raw`/`aac`/`opus`/`flac`），接收端按头自动分发。
- Android 11 以下无回放采集能力，应发送"禁流"标记优雅降级，而非崩溃。

## 5. 宿主端：接收与解码

1. **流头**（12B：codecId + width + height）每条流只读一次；**帧元数据**（8B pts+flags + 4B size）+ payload 循环读取。
2. **ptsAndFlags 高位复用为标志位**：如 `1<<63` = CONFIG（含方向信息）、`1<<62` = 关键帧。标准帧的 PTS 有效位远低于 61，不会冲突。
3. **CONFIG 帧驱动一切**：抽 SPS/PPS（H.264 码流中 `00 00 00 01` 分隔的前后段）→ 更新本地布局尺寸 → 解码器 configure（CSD 注入 csd-0/csd-1）。旋转后编码器重发 CONFIG，宿主借此感知新方向——与手机端 resize 机制闭环。
4. 解码输出直接 `releaseOutputBuffer(index, true)` 渲染到 SurfaceView 的 Surface；音频按 codecId 分发：PCM 直写 AudioTrack，压缩格式走 MediaCodec。
5. **解析缓冲按流隔离**（音/视频线程各自持有 header/meta 缓冲），避免跨线程数据竞争。

## 6. 反向控制：HID 鼠标

输入控制不走应用层控制通道，而是 **AOAv2 的 HID 注册机制**，直接在系统层注入：

1. request 54（REGISTER_HID）+ request 56（SET_HID_EVENT_REPORT）：注册自定义鼠标 HID 描述符（5 按键 + X/Y 相对位移 + 滚轮）。
2. 宿主捕获本机鼠标（`requestPointerCapture` + `OnCapturedPointerListener`），每个事件经 request 57 发送 **4 字节 HID 报告**：`[按键位掩码, dX(相对位移), dY, 滚轮]`。
3. 手机系统把它当成真实 USB 鼠标处理——**不经过任何应用层**，无需采集端配合，也无需任何权限。

取舍：HID 是相对位移 + 滚轮，无多点触摸/键盘/剪贴板能力；若需要完整输入，应启用控制流走 scrcpy 风格控制消息（INJECT_TOUCH_EVENT 等，服务端经 InputManager 注入）。

## 7. 端到端时序

```
宿主 App                              手机配套 App
 │ ── AOAv2: 52×6 + 53 ───────────────►│ （系统重枚举 PID=0x2D00）
 │ ◄─ USB_ACCESSORY_ATTACHED 拉起 App
 │ ── CNXN ───────────────────────────►│
 │ ◄─ CNXN(payload=宽,高) ──────────── │
 │ ── OPEN("newScreen v:a 参数") ─────►│ 解析参数 → 发起录屏授权
 │    （手机弹 MediaProjection/录音授权，授权后）
 │ ◄─ OKAY（三条流就绪）────────────── │ 启动采集/编码
 │ ◄══ 流头(12B) + CONFIG(SPS/PPS) ═══ │
 │ ◄══ H.264 帧 ══════════════════════│
 │ ◄══ 4B codecId + 音频帧 ═══════════│
 │ ── HID 鼠标报告(57) ───────────────►│ 系统注入
 │      ……旋转时……
 │ ◄══ 新 CONFIG（方向标志翻转）══════ │ resize+setSurface，虚拟屏不重建
```

## 8. 专项分析：流程、稳定性、速度

### 8.1 流程（连接 / 重连）

**建议具备的流程要素**：

| 环节 | 要点 |
| --- | --- |
| 插线即达 | 宿主 Activity 注册 `USB_DEVICE_ATTACHED`（空过滤）+ "始终"默认；系统自动授权 |
| 权限授予 | `requestPermission` → 授权回调中重入枚举；无权限不得静默失败 |
| 页面已开时插线 | `singleTask` + `onNewIntent` 复用实例重新枚举 |
| 断连感知 | DETACHED 广播 + 读写异常双路径，统一收敛到 `onError`，释放 HID 与流资源 |

**常见流程缺陷与对策**：

1. **无自动重连**：断开后需重新插拔。建议 `onError` 后带退避延时自动重试枚举（限次数）。
2. **OPEN 应答无限等待**：手机端授权被拒/被杀时宿主线程挂起。所有 `wait()` 必须带超时并转为 `onError`。
3. **授权失败无应答**：手机端录屏授权失败应向宿主回 CLSE（或禁流标记），让宿主走断连流程，而不是互相干等。
4. **粗暴退出**：手机端断开时避免直接杀进程，应停服务、释放 MediaProjection，仅异常路径才自杀退出。

### 8.2 稳定性

**高频踩坑清单**（本方案实践中真实出现过的问题）：

| 问题 | 根因 | 对策 |
| --- | --- | --- |
| 采集端进程崩溃 | RAW 音频误入编码器，`audio/raw` 无 MediaCodec 实现 | RAW 分流到直通记录器 |
| 接收端 NPE | "重新配置"标志吞掉首帧 CONFIG，用空参数 configure 解码器 | CONFIG 帧永远重新解析 SPS/PPS + 判空防护 |
| 投屏间歇断流 | USB ZLP 使读请求 0 字节完成，空缓冲越界 | 读请求循环凑满，0 字节完成丢弃重排 |
| 握手静默失败 | 无 USB 权限时 `openDevice()` 返回 null 被忽略 | `hasPermission` 门控 + 授权回调重入 |
| 旋转黑屏/比例错 | 重建虚拟屏开销大；只 resize 则画面拉伸 | resize + setSurface + 编码器重配置三件套 |

**建议的加固项**：

1. **流具名化**：不要用数组下标取流（`[1]`/`[2]`），一旦流顺序因重连/失败重排即音画错位；OPEN 应答应携带流类型映射。
2. **流健康监测**：USB 半插（供电正常、数据断）两端都无感知，画面冻结。建议控制流周期 ping，或把写超时异常明确转为重连流程。
3. **编码器死亡上报**：采集端编码 fatal 后应向宿主回 CLSE/禁流标记，否则宿主画面冻结而不知情。
4. **跨线程可见性**：UI 线程写、解码线程读的字段（Surface、屏幕尺寸）用 `volatile`/原子类保证 happens-before。
5. **优雅降级提示**：不支持音频回放的老设备发禁流标记，接收端 UI 明示"该设备不支持音频"。

### 8.3 速度

**链路延迟构成**（估算）：采集合成 ~10-30ms → 编码 ~20-50ms → USB bulk 传输（32KB 块约 1ms 级）→ 解码 ~20-40ms → 渲染。端到端约 **80-150ms**；瓶颈在编码/解码管线，USB 带宽余量极大。

**已具备的优化**：见 3.1（合并写 / noWait / 大缓冲 / 带偏移写）+ 4.2（旋转零重建）+ 4.1（持续送帧）。

**参数调优参考**：

| 参数 | 典型值 | 评估 |
| --- | --- | --- |
| max_size | 1600 | 两端一致时无二次缩放；性能弱的宿主可降 |
| video_bit_rate | 6 Mbps | USB2 实际 ~30MB/s，余量巨大；求清晰度可提至 12-20 Mbps |
| audio_bit_rate | 64 kbps | 对 PCM 直通无意义（固定 1.5 Mbps）；切 AAC 后才有意义 |
| I 帧间隔 | 10 s | 花屏后最长 10s 才能自愈；偶发花屏场景降到 2-5s |
| max_fps | 30 | 编码由内容驱动，静止画面不耗带宽 |

**进一步方向**：帧缓冲预分配按最大关键帧估算（1600p 关键帧可超 64KB，避免运行时扩容 GC 峰值）；API 30+ 可评估 `KEY_LOW_LATENCY`；禁用自适应抖动缓冲以降低音频延迟。

## 9. 设计权衡备忘

- **无认证是特性也是风险**：安全性完全依赖物理接触（OTG 线在手），封闭场景可接受，公开产品需重新评估。
- **免调试是核心价值**：牺牲了 adb 的通用能力（shell/端口转发/文件推送），换来零配置开箱即投。
- **协议与 scrcpy 生态对齐**：报文复用 ADB 格式、流协议对齐 scrcpy 传输格式（含方向标志扩展），可复用其解码/解析实现与抓包工具。
- **系统层输入注入**：HID 机制绕开应用层，天然免权限，但能力上限是"相对位移鼠标"；完整输入能力需控制通道 + 系统注入接口（需要系统签名或 root 环境）。
