# 排错手册

面向「插上线但画面没出来」的场景。配套文档：

- `配件投屏核心原理.md` —— 为什么这样做（AOA / 协议 / 采集链路）
- `实施计划.md` —— 怎么做的（冻结清单 v2、进度、10.4 真机实测记录）

> **本手册的所有结论都来自真机实测**（宿主 BOE P40UCH / Android 14，配件 HONOR MAA-AN10 / Android 16），
> 不是推测。凡是标注「实测」的条目都附了当时的原始现象。

## 0. 先确认你用的是哪个包

**这一步不看会浪费很多时间**：应用了 release 调试门控（计划 5.2）之后，两个包的**行为不同**。

| | `-debug.apk` | `-release.apk` |
| --- | --- | --- |
| `.uav` 回放（按钮 + `--es replay_path`） | ✅ 可用 | ❌ 按钮不显示，extra 被忽略 |
| `--ez scan` / `--ez force_handshake` | ✅ 可用 | ❌ 被忽略 |
| 手机端抓流落盘（`uav-dump.uav`） | ✅ 写出 | ❌ **不落盘**（避免持续写 28MB+） |
| 周期 `STATS` 日志（每 5 秒） | ✅ 打印 | ❌ 关闭 |

**排错必须用 debug 包。** release 包里「回放按钮不见了」不是 bug，是设计。
若在 release 上排错，`adb shell am start ... --es replay_path ...` 会被忽略——
它不会进入回放，而是继续走正常 USB 路径，很容易误判成"回放入口坏了"。

**判断是不是门控在起作用**，看这两条日志（它们让门控在运行时自证）：

```
W/UAV-Host:      release 构建：调试入口已关闭，忽略 intent extra
I/UAV-Accessory: release 构建：抓流落盘已关闭，只转发不落盘
```

宿主那条**只在真的传了调试 extra 时**才打印（不吵）；配件那条在每次建立链路时打印一次。
看到它们 = 门控生效，不用再怀疑"是不是入口写坏了"。

包体路径：

```
app-host/build/outputs/apk/debug/app-host-debug.apk
app-accessory/build/outputs/apk/debug/app-accessory-debug.apk
```

## 1. 二分定位法：先把问题域切两半

这是本项目最有效的排错手段，**先做这一步再查任何细节**。

趁链路还好的时候，手机端会自动抓一份 `.uav`；把这份抓流喂给宿主回放：

```bash
# 1) 从手机取回抓流（★ 必须用 cat 直取，别用 adb pull —— 见第 4 节）
adb -s <acc> exec-out "cat /sdcard/Android/data/com.uav.accessory/files/uav-dump.uav" > dump.uav

# 2) 灌进宿主 App 私有目录
adb -s <host> push dump.uav /data/local/tmp/replay.uav
adb -s <host> shell "run-as com.uav.host sh -c 'cp /data/local/tmp/replay.uav files/replay.uav'"

# 3) 触发回放（跳过整个 USB 与握手）
adb -s <host> shell am start -n com.uav.host/.HostActivity \
  --es replay_path /data/data/com.uav.host/files/replay.uav
```

判定：

| 回放结果 | 结论 | 下一步 |
| --- | --- | --- |
| **能出画面** | USB 握手 / 协议 / 传输**已通**，问题全在实时链路（超时、背压、线程、拔插） | 查第 2 节里与「链路/超时」相关的行 |
| **出不了画面** | 问题在**协议解析或解码器配置**，与 USB 无关 | 查第 2 节里与「流头/解码器」相关的行；也可直接跑 `./gradlew :protocol:test` |

为什么这么切最省事：`.uav` 就是**原样的报文流**（24B 头 + payload 逐条拼接，零封装），
实时路径与回放路径**共用同一套 `AdbMessage` 解析代码**，所以这两半是干净正交的。

> 前提：手机端抓流落盘要开着（debug 包默认开）。抓流是**全量**写出的——
> 实测 110 秒 ≈ 28 MB，长时录制注意空间。

## 2. 症状 → 根因 → 处置 速查表

按「你在哪一侧看到什么」查。带 ★ 的是实测踩过的。

### 2.1 宿主侧

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| 日志停在不出现 `AOAv2 version=2` | `openDevice()` 返回 null（无 USB 权限） | 看是否弹了授权框；`dumpsys usb` 检查设备是否还在 |
| ★ `等待重枚举超时（5000ms）` | ① 手机没切进配件模式 ② 手机**本来就在**配件模式（`START_ACCESSORY` 不会重新枚举） ③ OTG 链路瞬时不稳 | 先试 **重插拔**（实测最有效）；再用 `--ez force_handshake true` 强制重握手；仍不行查手机侧 2.2 |
| ★ 收到 attach 后无任何反应 | 部分宿主（BOE P40UCH）重枚举后**只发 DETACHED 不发 ATTACHED** | 已内置前台轮询兜底（2s/次）。若仍不动，点界面 **Scan / Retry** |
| `openDevice 返回 null` / `openAccessory 返回 null` | 授权失败，或配件被**别的宿主 App** 占用 | 见 2.3「身份被顶掉」 |
| ★ `首个 payload 不是合法流头(xxxB)` | 上一会话残留在 USB FIFO 里的帧数据被当成流头 | **这是设计内的自愈**：宿主会丢弃杂散 payload 并继续等真流头。同一句**只出现一次**属正常；反复刷说明手机端在乱发，查 2.2 |
| ★ `StreamHeader(乱码 8x466)` 之类 | 同上，但发生在旧版本（流头校验未加严格版） | 确认用的是最新包；流头校验现已要求「可打印 ASCII + 尺寸 16..8192」 |
| `尚未收到 CONFIG 帧，先丢弃普通帧` | 手机端还没产出 `INFO_OUTPUT_FORMAT_CHANGED` | 正常会短暂出现。持续不消失 ⇒ 编码器没起来，查 2.2 |
| `Surface 尚未就绪，无法配置解码器` | 回放时文件是**秒读**的，CONFIG 比 `surfaceCreated` 先到 | 已修（`awaitSurface` 等 surface）。若仍出现，检查 SurfaceView 是否被遮挡/未 attach |
| `已断开：...` | 设备拔出，或读写异常 | 与读写异常统一收敛路径，属正常上报 |

### 2.2 配件（手机）侧

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| ★ `dumpsys usb` 里身份为 `manufacturer=U model=u version=1`（**只剩首字符**） | `SEND_STRING` 编码错误（用 UTF-16LE 而非 UTF-8），AOSP 按 `\u0000` 切分字节串 | **必须 UTF-8 + 单个 `\0`**。这是历史红线，已修；若复现说明编码被改回去了，见 3.1 |
| 身份正确但系统不派发 `USB_ACCESSORY_ATTACHED` | 身份与 `accessory_filter.xml` 不匹配 | 两端三处必须逐字一致：`manufacturer=UAV` / `model=usbscreen` / `version=1.0`（见 3.1 的镜像表） |
| ★ `openAccessory 抛异常: User has not given <uid> permission to accessory UsbAccessory[Ewin/...]` | 手机上这个配件是**上一次别的宿主 App 留下的孤立链路**，我们的 App 从没收到过派发 | 让手机**切回普通模式**再走一遍完整握手，见 2.3 |
| `录屏授权被拒绝 —— 无法投屏` | 用户点了拒绝 | 点界面 **Grant** 重新授权；Android 14+ 每次投屏都要点一次，无法绕过 |
| `openAccessory 第 N 次尝试成功` | 系统派发晚于服务启动的瞬时无权限 | 正常（内置 6 次重试）。若 6 次全失败，查 2.3 |
| 画面冻结但日志正常 | 编码器死了却没上报 | 已知缺口，见 `实施计划.md` 路线图 P2「编码器死亡上报」 |
| ★ 静态画面只有 ~10 fps | **不是问题**：`KEY_REPEAT_PREVIOUS_FRAME_AFTER=100ms` 的设计效果（静止时兜底送帧、不让链路空转） | 不需要处置。要测帧率**必须让画面动起来** |

### 2.3 「配件身份被顶掉」——本机特有

**现象**：宿主能握手成功、拿到接口，但永远等不到通话（`等待手机 CNXN 超时`），
手机侧则报 `openAccessory` 无权限，且 `dumpsys usb` 显示配件身份是**别人的**。

**根因**：手机当前这个「配件态」是**别的宿主 App** 建立的。本机实测遇到过
宿主上另装了 `com.ewin.screenaccessory`（旧项目），手机上因此报 `Ewin/EwinScrcpy/0.1`。
关键约束是：**手机已经在配件模式时，`START_ACCESSORY` 不会重新枚举 USB 设备**，
也就不重新派发 intent —— 所以身份不会自动被改写，我们的手机端 App 永远不会被拉起。

**处置（按顺序试）**：

```bash
# ① 先让宿主别抢跑
adb -s <host> shell am force-stop com.uav.host

# ② 手机切回普通模式（触发 gadget 重新枚举）
adb -s <acc> shell svc usb setFunctions

# ③ 确认手机真的切回去了（应显示 mtp/adb 之类，不再是 accessory）
adb -s <acc> shell getprop sys.usb.config

# ④ 确认宿主看到了手机（VID 应为 0x339B，不是 0x18D1）
adb -s <host> shell dumpsys usb | grep -E "vendor_id|product_id"

# ⑤ 再启动宿主，让前台轮询走一次完整握手（此时才会写入 UAV/usbscreen 身份）
adb -s <host> shell am start -n com.uav.host/.HostActivity
```

或更省事的方式：`--ez force_handshake true` 强制完整重握手（debug 包），
宿主内也已内置自愈——快路径失败时自动回退重试一次。

> **防复发**：把宿主上其它抢占 USB 配件模式的项目（如 `com.ewin.screenaccessory`）卸载，
> 或在联调前先 `pm disable` 掉。

## 3. 三条必须记住的硬约束

### 3.1 配件身份有**两处**定义，改一处必须同步另一处

| 载体 | 位置 |
| --- | --- |
| 宿主发送的字符串（权威来源） | `:protocol` 的 `com.uav.protocol.AccessoryIdentity` |
| 手机端的匹配过滤器 | `app-accessory/src/main/res/xml/accessory_filter.xml` |

前者是 Kotlin 常量，后者是 XML —— **XML 无法引用 Kotlin 常量，只能手工镜像**。
参与匹配的三项必须逐字一致：`manufacturer=UAV`、`model=usbscreen`、`version=1.0`。

编码方式：**UTF-8 + 单个结尾 `\0`**。
（`SEND_STRING` 对编码错误**只返回失败、不报原因**，是本项目最隐蔽的坑，详见 3.4。）

### 3.2 端点地址不能写死

实测配件端点是 **`in=0x81` / `out=0x01`**，不是常见示例里的 `0x02`。
代码按 direction/type 遍历选定并打日志，**不要改成常量**。

### 3.3 配件接口不能按 interface class 识别

实测配件接口描述符是 `class=255 sub=255 proto=0`，与 **adb 接口完全相同**
（adb 是 `255/66/1`）。识别只能按 **PID `0x2D00` / `0x2D01`**。

### 3.4 `SEND_STRING` 报错点离根因极远（值得单独记）

编码错误时的**症状链**：

```
UTF-16LE 编码  →  手机 dumpsys 显示 manufacturer=U（只剩首字符）
               →  身份对不上 accessory_filter.xml
               →  系统不派发 USB_ACCESSORY_ATTACHED
               →  手机端拿不到权限
               →  openAccessory 返回/抛 null
               →  宿主永远等不到 CNXN，超时报错
```

**报错在"超时"，根因在"编码"**。之所以会只剩首字符：`UAV` 编成 `55 00 41 00 56 00 00 00`，
而 AOSP 按 `\u0000` 切分，读到第一个 `00` 就断了。

**自查方法**（一眼定位，不用看日志）：

```bash
adb -s <acc> shell dumpsys usb | sed -n '/current_accessory/,/}/p'
# 六个字符串都完整（UAV / usbscreen / ... / 1.0）才是对的
```

## 4. adb 操作红线（Windows + Git Bash）

这几条都实际踩过，**照抄能省很多时间**。

| 红线 | 现象 | 处置 |
| --- | --- | --- |
| **Git Bash 会改写 Android 绝对路径** | `adb push /data/local/tmp/x` 报 "1 file pushed" 但文件不在那儿；`adb pull /sdcard/...` 报 `failed to stat remote object 'D:/...'`（路径被改写成 Windows 形式） | 每次开 adb 前先 `export MSYS_NO_PATHCONV=1` |
| **`adb shell` 默认分配 PTY，会改写二进制流** | 传二进制文件被破坏 | 传二进制用 `adb shell -T`（禁 PTY） |
| **大文件用 `adb exec-out "cat ..."` 直取** | `adb pull` 受路径改写影响、且对受限目录假成功 | `adb -s <acc> exec-out "cat /sdcard/.../uav-dump.uav" > dump.uav` |
| **`/sdcard/Android/data/<pkg>/` 在 Android 11+ 对 adb shell 受限** | `push` 假成功，文件其实没进去 | 要放进 App 私有目录，用 `adb shell "run-as <pkg> sh -c 'cp /data/local/tmp/f files/'"`；或 `adb shell -T "run-as <pkg> sh -c 'cat > files/x'" < local` |
| **`am force-stop` 会让 App 进入 stopped 状态** | 此后系统**不再用隐式 intent**（如配件 attach）拉起它 ⇒ 会把「链路不通」误判成软件 bug | 调试时别随手 `force-stop` 手机端 App。要清状态就用显式启动一次：`am start -n com.uav.accessory/.ProjectionActivity` |
| **OTG 链路偶发不稳** | 出现「等待重枚举超时」，双方日志都看不出原因 | **重插拔即恢复**（实测两次都是这样好的）。连续快速切 USB 模式容易触发 |

另外：本机 `ANDROID_HOME` / `ANDROID_SDK_ROOT` 均为空，adb 要用绝对路径或在
PATH 前挂 `/d/Develop/Android/sdk/platform-tools`。

## 5. 怎么读宿主日志

排错时最省事的一条命令：

```bash
export PATH="/d/Develop/Android/sdk/platform-tools:$PATH"
export MSYS_NO_PATHCONV=1
adb -s <host> logcat -v time -s UAV-Host UAV-Video UAV-Protocol UAV-Accessory
```

**周期统计行**（debug 包每 5 秒一条，压测与判活主要看它）：

```
STATS phone=1224x2700 maxSize=1920 | msgs(r/w)=710/2
      video=avc1 872x1920 frames=706 config=1 bytes=3405509
      queue=FrameQueue(video size=0/4 dropped=0[0 nonKey/0 key])
      decoded=705 queued=706 | inputStalls=0 cfgFailures=0
      | delay avg=104.9 p50=66.9 p95=166.9 p99=424.3 max=567.8ms n=300 bad=0
      | fresh avg=68.9 p50=63.6 p95=140.2 p99=158.9 max=174.3ms n=300 bad=0
      | skew=±12ms
```

判读：

| 字段 | 健康值 | 异常含义 |
| --- | --- | --- |
| `queue size` | `0/4` 恒定 | 持续接近 4 ⇒ 消费跟不上（解码器慢/背压失效）⇒ **延迟会累积** |
| `dropped` | `0` 恒定 | `nonKey` 涨 ⇒ 网络式丢帧，画面会花；**`key` 涨 ⇒ 会花满一个 I 帧间隔（3s）** |
| `decoded` vs `queued` | 差恒为 1（正在解的那帧） | 差持续拉大 ⇒ 解码落后 |
| `inputStalls` | `0` | 涨 ⇒ 解码器饥饿（喂帧太慢或 Surface 有问题） |
| `cfgFailures` | `0` | 涨 ⇒ csd 注入失败，是否回退了起始码切分？ |
| `frames` / `config` | `config` 恒为 1 | `config` 反复涨 ⇒ 手机端在反复重配（旋转场景下才应出现） |
| `bytes` / 时间 | 静态约 10 fps、运动明显更高 | 长期不涨 ⇒ 链路卡死 |
| `delay` / `fresh` | 两者都有数、`fresh` 的 p50 更小 | 见下方「延迟三种异常写法」 |
| `skew=±Nms` | N ≤ 12 | N 很大（>50）⇒ CNXN 往返太慢，标定不可信，延迟读数仅供参考 |
| `sizeChanges=N`（在 `msgs(r/w)` 之后） | 旋转过几次就是几 | **手机旋转后它不动** ⇒ 手机端根本没上报旋转（先查手机是否**开了自动旋转**） |
| `stray=N` | 不出现 | 出现 ⇒ 链路上有杂散字节（上一次会话残留），偶发正常、持续出现要查 |

**延迟那一栏的三种异常写法**：

| 写法 | 含义 |
| --- | --- |
| `delay=(未标定：对端未带时钟读数)` | 手机端是**旧版本**（CNXN payload 只有 8B），或本次没走到 CNXN 交换 |
| `delay=(回放，非实时链路)` | 回放模式没有对端时钟可标定，本来就不测 |
| `delay` 的 p50 明显大于 `fresh` 的 | **画面基本静止**：编码器在按 `repeat-previous-frame-after=100ms` 重复送出上一帧，它们的 PTS 停在旧值上。**这时看 `fresh` 才准** |

> `delay`（全量）与 `fresh`（仅 PTS 间隔 < 50ms 的连续帧）是两个口径：
> 前者用于观察与定位，**后者才代表观感**。实测静止时两者差约 70ms，运动时基本重合。
> 完整方法与数据见 `docs/实施计划.md` 10.6。

> `frames` **只算媒体帧**，CONFIG 帧单独走 `config`；`bytes` 是链路口径（含 CONFIG）。
> 这是刻意区分的——把 CONFIG 算作帧会让帧率统计系统性偏大。

## 6. 一句话总结的排查顺序

1. **看是哪个包**（release 没有回放/抓流/日志，别在那儿排错）
2. **跑一次回放**，把问题切成「USB/协议」或「解码/渲染」两半
3. **看手机 `dumpsys usb` 的身份**，六个字符串是否完整（3.4 的自查）
4. **看宿主 `STATS` 行**，`queue`/`dropped`/`stalls` 三个数就够判断链路健康
5. **卡住就重插拔**，然后 `--ez force_handshake true` 重走一遍完整握手
6. 仍不通 ⇒ 走第 2.3 节的「切回普通模式」流程
