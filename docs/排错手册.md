# 排错手册

面向「插上线但画面没出来」的场景。配套文档：

- `配件投屏核心原理.md` —— 为什么这样做（AOA / 协议 / 采集链路）
- `实施计划.md` —— 怎么做的（冻结清单 v2、进度、10.4 真机实测记录）

> **本手册的所有结论都来自真机实测**（宿主 BOE P40UCH / Android 14，配件 HONOR MAA-AN10 / Android 16），
> 不是推测。凡是标注「实测」的条目都附了当时的原始现象。

## 0. 先确认你用的是哪个包

**这一步不看会浪费很多时间**：应用了 release 调试门控（计划 5.2）之后，两个包的**行为不同**。

| | `-debug.apk` | `-release.apk` |
| --- | --- | --- |
| `.uav` 回放（按钮 + `--es replay_path`） | ✅ 可用 | ❌ 按钮不显示，extra 被忽略 |
| `--ez scan` / `--ez force_handshake` | ✅ 可用 | ❌ 被忽略 |
| 手机端抓流落盘（`uav-dump.uav`） | ✅ 写出 | ❌ **不落盘**（避免持续写 28MB+） |
| 周期 `STATS` 日志（每 5 秒） | ✅ 打印 | ❌ 关闭 |

**排错必须用 debug 包。** release 包里「回放按钮不见了」不是 bug，是设计。
若在 release 上排错，`adb shell am start ... --es replay_path ...` 会被忽略——
它不会进入回放，而是继续走正常 USB 路径，很容易误判成"回放入口坏了"。

**判断是不是门控在起作用**，看这两条日志（它们让门控在运行时自证）：

```
W/UAV-Host:      release 构建：调试入口已关闭，忽略 intent extra
I/UAV-Accessory: release 构建：抓流落盘已关闭，只转发不落盘
```

宿主那条**只在真的传了调试 extra 时**才打印（不吵）；配件那条在每次建立链路时打印一次。
看到它们 = 门控生效，不用再怀疑"是不是入口写坏了"。

包体路径：

```
app-host/build/outputs/apk/debug/app-host-debug.apk
app-accessory/build/outputs/apk/debug/app-accessory-debug.apk
```

## 1. 二分定位法：先把问题域切两半

这是本项目最有效的排错手段，**先做这一步再查任何细节**。

趁链路还好的时候，手机端会自动抓一份 `.uav`；把这份抓流喂给宿主回放：

```bash
# 1) 从手机取回抓流（★ 必须用 cat 直取，别用 adb pull —— 见第 4 节）
adb -s <acc> exec-out "cat /sdcard/Android/data/com.uav.accessory/files/uav-dump.uav" > dump.uav

# 2) 灌进宿主 App 私有目录
adb -s <host> push dump.uav /data/local/tmp/replay.uav
adb -s <host> shell "run-as com.uav.host sh -c 'cp /data/local/tmp/replay.uav files/replay.uav'"

# 3) 触发回放（跳过整个 USB 与握手）
adb -s <host> shell am start -n com.uav.host/.aoa.HostActivity \
  --es replay_path /data/data/com.uav.host/files/replay.uav
```

判定：

| 回放结果 | 结论 | 下一步 |
| --- | --- | --- |
| **能出画面** | USB 握手 / 协议 / 传输**已通**，问题全在实时链路（超时、背压、线程、拔插） | 查第 2 节里与「链路/超时」相关的行 |
| **出不了画面** | 问题在**协议解析或解码器配置**，与 USB 无关 | 查第 2 节里与「流头/解码器」相关的行；也可直接跑 `./gradlew :protocol:test` |

为什么这么切最省事：`.uav` 就是**原样的报文流**（24B 头 + payload 逐条拼接，零封装），
实时路径与回放路径**共用同一套 `AdbMessage` 解析代码**，所以这两半是干净正交的。

> 前提：手机端抓流落盘要开着（debug 包默认开）。抓流是**全量**写出的——
> 实测 110 秒 ≈ 28 MB，长时录制注意空间。

## 2. 症状 → 根因 → 处置 速查表

按「你在哪一侧看到什么」查。带 ★ 的是实测踩过的。

### 2.1 宿主侧

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| 日志停在不出现 `AOAv2 version=2` | `openDevice()` 返回 null（无 USB 权限） | 看是否弹了授权框；`dumpsys usb` 检查设备是否还在 |
| ★ `等待重枚举超时（5000ms）` | ① 手机没切进配件模式 ② 手机**本来就在**配件模式（`START_ACCESSORY` 不会重新枚举） ③ 手机端持着一个**收不到应答的配件 fd**（fd 泄漏，见 3.5）—— 这是本机实测最常见的一种 | **会自动重试，先等等**（退避 2s→30s；手机端 12s 后自释放假配件）。仍不行：`--ez force_handshake true`，再不行 `adb -s <acc> shell am force-stop com.uav.accessory`，最后才重插拔 |
| ★ 收到 attach 后无任何反应 | 部分宿主（BOE P40UCH）重枚举后**只发 DETACHED 不发 ATTACHED** | 已内置前台轮询兜底（2s/次）。若仍不动，拔插一次数据线，或点「开始投屏」（原来的 `Scan / Retry` 按钮 **2026-10-21 起已隐藏**，`--ez scan true` 仍可用） |
| `openDevice 返回 null` / `openAccessory 返回 null` | 授权失败，或配件被**别的宿主 App** 占用 | 见 2.3「身份被顶掉」 |
| ★ `首个 payload 不是合法流头(xxxB)` | 上一会话残留在 USB FIFO 里的帧数据被当成流头 | **这是设计内的自愈**：宿主会丢弃杂散 payload 并继续等真流头。同一句**只出现一次**属正常；反复刷说明手机端在乱发，查 2.2 |
| ★ `StreamHeader(乱码 8x466)` 之类 | 同上，但发生在旧版本（流头校验未加严格版） | 确认用的是最新包；流头校验现已要求「可打印 ASCII + 尺寸 16..8192」 |
| `尚未收到 CONFIG 帧，先丢弃普通帧` | 手机端还没产出 `INFO_OUTPUT_FORMAT_CHANGED` | 正常会短暂出现。持续不消失 ⇒ 编码器没起来，查 2.2 |
| `Surface 尚未就绪，无法配置解码器` | 回放时文件是**秒读**的，CONFIG 比 `surfaceCreated` 先到 | 已修（`awaitSurface` 等 surface）。若仍出现，检查 SurfaceView 是否被遮挡/未 attach |
| `已断开：...` | 设备拔出，或读写异常 | 与读写异常统一收敛路径，属正常上报 |
| ★ 插着 iPad 时 AOA 页每 2 秒刷 `设备不支持 AOAv2 (version=0)` | AOA 页把 Apple 设备（VID `0x05AC`）当成安卓手机去握手 —— 它走的是 iOS 那条 QuickTime 链路，对 AOA 请求一律不认 | **已修（2026-10-21）**：`Aoa.isApple()` 在 `pickCandidate` / `onDeviceAttached` / detach 广播四处都跳过 Apple 设备。现在插着 iPad 打开 AOA 页会停在「空闲中 —— 请把配件手机插上来」，不再空转 |
| ★ 主行「**链路出错**」+ 副行「宿主版本过低：宿主 v2 / 配件 v3」 | 配件端比宿主新 —— 新配件端可能发旧宿主解析不了的报文，所以宿主**主动拒绝**（硬约束：宿主可以更新，不能更旧） | 升级宿主 APK。**不要**靠降级配件端绕过：新功能通常先落在配件端，旧宿主读不懂 |
| ★ 主行「**对方设备无应答**」+ 面板多出「获取配套 App」按钮 | 手机已切进配件模式，但**没有任何软件接管这条管道**：没装 `com.uav.accessory`、装后被 `force-stop`、或首次插线时把系统那个"是否打开该 App 处理配件"点了否 | 装/打开配套 App。点面板上的按钮会打开 GitHub Releases；若宿主没有浏览器（盒子/车机），链接会被复制到剪贴板。⚠️ **`force-stop` 过的 App 系统不会再派发配件 intent，必须手动点一次图标** |
| 断链后**不自动恢复** | 轮询的接管条件是 `session == null`；若出错路径没清会话，就永远不会重试（10.8 之前的老毛病） | **已修**（10.8）。日志里应出现 `轮询发现设备`；重试间隔随连续失败指数退避（2s→30s） |
| ★ `链路失步[N]（bad magic…）→ 跳过 M 字节后重新同步到报文头` | 我们**不是在报文边界上**开始读的：上一次会话结束时配件端还在推流，FIFO 里留着**半条报文**；`drainStaleInput()` 只能在读超时处停下，天然可能停在报文中间 | **这是自愈日志，不是错误**（10.35）。跳过量 = 错位偏移，通常几十~几百字节。反复出现说明配件端在上一次会话结束后仍在推流（见 3.9） |
| ★ `解码器 configure 失败（尺寸 …x…, CONFIG 32B）`，同时系统日志有 `ACodec: decoder can not set low-latency to 1` | 老厂商 **legacy OMX 组件**不接受 `low-latency` 这个调优键（RK356x 的 `OMX.rk.video_decoder.avc` 返回 `UnsupportedIndex`），而 `ACodec` 把它当**致命错误** | **已修**（10.35）：带调优 configure 失败会自动去掉 `low-latency`/`priority` 重试。日志出现 `去掉 low-latency/priority 后才 configure 成功` 即为此情形 |
| `REGISTER_HID[1] 失败 n=-1` + `HID 触摸回传未注册` | 宿主是**机顶盒/车机**（没有触摸源），或该宿主的 USB 栈不支持 AOA HID | **机顶盒可忽略**（画面不受影响）。触屏宿主才需要查手机是否在配件模式 |

**关于 AOA `SEND_STRING[4]`（URI）**：这是 AOA 里唯一的「去哪下载配套 App」字段。
手机切进配件模式但**没有任何应用认领**时，系统会拿它给用户一个去处。
本项目的值在 `:protocol` 的 `AccessoryIdentity.URI`，指向
`https://github.com/ghbhaha/UsbScreenMirror/releases/latest`（以前是占位符
`uav.example.com`，等于把自救路径指进死路，已被单测钉住）。
**前提条件比想象中严格：只有「没有任何 App 认领这条配件」时才会弹。**
它由 `UsbHandlerManager.showUsbAccessoryUriActivity()` 触发，组件是
`com.android.systemui/.usb.UsbAccessoryUriActivity`（**不在 Settings 里**，我一开始查错了对象）。
AOSP 的判定是：配件 attach 时先找声明了 `USB_ACCESSORY_ATTACHED` 的应用 ——
**找到一个就直接交给它，找不到才弹 URI 提示**。

★ **实测（HONOR MAA-AN10 / MagicOS）：URI 写对了也不会弹，因为被荣耀「多屏协同」接走了。**
三条日志挨着看就是完整因果：

```
20:57:02.105 I UsbDeviceManager: entering USB accessory mode: UsbAccessory[
             mManufacturer=UAV, mModel=usbscreen,
             mUri=https://github.com/ghbhaha/UsbScreenMirror/releases/latest ...]   ← URI 确实带上了
20:57:02.151 I ActivityTaskManager: START u0 {act=...USB_ACCESSORY_ATTACHED
             cmp=com.hihonor.android.airsharing/com.hpplay.sdk.source.usb.UsbNotifyActivity}
             from uid 1000                                                          ← 被多屏协同接走
```

那个 `UsbNotifyActivity`（乐播 hpplay SDK）**只声明 action、不带 `<usb-accessory>` 过滤**，
等于"任何配件都归我管"。只要它在，系统就认为"有人能处理"，**永远走不到弹 URI 那条分支** ——
URI 里填什么都不影响结果。

> 想亲眼确认这个结论：`pm disable-user --user 0 com.hihonor.android.airsharing` 后再拔插一次，
> 弹窗立刻出现（`pm enable` 恢复）。**但这只是验证手段，不能当产品方案** ——
> 总不能要求用户为了装个 App 去禁用自己的多屏协同。

⚠️ 另外两条实测细节：
- URI 只在**真实的 attach 那一刻**读取一次。手机已经处在配件模式时，宿主重写 `SEND_STRING`
  只更新 identity，不会重新评估（`START_ACCESSORY` 在已处配件模式时不重新枚举，见 3.x）；
- 组件本身是好的，可以先单独验证：`am start -n com.android.systemui/.usb.UsbAccessoryUriActivity
  --es uri '<url>'` 会显示「USB 配件 / 未安装此 USB 配件适用的应用…查看」。

**结论：不要依赖这个弹窗做引导。** 宿主侧的 `NO_ACCESSORY_APP` 提示（见上一张表的
「对方设备无应答」）才是可控的那条路；要让用户**在手机上**拿到安装包，方向是宿主屏显示二维码。

### 2.2 配件（手机）侧

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| ★ `dumpsys usb` 里身份为 `manufacturer=U model=u version=1`（**只剩首字符**） | `SEND_STRING` 编码错误（用 UTF-16LE 而非 UTF-8），AOSP 按 `\u0000` 切分字节串 | **必须 UTF-8 + 单个 `\0`**。这是历史红线，已修；若复现说明编码被改回去了，见 3.1 |
| 身份正确但系统不派发 `USB_ACCESSORY_ATTACHED` | 身份与 `accessory_filter.xml` 不匹配 | 两端三处必须逐字一致：`manufacturer=UAV` / `model=usbscreen` / `version=1.0`（见 3.1 的镜像表） |
| ★ `openAccessory 抛异常: User has not given <uid> permission to accessory UsbAccessory[Ewin/...]` | 手机上这个配件是**上一次别的宿主 App 留下的孤立链路**，我们的 App 从没收到过派发 | 让手机**切回普通模式**再走一遍完整握手，见 2.3 |
| `录屏授权被拒绝 —— 无法投屏` | 用户点了拒绝 | 点界面 **Grant** 重新授权；Android 14+ 每次投屏都要点一次，无法绕过 |
| `openAccessory 第 N 次尝试成功` | 系统派发晚于服务启动的瞬时无权限 | 正常（内置 6 次重试）。若 6 次全失败，查 2.3 |
| 画面冻结但日志正常 | 编码器死了却没上报 | 已知缺口，见 `实施计划.md` 路线图 P2「编码器死亡上报」 |
| ★ 静态画面只有 ~10 fps | **不是问题**：`KEY_REPEAT_PREVIOUS_FRAME_AFTER=100ms` 的设计效果（静止时兜底送帧、不让链路空转） | 不需要处置。要测帧率**必须让画面动起来** |
| 断链后手机端 App 直接消失、投屏不再恢复 | 曾是 `onClosed` 里直接 `stopSelf()` + 释放虚拟屏（服务自杀，且重连就得重新授权） | **已修**（10.8）。日志应出现 `自动重连第 N/10 次`；只有超过 10 次才停 |

### 2.3 「配件身份被顶掉」——本机特有

**现象**：宿主能握手成功、拿到接口，但永远等不到通话（`等待手机 CNXN 超时`），
手机侧则报 `openAccessory` 无权限，且 `dumpsys usb` 显示配件身份是**别人的**。

**根因**：手机当前这个「配件态」是**别的宿主 App** 建立的。本机实测遇到过
宿主上另装了 `com.ewin.screenaccessory`（旧项目），手机上因此报 `Ewin/EwinScrcpy/0.1`。
关键约束是：**手机已经在配件模式时，`START_ACCESSORY` 不会重新枚举 USB 设备**，
也就不重新派发 intent —— 所以身份不会自动被改写，我们的手机端 App 永远不会被拉起。

**处置（按顺序试）**：

```bash
# ① 先让宿主别抢跑
adb -s <host> shell am force-stop com.uav.host

# ② 手机切回普通模式（触发 gadget 重新枚举）
adb -s <acc> shell svc usb setFunctions

# ③ 确认手机真的切回去了（应显示 mtp/adb 之类，不再是 accessory）
adb -s <acc> shell getprop sys.usb.config

# ④ 确认宿主看到了手机（VID 应为 0x339B，不是 0x18D1）
adb -s <host> shell dumpsys usb | grep -E "vendor_id|product_id"

# ⑤ 再启动宿主，让前台轮询走一次完整握手（此时才会写入 UAV/usbscreen 身份）
adb -s <host> shell am start -n com.uav.host/.aoa.HostActivity
```

或更省事的方式：`--ez force_handshake true` 强制完整重握手（debug 包），
宿主内也已内置自愈——快路径失败时自动回退重试一次。

> **防复发**：把宿主上其它抢占 USB 配件模式的项目（如 `com.ewin.screenaccessory`）卸载，
> 或在联调前先 `pm disable` 掉。

## 3. 硬约束，以及最贵的几个坑

> 3.1~3.3 是**三条硬约束**（初版计划就列出的），3.4/3.5/3.6 是后来真机踩出来的坑。

### 3.1 配件身份有**两处**定义，改一处必须同步另一处

| 载体 | 位置 |
| --- | --- |
| 宿主发送的字符串（权威来源） | `:protocol` 的 `com.uav.protocol.AccessoryIdentity` |
| 手机端的匹配过滤器 | `app-accessory/src/main/res/xml/accessory_filter.xml` |

前者是 Kotlin 常量，后者是 XML —— **XML 无法引用 Kotlin 常量，只能手工镜像**。
参与匹配的三项必须逐字一致：`manufacturer=UAV`、`model=usbscreen`、`version=1.0`。

编码方式：**UTF-8 + 单个结尾 `\0`**。
（`SEND_STRING` 对编码错误**只返回失败、不报原因**，是本项目最隐蔽的坑，详见 3.4。）

### 3.2 端点地址不能写死

实测配件端点是 **`in=0x81` / `out=0x01`**，不是常见示例里的 `0x02`。
代码按 direction/type 遍历选定并打日志，**不要改成常量**。

### 3.3 配件接口不能按 interface class 识别

实测配件接口描述符是 `class=255 sub=255 proto=0`，与 **adb 接口完全相同**
（adb 是 `255/66/1`）。识别只能按 **PID `0x2D00` / `0x2D01`**。

### 3.4 `SEND_STRING` 报错点离根因极远（值得单独记）

编码错误时的**症状链**：

```
UTF-16LE 编码  →  手机 dumpsys 显示 manufacturer=U（只剩首字符）
               →  身份对不上 accessory_filter.xml
               →  系统不派发 USB_ACCESSORY_ATTACHED
               →  手机端拿不到权限
               →  openAccessory 返回/抛 null
               →  宿主永远等不到 CNXN，超时报错
```

**报错在"超时"，根因在"编码"**。之所以会只剩首字符：`UAV` 编成 `55 00 41 00 56 00 00 00`，
而 AOSP 按 `\u0000` 切分，读到第一个 `00` 就断了。

**自查方法**（一眼定位，不用看日志）：

```bash
adb -s <acc> shell dumpsys usb | sed -n '/current_accessory/,/}/p'
# 六个字符串都完整（UAV / usbscreen / ... / 1.0）才是对的
```

### 3.5 ★ 手机端"永远切不进配件模式"：一个 fd 泄漏（本项目最贵的坑）

**现象（看起来像硬件不灵）**：

- 宿主刷 `等待重枚举超时（5000ms）`，一轮接一轮，永不好转；
- 手机 `sys.usb.config` **始终不变成** `accessory`（一直是 `mtp,adb` / `hisuite,mtp,...`）；
- 手机端日志里 `openAccessory 第 N 次失败`（连试几次全失败）；
- **`force-stop` 掉手机端 App 立刻就恢复正常**，重插拔也"有效"。

**根因**：`/dev/usb_accessory` 是**独占打开**的。只要有一个 fd 没被关掉
（例如 `Connection.fail()` 出错时漏关底层通道，而 `closing` 已置 true 又让后续
`close()` 直接返回 —— fd 就永远关不掉了），手机端 gadget 就**再也进不了配件模式**。
于是宿主怎么握手都白费。

> ⚠️ 这条推翻了此前"OTG 链路偶发不稳、重插拔即恢复"的归因：
> 拔插之所以"有效"，只是因为它顺带杀掉了持 fd 的进程。**别再靠拔插来确认问题**。

**判定（不用猜）**：

```bash
# 1) 手机到底有没有切过去？这是决定性的一个字段
adb -s <acc> shell getprop sys.usb.config          # 期望 accessory,adb

# 2) 宿主在反复握手但手机没切 —— 基本就是这一条
adb -s <host> logcat -d -s UAV-Host | grep -E "re-enumerated|等待重枚举超时"

# 3) 进阶：直接数 App 持有的配件 fd（debug 包，正常恒为 1；>1 就是在漏）
adb -s <acc> shell "P=\$(pidof com.uav.accessory); \
  run-as com.uav.accessory ls -l /proc/\$P/fd | grep -c usb_accessory"
```

**处置**：

```bash
# 立竿见影（用于人工救急）
adb -s <acc> shell am force-stop com.uav.accessory
```

**当前版本已内置自愈，正常情况下不需要人工介入**（见 10.8）：

- 出错/EOF 路径会真正 `transport.close()`（不再只把引用置 null）；
- 会话起来后 12s 内宿主毫无应答 ⇒ 判为「假配件」，**主动释放 fd 且不重连**，
  把 gadget 让出来等宿主重新握手。

预期日志（两端各一句，出现即说明自愈生效）：

```
UAV-Accessory: 传输层已释放（链路错误: ...）
UAV-Host:      re-enumerated as accessory: ... → link ready
UAV-Accessory: 复用既有编码器，已重发流头与 CONFIG
```

### 3.6 HID 触摸注入：注入了但手机没反应

宿主已经把触摸转发做成了功能（点宿主屏幕 = 点手机，见 `docs/实施计划.md` 10.11），
所以这里先分三件事：**有没有注册**、**注册了但报告没到**、**点在了不转发的地方**。

```bash
# A) 宿主侧：注册了吗？空间是多少？
adb -s <host> logcat -s UAV-Host | grep -E "HID 触摸屏已注册|清理了|触摸转发|触摸忽略"

# B) 手机侧：真的有这块"触摸屏"吗？（关键看 INPUT_PROP_DIRECT）
adb -s <acc> shell "getevent -pl | grep -E 'add device|name:'"
adb -s <acc> shell "getevent -pl /dev/input/eventN"      # 期望看到 BTN_TOUCH + ABS_MT_POSITION_X/Y
#    ⚠️ INPUT_PROP_DIRECT = 触摸屏；写成 INPUT_PROP_POINTER 说明被当成鼠标（Usage 写错了）
#    ⚠️ 我们的设备 name 是空的（AOA 不给 product string），靠这一点最好找

# C) 手机侧：报告到底到没到？
adb -s <acc> shell "getevent -lt /dev/input/eventN"
#    ⚠️ **指定了设备路径后，输出行不带 /dev/input/eventN 前缀** ——
#       按设备名 grep 会得到"一条都没有"的假象（我踩过）
#    ⚠️ event 编号会随设备增减变化，别把 eventN 写死
```

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| 宿主日志 `尚未绑定连接（链路未就绪）` | 注册被安排在"链路就绪"之前（**必须等 `CNXN` + 流头都到齐**） | 等 `video config` 之后自然会注册；见 10.11 |
| 宿主日志 `清理了 N 个上一次连接残留的 HID 设备` | 正常：不重枚举的重连会在手机上留幽灵触摸屏，注册前会扫掉 | 不用管；若 `N` 一直增长说明扫描没生效 |
| 手机上 `dumpsys input` 里出现**多个**空名字触摸屏 | 旧版本没做残留清理 | 已修（10.11）；现有的多余设备会在下一次**真重枚举**后消失 |
| `REGISTER_HID` 返回负数 | 手机还没进配件模式（内核尚未接管 `f_accessory`） | 等 `link ready` 之后再注册 |
| 设备列表里**没有**新设备 | 描述符本身没被接受 | 看宿主日志里 `SET_HID_REPORT_DESC` 是否失败；确认 `REGISTER_HID` 的 `index` = **描述符总长度** |
| 有设备但 `INPUT_PROP_POINTER` | Usage 写成了 `Pen` 之类 | Usage 必须是 `Digitizer(0x0D) / TouchScreen(0x04)` |
| 有设备、`getevent` 无输出 | 报告发错 id / `SEND_HID_EVENT` 失败 | 宿主日志 `SEND_HID_EVENT[id] 失败 n=...` |
| **点宿主屏幕手机没反应** | ① 点在了**信箱边**（视频显示区之外，不转发）② 锚点算错 | 看宿主日志的 `触摸转发：视图内 (…) → 手机 (…)` / `触摸忽略：…不在显示区内`；见 10.11 |
| 触摸坐标整体偏移 | 坐标空间不是手机屏幕尺寸 | 用 `CNXN` 的手机屏幕尺寸，别用编码后的视频尺寸 |
| 旋转后坐标错位 | 描述符的 Logical Max 没跟着换 | 空间变了必须重新注册（10.11 已自动做） |
| 手指"卡住"不抬 | 断链期间未重发/未补抬起 | 重连后会重发当前触摸状态，切后台会补一个抬起 |
| 想肉眼确认落点 | — | `settings put system show_touches 1` 后触摸，屏幕上会出现触摸圆圈（用完记得关回 0） |
| **第二根手指不出来 / 一按就释放** | 描述符形状错：必须是 **N 个独立 Finger collection**，`Contact Count` 放在**最后**且填**帧内记录数**（不是按下的触点数） | 见 10.12；对照 `getevent -pl` 里有没有多余的 `ABS_MT_TOOL_X/Y`（错误形状才会出现） |

> ★ **断链后必须重新注册**（已实证）：重枚举会让 HID 设备从手机上消失（输入设备数掉回去）。
> 这与 3.5 的 fd 泄漏是两件事，别混。
> ★ **反向也要注意**：**不重枚举**的重连**不会**清掉旧 HID 设备 → 会累积幽灵触摸屏，
> 所以注册前会扫一遍残留（10.11）。

### 3.7 切后台 / 回前台（Surface 销毁与重建）

宿主用的是 `SurfaceView`，**切后台、息屏、Activity 销毁都会销毁它的 Surface**。
这里踩过两个坑，都已修（见 `docs/实施计划.md` 10.10）：

| 症状 | 根因 | 现状 |
| --- | --- | --- |
| 按 Home / 打开最近任务后**整个 App 崩溃**，`CodecException: rendering to non-initialized(obsolete) surface` | `surfaceDestroyed` 先于 `onDestroy`，中间解码线程仍在往失效 Surface 上渲，而 `releaseOutputBuffer` 当时没有保护 | ✅ 已修：`surfaceDestroyed` 立即停渲染 + `VideoDecoder` 最内层兜底 |
| 切后台较久后回前台，**永远黑屏**，日志反复 `等待手机 CNXN 超时` | 会话被停 → 手机释放配件 fd → 超过它 12s 空闲看门狗后不再重开；而手机已在配件模式时 `START_ACCESSORY` 不会重新枚举、系统也不再派发 attach | ✅ 已修：改为**只停渲染、链路保持**（不再触发 USB 重枚举） |

**正常日志长这样**（切后台 → 回前台，全程零重枚举）：

```
surface destroyed
Surface 已销毁：已释放解码器、停止渲染（链路保持）
surface created: ...
Surface 已恢复：准备用缓存的 CONFIG 重建解码器
解码器已在新 Surface 上重建（872x1920，csd=32B） —— 最多到下一个 I 帧（3s）画面才干净
```

⚠️ **若已经掉进"手机 fd=0 但 config=accessory"的死锁**，宿主这边无解，只能真重枚举：
`adb -s <acc> shell svc usb setFunctions mtp`（用户侧就是拔插一次）。

### 3.8 音频内录：没声音 / 录到全 0

**先分清"没有音频流"还是"有流但录到静音"** —— 这两类的处置完全不同。

```bash
# A) 手机到底有没有在录？（看内录心跳里的电平）
adb -s <acc> shell "P=\$(pidof com.uav.accessory); logcat -d --pid=\$P | grep UAV-Audio | tail -3"
#    rms=-120.0dBFS = 静音下限；只要不是 -120 就说明真的录到东西了
#    ★ 判据只有电平：内录失败最典型的样子是"帧数一直在涨、宿主也在播放，但录到的是全 0"

# B) 手机此刻真有声音在放吗？（内录录不到"没在播的东西"）
adb -s <acc> shell "dumpsys audio | grep -E 'player piid|state:started'"
#    期望看到一条 usage=USAGE_MEDIA（或 USAGE_GAME）且 state:started 的播放器

# C) 宿主侧解出来的 PCM 电平
adb -s <host> logcat -d -s UAV-Host | grep STATS | tail -1 | grep -oE "audio 48000Hz.*输入超时=[0-9]+"
```

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| 手机日志完全没有 `UAV-Audio` | 宿主没要音频 / 内录没起来 | 看宿主 STATS 里有没有 `audio=aac`；手机端看 `内录已启动` 或 `内录启动失败` |
| `无录音权限，仅投屏` | `RECORD_AUDIO` 被拒 | 授予录音权限后**重新投屏**（权限是启动时要的） |
| `内录启动失败` + `AudioRecord 未初始化` | 权限缺失，或 ROM 阉割了内录 | 见上一行；确认 `getMinBufferSize > 0` |
| 帧数在涨但 `rms` 恒 `-120.0` | ① 手机没在放东西 ② 放的那个应用被捕获白名单挡住 | 先 `dumpsys audio` 确认有 `USAGE_MEDIA` 在响 |
| 播放器在响但仍是静音 | 那个应用声明了 `allowAudioPlaybackCapture="false"`，或 `targetSdk < 29` 且没 opt-in | **框架限制，无法绕过**（银行/DRM 属于这类）。换一个应用验证 |
| 通知/铃声/闹钟录不到 | usage 不在白名单（只允许 MEDIA/GAME/UNKNOWN） | 同上，改不了 |
| 宿主无声音、手机有声音 | 宿主 `AudioPlayer` 初始化失败 | 看 `音频输出已就绪`；失败会打 `音频输出初始化失败` |
| 后台一段时间后没声音 | 前台服务缺 `microphone` 类型（Android 14+） | 见 10.13「最反直觉的一条」；确认 `startForeground` 的类型含 microphone |
| 音画不同步 | 只做了起播常量补偿 | `--ez scan true --ei audio_delay_ms N` 现场调 |

**肉眼/耳朵验证（debug 包）**：手机上放一段**你自己的**声音最省事 —— 测试音入口：

```bash
# USAGE_MEDIA 的 1kHz 正弦，手机扬声器也会响（这是预期）
adb shell am start -n com.uav.accessory/.ProjectionActivity --ez tone true --ei tone_ms 30000
#   ⚠️ 只能打 Activity：CaptureService 是 exported=false，am startservice 会被直接拒掉
#   ⚠️ 但**别**用它去改 USB 状态（见 3.5）—— 该入口已保证不碰传输会话
```

⚠️ **别拿系统铃声当声源测内录**：铃声是 `USAGE_NOTIFICATION_RINGTONE`，**不在可捕获的 usage 里**，
录不到是正常的，用它测会得出"内录坏了"的假结论。

### 3.9 ★ 宿主设备自己重启了 —— 先分「我们的 bug」还是「设备 kernel panic」

宿主突然回到锁屏/重启、调试端口变了，**第一件事不是怀疑代码**，而是读设备自己持久化的启动原因：

```bash
adb -s <host> shell "getprop persist.sys.boot.reason.history"   # 最近三次启动的原因+时间戳
adb -s <host> shell "getprop ro.boot.bootreason"                # 本次启动原因
adb -s <host> shell "cat /proc/uptime"                          # 内核已跑多久（判断是否真重启）
```

| 读到的值 | 含义 | 该怎么办 |
| --- | --- | --- |
| `kernel_panic,bug,...` | **内核 panic**（不是掉电）。`...` 是启动时刻的 epoch 秒 | 见下 |
| `reboot,ota` / `reboot,xxx_reboot` / `shutdown,...` | 正常重启 / OTA / 长待机 | 与我们无关 |
| `watchdog,...` | 看门狗 | 先看是否卡死在驱动里 |

内核 panic 现场还能从 dropbox 里捞（含调用栈）：

```bash
adb -s <host> shell "dumpsys dropbox --print SYSTEM_LAST_KMSG | grep -B60 -A6 ipanic_die"
#   ipanic_die / mrdump_common_die   ← MediaTek 的 panic 记录模块
#   die() ← bug_handler ← brk_handler ← do_debug_exception   ← BUG_ON(BRK) 踩死
#   ⚠️ 这份 kmsg 可能**是旧的**（mrdump 不一定每次刷新），逐次 panic 未必都能读到现场
```

**本项目实测（宿主 BOE P40UCH / MT8781V / 内核 5.10.226，`Tainted: G W O`）**：

```
kernel_panic,bug,1792147809   ← 18:50:09
kernel_panic,bug,1792146459   ← 18:27:39     （上一次只活了 22.5 分钟）
kernel_panic,bug,1792146348   ← 18:25:48     （上一次只活了 111 秒）
```

**连续三次 boot 全是 kernel_panic**；同一时刻手机端（HONOR）的启动原因是
`reboot,honor_reboot` / `reboot,ota` / `shutdown,longstandby`、uptime 2.2 天 —— 全都正常。

### ⚠️ 重大更正（10.16）：那三次 panic 是**我们的 App 搞崩的**，不是固件问题

本节最初写的是"⇒ 是宿主设备的固件/内核问题，App 层解决不了"——**这个结论是错的**，
当时只看了启动原因就下结论。后来拿到 MTK 完整日志包（`APLog_*` 里的 `last_kmsg`，
即 `/data/debuglogger/console-ramoops-0` 的持久化 ramoops，比 DropBox 那份截断版全），
现场把肇事线程和系统调用指名道姓地暴露了：

```
usercopy: Kernel memory exposure attempt detected from SLUB object 'kmalloc-128' (offset 0, size 391)!
kernel BUG at mm/usercopy.c:99!                Internal error: Oops - BUG
CPU: 7  PID: xxxxx  Comm: uav-reader           ← 宿主端我们的 bulk 读线程
  usercopy_abort <- __check_object_size <- do_proc_bulk+0x374 <- usbdev_ioctl
                                                ↑ USBDEVFS_BULK = bulkTransfer
```

**根因（App 层，已修）**：协议层读报文头(24B)/小帧末段时，`BulkByteChannel` 把同样小的
长度透传给了内核 —— **小于端点包长 512B**。这台 MTK 主机栈不把 `actual_length` 截到请求长度，
设备交付更大的包（实测 391B）时，内核拿 391 去拷 128B 的 bounce buffer → 加固 usercopy `BUG()`。
修法：`BufferedByteChannel`（`:protocol`，10.16）—— 对底层永远整块 16KB 读 + 残留续读。

**定性"panic 是谁干的"——别再靠启动原因猜，直接读现场**：

1. **读完整 ramoops**（比 dropbox 的截断版全得多）：
   ```bash
   adb -s <host> shell "ls -la /data/debuglogger/console-ramoops-0"   # root 才能读
   #   无 root：用 MTK 工程模式导出 APLog 包，取其中 last_kmsg（= console-ramoops-0）
   ```
2. 在 kmsg 里搜 `kernel BUG` / `usercopy` / `Internal error`，**看 `Comm:` 是谁**：
   - `Comm: uav-reader` / `uav-writer` / 栈里有 `do_proc_bulk` ⇒ **我们的 bug**，修 App；
   - `Comm:` 是无关驱动/线程 ⇒ 才谈得上"设备自己的问题"。
3. App 层崩 vs 内核崩的区分依然有效（`-b crash` 有 `FATAL EXCEPTION` 是 App 崩；
   只有 `kernel_panic` + uptime 归零是内核崩）—— 但"内核崩"**不等于**"与我们无关"。

### 3.10 画面"偏小/发糊"：如何判断 1:1 像素映射有没有生效

先量三个数，一眼就能定位（不用猜）：

```bash
# A) 宿主协商时用的显示区与 max_size
adb -s <host> logcat -d -s UAV-Host | grep "OPEN options" | tail -1
#   OPEN options: max_size=992 display_area=1920x987 phone=1224x2700 panel=1920x1080

# B) 手机端实际编码尺寸 + 用的是哪套口径
adb -s <acc> shell "P=\$(pidof com.uav.accessory); logcat -d --pid=\$P | grep -E 'virtualDisplay|旋转：' | tail -2"
#   1:1 生效  : scaled 456x992  (max_size=992, 1:1(宿主显示区 1920x987), ...)
#   走了回退  : scaled 872x1920 (max_size=1920, 旧口径(宿主长边), ...)      ← 见下表第 2 行

# C) 宿主实际把画面显示成多大（= SurfaceView 的 bounds）
adb -s <host> shell "uiautomator dump /sdcard/ui.xml >/dev/null 2>&1; cat /sdcard/ui.xml" \
  | grep -o 'id/surface[^/]*bounds="[^"]*"'
#   把 bounds 的宽高与 B 的编码尺寸比一下：差 1~3px 属正常（align8 取整）
```

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| 画面比可用区小一圈（四周几十 px 黑边） | `OPEN` 时读到的显示区比最终布局小（insets 尚未稳定，实测差 36px ≈ 状态栏） | **正常**，见 10.15「已知边界 2」。绝不会放大模糊，只是没吃满 |
| 画面发糊（编码尺寸明显小于显示区） | 走了**旧口径**，或尺寸是**旧方向**算的 | 先看宿主面板「画质」是否**切到了「高清」**——那么 `旧口径(宿主长边)` 是**预期行为**（10.17：高清就是故意编高分辨率再让宿主缩）；若画质是「1:1」还出现 `旧口径` ⇒ 宿主没下发 `display_width/height`（两端版本不一致）；`max_size` 与当前方向不符 ⇒ 宿主窗口尺寸变了但没触发重协商 |
| 换方向后糊 | 手机旋转没重算尺寸 | 该有 `旋转：... max_size X -> Y` 一行；没有就是手机端还是旧包（10.15 之前） |
| 想省带宽（而不是提画质） | 码率是固定 8 Mbps，1:1 只降像素不降字节 | 见 10.15「关于省了多少带宽」——需要按面积缩放 `video_bit_rate`（未做） |

> ⚠️ `STATS` 里的 `maxSize=` 是**协商当时**的值，手机旋转后会过期；
> 真实尺寸看同一行的 `video=avc1 WxH`。别只看 `maxSize` 就下结论。

### 3.11 点了「画质」开关没反应 / 画面清晰度没变 / 切换很慢

宿主面板（10.19 起为**左侧竖栏**）里的「画质」**分段控件**：`1:1 像素` / `高清`（10.17）。**判据是宿主解码尺寸**，别看别的：

```bash
adb -s <host> logcat -d -s UAV-Host | grep -E "像素模式切换|原地重协商|OPEN options" | tail -3
#  像素模式切换 → 高清（按面板长边编码）
#  原地重协商：在同一条连接上重发 OPEN     ← 10.18：不重连、约 2~3s 生效
#  OPEN options: max_size=1920 display_area=- phone=1224x2700 panel=1920x1080
adb -s <host> logcat -d -s UAV-Host | grep STATS | tail -1
#  video=avc1 872x1920  ⇒ 高清已生效（1:1 时这里是 456x992）
```

| 症状 | 原因 | 怎么办 |
| --- | --- | --- |
| 点了没反应、`像素模式切换` 日志都没有 | 面板没展开（GONE 点不到）或点到了画面 | **优先点左上「状态药丸」展开面板**（它常驻、且不会把点击转发给手机）；点信箱边空白也行，但**面板已是展开态时那一击会先把面板关掉、再被当成触摸转发给手机**（踩过）。面板在**左侧竖栏**（10.19），按钮位置随状态行行数变，别写死坐标 |
| 有 `像素模式切换`、但 `video=` 一直不变 | 手机端**重连复用了既有编码器**（10.17 之前的包） | 手机端要跑含 `applyOptions` 的包；看手机日志有没有 `像素模式变更：… 编码 A -> B` |
| 切换后几十秒才生效 | 走的是**断线重连**（原地重协商失败/包不含 10.18），偶尔首条 `OPEN` 撞 `bad magic` 后重试 | 正常应 2~3s；看日志有没有 `原地重协商：在同一条连接上重发 OPEN`。没有 ⇒ 走了回退（`原地重协商未成功 → 回退到断开重连`），按 3.x 查链路 |
| 切高清后仍觉得糊 | 高清只让"编码分辨率变高、宿主端缩下去"更像超采样，**码率没变** | 见 10.17「未做」——按面积调码率属 P1 |

⚠️ **`max_size` 只在 `OPEN` 时协商一次**，所以开关必须**重发一次 `OPEN`** —— 10.18 起是**在原地**发，不重连。

宿主面板自 10.19 起是**左侧竖栏**（宽 300dp，落在竖屏视频左侧的信箱边里，不挡画面）；
面板收起后由左上角**状态药丸**（圆点颜色：空闲灰 / 连接中黄 / 投屏中绿 / 出错红）充当状态显示与「再次打开」入口。

### 3.12 ★ 换一台宿主就完全连不上：两个"只在特定宿主出现"的坑

2026-10-18 在 **RK356x 机顶盒（DBBOXH3 / Android 11）** 上第一次跑，症状是
「宿主每 330ms 重试一次、配件端每次都回 `CNXN`，但宿主一个合法报文都解不出来」，
同时把两个与设备强相关的坑一起暴露了。**换宿主（电视盒子 / 车机）先看这一节。**

#### ① 失步（bad magic）不能判链路死，必须重新同步

```
W/UAV-Host: 丢弃 33694 字节入站残留（上一次会话的尾巴）
E/UAV-Host: reader loop failed: bad magic: got 0x0 expected 0xce9c899e (command=0x31637661)
            00000000  61 76 63 31 f0 01 00 00 38 04 00 00 57 52 54 45   avc1........WRTE
```

`61 76 63 31` 是 `avc1` —— 也就是**一条 12B 流头**，它后面紧跟着 `WRTE` 报文头。
这说明读指针停在"某条报文的 24B 头之后、payload 之前"，是**半条报文**，不是对端乱发。

成因（三条同时成立才会出现）：
1. 上一次会话结束时配件端还在推流，FIFO 里留着半条报文；
2. 配件端的写线程被压住（bulk write 阻塞数秒），期间它连我们的 `CNXN` 都读不到
   → 宿主侧表现成「等了 15s 一个字节都没回」；
3. 宿主的 `drainStaleInput()` 只能在"读超时"处停下，**天然可能停在报文中间**。

⇒ 协议**没有事务边界**，唯一正确的处理是"前移到下一个合法报文头继续"
（`protocol/adb/DesyncRecovery.kt`，判据 = `magic == command xor 0xffffffff` +
已知命令字 + `data_length` 在限内 + `arg0` 是已知流 id）。
日志 `链路失步[N] → 跳过 M 字节后重新同步到报文头` 就是它，**属于自愈，不是错误**。

⚠️ 别把"扫描重同步"用在**所有**协议错误上：`AUTH`/`STLS`（已裁剪命令）是对端真的
说了不该说的话，仍然是普通 `ProtocolException`，必须判死。

#### ② `low-latency` 会把老厂商 OMX 组件的 configure 直接打死

```
E/OMXNodeInstance: setConfig(0xef800400:rk._decoder.avc, ??(0x6f800006)) ERROR: UnsupportedIndex(0x8000101a)
E/ACodec: decoder can not set low-latency to 1 (err -1010)
E/ACodec: [OMX.rk.video_decoder.avc] configureCodec returning error -1010
```

`MediaFormat.setInteger("low-latency", 1)` **永远不会抛异常** —— 它只是往包里塞一个键，
真正的失败在 `configure()` 里：`ACodec` 会 `setConfig(OMX_…lowLatency)`，
RK 的 legacy 组件返回 `UnsupportedIndex`，`ACodec` **当致命错误**处理。
手机端（MTK/高通的 Codec2）能接受这个键，所以这个坑一直在盒子/车机上等着。

⇒ 调优键必须**可退让**：带调优 configure 失败就换最小 format 再试一次
（`VideoDecoder.tryConfigure(..., tune = false)`），日志会打
`去掉 low-latency/priority 后才 configure 成功`。

#### ③ 顺带：机顶盒的 `REGISTER_HID` 失败可以忽略

`REGISTER_HID[1] 失败 n=-1` ⇒ 触摸回传不可用。机顶盒/车机没有触摸源，画面不受影响。
**别被这句 ERROR 带偏**（原来它写的是"手机是否真的在配件模式？"，误导性很强）。
另外这些盒子的 `pm list features` 里**有** `android.hardware.touchscreen`
（为了让只支持触摸的 App 能装），真实判据只有 `dumpsys input` 里各设备的 `Sources`
有没有 `0x1000`（`SOURCE_TOUCHSCREEN`）位。

#### ④ 没有 SystemUI 的宿主：只能出「系统签名包」

**判据**（三条都命中就是它）：

```bash
adb shell pm path com.android.systemui                 # 空
adb shell ls /system/priv-app | grep -i systemui        # 空
adb shell find /system -iname '*SystemUI*'              # 空
```

症状是 `requesting permission for device …` → `ActivityManager: START …UsbPermissionActivity`
→ `permission wait timed out after 60000ms`，每 60 秒一轮，界面永远停在"等待 USB 授权…"。

**为什么"签个名"不够**（AOSP 7.1.2 源码实证，别凭直觉）：

- `UsbSettingsManager.hasPermission()` 只认三种：`uid == SYSTEM_UID` / `mDisablePermissionDialogs`
  （ROM 的 `config_disableUsbPermissionDialogs` 资源）/ 已记录的 uid grant —— **没有签名检查**；
- attach 时的自动授权要求「唯一匹配 **且** 该 App 是 `FLAG_SYSTEM`」，签名不改 `FLAG_SYSTEM`；
  而且 **MTP 设备走 `MtpNotificationManager` 通知分支、根本不进 `resolveActivity`**
  ⇒ `pm disable-user com.android.mtp` 那类办法无效（实测过）。

**能自己解决的路：`sharedUserId=android.uid.system` + 平台签名**

```bash
./gradlew :app-host:assembleSystem      # → apk/system/app-host-system.apk
```

- `buildType = system`，清单来自 `app-host/src/system/AndroidManifest.xml`，里面只有一句
  `android:sharedUserId="android.uid.system"` ⇒ 进程 uid = 1000 ⇒ `hasPermission()` 直接为真，
  不弹窗、不需要 SystemUI、也不用反射隐藏 API。
- 平台密钥同样放**仓库外**，在 `$GRADLE_USER_HOME/gradle.properties` 里写四个属性
  `usbscreen.platform.storeFile / storePassword / keyAlias / keyPassword`。
  `platform.pk8` + `platform.x509.pem` 不能直接用，先转 keystore：

  ```bash
  openssl pkcs8 -inform DER -nocrypt -in platform.pk8 -out platform.pem
  openssl pkcs12 -export -in platform.x509.pem -inkey platform.pem \
          -name platform -out platform.p12 -passout pass:******
  keytool -importkeystore -srckeystore platform.p12 -srcstoretype PKCS12 \
          -destkeystore usbscreen-platform.jks -deststoretype JKS -alias platform
  ```

⚠️ 三条硬约束：
1. 必须平台证书签名，否则装不上；
2. **装它要先卸载现有包**（uid 从 app 变成 1000 ⇒ `INSTALL_FAILED_UID_CHANGED`），
   而卸载会清空 `filesDir` —— **iOS 配对记录要重新配一次**；
3. `sharedUserId` 自 API 29 起弃用（功能仍在），所以这个变体只给老的定制宿主；
   `release` / `debug` 包**不带**这个属性，普通手机照旧。

> 另一条更省事的路（需要能改固件）：把 ROM 的 `config_disableUsbPermissionDialogs` 设成
> `true`，这台机器上**所有** USB Host 应用都免弹窗，连系统签名都不用。

#### ⑤ Amlogic 商显：`screencap` 抓不到视频层（别据此判"黑屏"）

在 V31103（Android 7.1.2 / Amlogic）上 `adb exec-out screencap -p` 出来的**视频区永远是黑的** ——
解码走**硬件视频层**直接合成（日志里 `AmlogicVideoDecoderAwesome` / `use_frame_mode=1`），
`screencap` 只抓 GPU/OSD 层。`dumpsys SurfaceFlinger --latency <视频层>` 同样全 0，两个都不能用。

⇒ 这类设备的验收判据只有两条：
1. 宿主日志出现 `首帧已输出 WxH`，且手机端 `MediaProjection` 已启动；
2. **人眼看屏**。
⇒ 想判断"到底还在不在出新帧"，看线程 CPU 增量（`/proc/<pid>/task/*/stat` 的第 14+15 字段，
   `uav-reader` / `uav-decode` 两条线程），别用截屏。

### 3.13 ★ iOS 配对卡在 `GetValue(DevicePublicKey)`：`java.util.Base64` 在 Android 7.1 上不存在

**症状**（CVTE V31103 / Android 7.1.2 / iPad8,9 iOS 27.2）：

```
← lockdownd 914B: <?xml …><key>Value</key><data>LS0tLS1CRUdJTi…</data>
✗ GetValue(DevicePublicKey) 无回复：超时
```

回包明明到了（914B，base64 完全合法），上层却说"没回复"。

**根因**：`java.util.Base64` 是 **API 26（Android 8.0）** 才有的类。`:protocol/ios` 里
`PlistXml.readData` / `Lockdown` / `Der.pemBody` / `CertKit.selfCheck` 都在用它 ⇒
在 API 25 上执行到那行抛 `NoClassDefFoundError`，被 `runCatching` 吞掉后
**只表现为"plist 解析失败"**，再被翻译成"设备没回复/超时"。

⚠️ **JVM 单测发现不了**（JVM 有 `java.util.Base64`），必须真机才能暴露；
这跟"设备把 `<data/>` 写成自闭合"是**两回事**，别混。

**修法**：`:protocol` 自带 `B64`（纯 Kotlin、零 Android 依赖）。**`:protocol` 里禁止再出现
`java.util.Base64`**（minSdk 23）。换完当场：`★★ Pair 成功（EscrowBag 32B）` → `FEED #1` → 首帧。

> 通用结论：**`runCatching` 包住的"环境缺 API"会伪装成业务失败**。移植到老宿主前，
> 先查用到的 `java.*` 类在目标 API level 有没有。

**顺带两个 mux 侧的坑**（同一次排查揪出来的）：

| 现象 | 根因 | 修法 |
|---|---|---|
| 放弃会话后，下次插上 `2s 内无有效 VERSION 回复（0B）`，只能拔插 iPad | 只关了 fd，没给设备发 TCP **FIN** ⇒ 设备侧那条连接一直 ESTABLISHED | `MuxLink.shutdown()` 发 FIN；放弃会话的每条路径都调 |
| 偶尔误报"设备无应答" | VERSION 应答是 20B，一次 `bulkTransfer` 可能只回 8B 头，而循环条件是 `pre.size < 8` | 攒够 20B 再判 |

#### 改 iOS 会话路径怎么验证（血泪版）

1. **先确认 iPad 是亮屏解锁的**。锁屏 = 零推流，我一度把"锁屏沉默"当成改坏的证据，白改三轮。
2. **不要 `am force-stop`**。杀进程不走 `onDestroy`/收尾 ⇒ 设备侧 QT 会话残留，下次
   `am start` 即使配置正确也拿 **0 字节**，**只有物理拔插能恢复**。
   正确顺序：界面返回键（或停止按钮）等日志出现 `收尾完成` → `adb install -r` → `am start`。
3. 判据只看这串：`PING#1/#2 → CWPA → FEED #1 → 首帧已渲染`。

#### TLS 那段 8 秒能不能省

能省到 **1 秒**（`IosFeatures.TLS_WAIT_MS`），起流从 ~10s 变 2s。

- **不能省成 0**：完全不升级 TLS ⇒ 设备回 1 次 `PING` 后永久沉默（零 CWPA / 零 FEED）；
- **1s 够**：`ClientHello` 照发、到点不握手成功就继续，`PING×2 → CWPA → FEED` 正常；
- 代价：`link.trusted` 恒为 false ⇒ 控制面（设备信息/唤醒/音量/事件）用不了；
  配对与音视频**不依赖**它（配对走明文 lockdown，QT 通道全程明文）。

## 4. adb 操作红线（Windows + Git Bash）

这几条都实际踩过，**照抄能省很多时间**。

| 红线 | 现象 | 处置 |
| --- | --- | --- |
| **Git Bash 会改写 Android 绝对路径** | `adb push /data/local/tmp/x` 报 "1 file pushed" 但文件不在那儿；`adb pull /sdcard/...` 报 `failed to stat remote object 'D:/...'`（路径被改写成 Windows 形式） | 每次开 adb 前先 `export MSYS_NO_PATHCONV=1` |
| **`adb shell` 默认分配 PTY，会改写二进制流** | 传二进制文件被破坏 | 传二进制用 `adb shell -T`（禁 PTY） |
| **大文件用 `adb exec-out "cat ..."` 直取** | `adb pull` 受路径改写影响、且对受限目录假成功 | `adb -s <acc> exec-out "cat /sdcard/.../uav-dump.uav" > dump.uav` |
| **`/sdcard/Android/data/<pkg>/` 在 Android 11+ 对 adb shell 受限** | `push` 假成功，文件其实没进去 | 要放进 App 私有目录，用 `adb shell "run-as <pkg> sh -c 'cp /data/local/tmp/f files/'"`；或 `adb shell -T "run-as <pkg> sh -c 'cat > files/x'" < local` |
| **`am force-stop` 会让 App 进入 stopped 状态** | 此后系统**不再用隐式 intent**（如配件 attach）拉起它 ⇒ 会把「链路不通」误判成软件 bug | 调试时别随手 `force-stop` 手机端 App。要清状态就用显式启动一次：`am start -n com.uav.accessory/.ProjectionActivity` |
| **OTG 链路偶发不稳** | 出现「等待重枚举超时」，双方日志都看不出原因 | **重插拔即恢复**（实测两次都是这样好的）。连续快速切 USB 模式容易触发 |

另外：本机 `ANDROID_HOME` / `ANDROID_SDK_ROOT` 均为空，adb 要用绝对路径或在
PATH 前挂 `/d/Develop/Android/sdk/platform-tools`。

## 5. 怎么读宿主日志

排错时最省事的一条命令：

```bash
export PATH="/d/Develop/Android/sdk/platform-tools:$PATH"
export MSYS_NO_PATHCONV=1
adb -s <host> logcat -v time -s UAV-Host UAV-Video UAV-Protocol UAV-Accessory
```

**周期统计行**（debug 包每 5 秒一条，压测与判活主要看它）：

```
STATS phone=1224x2700 maxSize=1920 | msgs(r/w)=710/2
      video=avc1 872x1920 frames=706 config=1 bytes=3405509
      queue=FrameQueue(video size=0/4 dropped=0[0 nonKey/0 key])
      decoded=705 queued=706 | inputStalls=0 cfgFailures=0
      | delay avg=104.9 p50=66.9 p95=166.9 p99=424.3 max=567.8ms n=300 bad=0
      | fresh avg=68.9 p50=63.6 p95=140.2 p99=158.9 max=174.3ms n=300 bad=0
      | skew=±12ms
```

判读：

| 字段 | 健康值 | 异常含义 |
| --- | --- | --- |
| `queue size` | `0/4` 恒定 | 持续接近 4 ⇒ 消费跟不上（解码器慢/背压失效）⇒ **延迟会累积** |
| `dropped` | `0` 恒定 | `nonKey` 涨 ⇒ 网络式丢帧，画面会花；**`key` 涨 ⇒ 会花满一个 I 帧间隔（3s）** |
| `decoded` vs `queued` | 差恒为 1（正在解的那帧） | 差持续拉大 ⇒ 解码落后 |
| `inputStalls` | `0` | 涨 ⇒ 解码器饥饿（喂帧太慢或 Surface 有问题） |
| `cfgFailures` | `0` | 涨 ⇒ csd 注入失败，是否回退了起始码切分？ |
| `frames` / `config` | `config` 恒为 1 | `config` 反复涨 ⇒ 手机端在反复重配（旋转场景下才应出现） |
| `bytes` / 时间 | 静态约 10 fps、运动明显更高 | 长期不涨 ⇒ 链路卡死 |
| `delay` / `fresh` | 两者都有数、`fresh` 的 p50 更小 | 见下方「延迟三种异常写法」 |
| `skew=±Nms` | N ≤ 12 | N 很大（>50）⇒ CNXN 往返太慢，标定不可信，延迟读数仅供参考 |
| `sizeChanges=N`（在 `msgs(r/w)` 之后） | 旋转过几次就是几 | **手机旋转后它不动** ⇒ 手机端根本没上报旋转（先查手机是否**开了自动旋转**） |
| `stray=N` | 不出现 | 出现 ⇒ 链路上有杂散字节（上一次会话残留），偶发正常、持续出现要查 |

**延迟那一栏的三种异常写法**：

| 写法 | 含义 |
| --- | --- |
| `delay=(未标定：对端未带时钟读数)` | 手机端是**旧版本**（CNXN payload 只有 8B），或本次没走到 CNXN 交换 |
| `delay=(回放，非实时链路)` | 回放模式没有对端时钟可标定，本来就不测 |
| `delay` 的 p50 明显大于 `fresh` 的 | **画面基本静止**：编码器在按 `repeat-previous-frame-after=100ms` 重复送出上一帧，它们的 PTS 停在旧值上。**这时看 `fresh` 才准** |

> `delay`（全量）与 `fresh`（仅 PTS 间隔 < 50ms 的连续帧）是两个口径：
> 前者用于观察与定位，**后者才代表观感**。实测静止时两者差约 70ms，运动时基本重合。
> 完整方法与数据见 `docs/实施计划.md` 10.6。

> `frames` **只算媒体帧**，CONFIG 帧单独走 `config`；`bytes` 是链路口径（含 CONFIG）。
> 这是刻意区分的——把 CONFIG 算作帧会让帧率统计系统性偏大。

## 6. 一句话总结的排查顺序

1. **看是哪个包**（release 没有回放/抓流/日志，别在那儿排错）
2. **先排除设备自己重启**：宿主突然"不对了"就先读 `persist.sys.boot.reason.history`（3.9）。
   是 `kernel_panic` 的话，接着按 3.9 的更正版读 ramoops 现场、看 `Comm:` 是谁 ——
   `uav-reader`/`do_proc_bulk` 就是我们搞崩的（10.16 已修），别再当"设备自己的问题"
3. **跑一次回放**，把问题切成「USB/协议」或「解码/渲染」两半
4. **看手机 `dumpsys usb` 的身份**，六个字符串是否完整（3.4 的自查）
5. **看宿主 `STATS` 行**，`queue`/`dropped`/`stalls` 三个数就够判断链路健康
6. **「等待重枚举超时」先数 fd**（3.5）—— 别再靠重插拔"确认"；自愈机制现在会处理这类断链
7. 仍不通 ⇒ `--ez force_handshake true` 重走完整握手，再走第 2.3 节的「切回普通模式」流程

### 3.14 ★ 机顶盒上没有触摸：遥控器焦点必须自己画

**症状**：遥控器方向键按下去，画面毫无反应；或者焦点感觉得到（能点开面板）但**看不出选中的是哪个按钮**。

**两个独立原因**：

1. **`android:defaultFocusHighlightEnabled`（系统自带焦点高亮）是 API 26 才有的**。
   机顶盒多是 Android 7/9 ⇒ 焦点移过去屏幕没有任何变化。
2. **`<selector android:state_focused="true">` 在触摸模式下不生效**——
   实测 `view.hasFocus()==true` 但 drawable state 里没有 `state_focused`
   （`focusableInTouchMode` 拿到的焦点不参与视觉状态）。
   ⇒ 只能 `setOnFocusChangeListener` 手动挂/摘前景（见 `common/FocusRing.kt`）。

**还有两个"焦点黑洞"**（会让人以为遥控器坏了）：

| 黑洞 | 原因 | 修法 |
|---|---|---|
| 日志 `TextView` | `android:textIsSelectable="true"` 会让它变成可聚焦 | 去掉该属性 / `focusable="false"` |
| 日志 `ScrollView` | **构造期自己 `setFocusable(true)`**，XML 的 `focusable="false"` 被它覆盖；而且每次 `fullScroll()` 都可能把焦点抢回来 | **运行期** `isFocusable = false` + `descendantFocusability = FOCUS_BLOCK_DESCENDANTS` |

另外 `onCreate` 里 `requestFocus()` 会因为 View 还没 attach（`isShown==false`）**静默失败**，
要 `post {}` 到下一帧。面板展开↔收起时也要跟着把焦点在"药丸 ↔ 收起按钮"之间搬一次，
否则焦点落在 `GONE` 的控件上，方向键就彻底没反应。

> ⚠️ 反向情形见 **3.15**：在**有触摸屏**的宿主上，这一整套（焦点环 + 自动聚焦 +
> `focusableInTouchMode`）必须关掉，否则会出现"点一下没反应 / 要点两次"。

### 3.15 ★ 触摸设备不启用焦点模式（否则"点一下没反应 / 要点两次"）

**症状**：在平板、一体机这类**带触摸屏**的宿主上，手指点完按钮，画面上多出一圈蓝边；
更糟的是**有些按钮要点两次才生效**。

**根因有两层，而且第二层是第一层的"解药"带出来的**：

1. 焦点环是给**没有触摸屏**的设备用的（见 3.14）。触摸设备上它是纯噪音：
   手指点一下，`focusableInTouchMode` 就把焦点给它，于是"点哪儿哪儿被选中"。
2. 但**只把焦点环摘掉会变成"要点两次"**：`focusableInTouchMode="true"` 的控件在
   "窗口里还没有任何焦点"时，**第一次触摸只用来获取焦点**，第二次才触发点击。
   以前启动时 `requestFocus()` 抢了焦点，这个坑被掩盖着；一旦不再自动聚焦，它立刻露出来。

**处置**：`common/FocusMode.kt` 统一判定，`FocusRing.install()` 据此二选一 ——

| 宿主 | 行为 |
|---|---|
| **无触摸源**（机顶盒 / 车机） | 挂焦点环 + 启动自动聚焦 + 面板展开/收起时搬焦点（即 3.14 那一套） |
| **有触摸源**（平板 / 一体机） | **不挂环、不自动聚焦**，并把布局里为遥控器加的 `focusableInTouchMode` 全部 `false` |

最后一条是关键：只关 `focusableInTouchMode`，**不动 `clickable`/`focusable`** ——
点击照常一次生效，真接了鼠标键盘也仍可移焦（只是没有环）。

**判据只能是输入设备表**：

```kotlin
InputDevice.getDeviceIds().any { id ->
    val d = InputDevice.getDevice(id) ?: return@any false
    (d.sources and InputDevice.SOURCE_TOUCHSCREEN) == InputDevice.SOURCE_TOUCHSCREEN
}
```

⚠️ **不能用 `PackageManager.hasSystemFeature(FEATURE_TOUCHSCREEN)`**：机顶盒为了能装
"只支持触摸"的 App 普遍会把这个 feature 声明上（本项目的 RK356x 盒子就是），判据会反。
等价的命令行判据是 `dumpsys input` 里各设备的 `Sources` 有没有 `0x1002` 位。

**验证**（P40UCH 实机）：`UAV-Focus: 检测到触摸源 ⇒ 关闭焦点模式（不挂焦点环、不自动聚焦）`，
界面里 `focused="true"` 的控件数为 **0**，单击卡片/按钮**一次生效**。

### 3.16 ★ 面板"看不见"：动画属性 + 合成器剔除（两层坑叠在一起）

**症状**（2026-10-20，P40UCH / iOS 采集页）：

- 点左上角药丸，日志明确打「面板 展开（animate=true）」，**屏幕全黑 —— 面板和药丸都不见了**；
- 之后点屏幕任何位置毫无反应（实测连点 30+ 次，日志全是 `menuShown=true`）；
- 把位移幅度从 450px 改成 16dp：面板出现，但**左侧被裁掉一条**；
- 彻底去掉位移动画：一切正常。

**根因有两层，缺一不可。**

#### 第一层：`withEndAction` 不是收尾机制

```kotlin
overlayView.animate().alpha(1f).translationX(0f)
    .setDuration(ANIM_MS)
    .withEndAction { settleMenu() }        // ← 动画被 cancel 时**永不执行**
    .start()
```

`setMenuVisible` 开头就有 `overlayView.animate().cancel()`：连点、首帧自动收起、`finishRun` 展开，
任何一个赶上来都会取消当前动画，属性就停在中间值，而负责"摆回可见位置"的 `withEndAction` 再也没机会跑。

#### 第二层（本机特有）：`translationX` 让 View 离开可视区后渲染节点被剔除

- 位移幅度取的是 `overlayView.width`（1080p 上 **450px**）⇒ 面板被推到 `x ∈ [-450, 0]`，**整块离开屏幕**。
  这台 MTK 设备上合成器会把它的渲染节点剔除，属性回到 0 之后**不再重绘**；
- 证据：日志里 `vis=VISIBLE alpha=1.0 tx=0.0` **三个值全部正常**，屏幕上却什么都没有；
- 改成 16dp 后"左侧被裁一条"，同一个机制（位置已变但重绘是旧帧）；
- 对照：AOA 侧 `HostPanel` 一直用固定 16dp，**从未出现**这个问题 —— 差别只在幅度。

#### 为什么极难查：三条"假证据"

1. `uiautomator dump` 的 `bounds` 是 **layout bounds，不含 transformation**。
   `bounds=[0,0][450,1080]` 看着完全正常，实际绘制位置已经在屏幕外 —— 一度把排查带向"布局/遮挡"。
2. 三个可查属性（`visibility` / `alpha` / `translationX`）全部正常，日志"自证清白"。
3. `toggleMenu()` 有**两个入口**（药丸 / 画面空白），日志长得一模一样，
   分不清"用户点错位置"还是"状态机坏了"。加一条 `点击来源=…` 才分清。

#### 最终方案（`app-host/.../ios/ui/IosPanel.kt`）

| 关注点 | 做法 |
|---|---|
| 显隐 | **`visibility` 唯一决定**；`menuShown` 只记意图 |
| 滑动 | `layoutParams.leftMargin` 从 `-16dp` 到 0（`ValueAnimator` 逐帧设 margin） |
| 淡入 | `alpha` 0↔1（`ViewPropertyAnimator`），只做装饰 |
| 终态守卫 | `settle`：`cancel` 两个动画 → `translationX=0` → `leftMargin=0` → 按 `menuShown` 设 alpha/visibility；**540ms 后无条件执行**（`ANIM_MS*3`，容忍系统动画缩放 2~3x） |
| 看门狗 | 显示后 700ms 校验 `visibility/alpha/margin`，不达标就地复位并打 W 日志 |
| 自愈 | 点画面时先判 `menuShown && !visuallyShown()`：**先强制显示**，再谈切换 |

#### 通用规则（以后照做）

- **显隐只用 `visibility`**，`alpha` / 位移只做装饰，绝不能当显隐机制；
- **不在动画回调里做状态收尾** —— 要么用独立的 `postDelayed` 守卫，要么让收尾幂等且能被任何路径调用；
- "抽屉滑入"用 `leftMargin` / `offsetLeftAndRight` 这类**真实布局位移**，不要用 `translationX`；
  幅度必须**小于控件宽度**，动画期间控件始终有一部分留在屏幕内；
- 排查"看不见"时看 `visibility / alpha / translationX` 三个真值，**别信 uiautomator 的 bounds**；
- 面板边界要画出来（右缘 2dp 亮线）：面板只占 23%，画面全黑时边界看不见，
  用户会把"点画面收起"当成 bug。

### 3.17 ⚠️「强制复位采集通道」按钮已**删除**（2026-10-21），待重新调研

> 这是**已知功能的删除记录**，不是待办事项的临时占位。删之前它是 iPad 页唯一的兜底按钮，
> 用户反馈「好像没用」—— 代码审查确认是**结构上就没用**，不是偶发。

#### 用户看到的现象

点下去 → 药丸变「唤醒中」、副行「正在唤醒 iPad 的采集通道…」→ 最长 **240 秒**毫无变化 →
日志末尾一句「✗ 240s 内设备根本没重枚举 ⇒ 只能拔插线或重启 iPad」。而界面**停在「唤醒中」不回来**。

#### 三层原因（`IosActivity.rearm()` → `IosRearmer.run()`，已随功能一起删除）

| # | 原因 | 说明 |
|---|---|---|
| ① | 做的事是 `capture()` 的子集 | 它只做 `setConfiguration(普通配置)` + `activate`；而 `IosCaptureFlow.capture()` 第 3 步本来就有「配置 3→5 重新武装」，零字节后还有 `rearmAndRunAgain`（配置 4→5 再来一次） |
| ② | 判据必然不成立 | 入口判 `configurationCount >= 5`（此值进过 QT 后**永远是 5**，见 09:16），READY 判据是「配置集先 <5 再 ≥5」⇒ 僵态下永不成立 ⇒ **必然跑满 240s 报 NOT_ENUMERATED** |
| ③ | 结果被丢弃 | `runCatching { rearmer.run() }` 没有消费 `Result`（9 个状态一个没用）⇒ 面板停在 `Stage.REARM`，`onReset` 只复位 busy/mirroring 不 render ⇒ chip 永远「唤醒中」，成功失败都看不出来；成功后也不会自动接投屏（`IosAutoStarter` 基线在 busy 时已对齐） |

更根本的一条：**它想救的场景和它能救的场景不是同一个**。

| 设备状态 | 强制复位能做到 | 开始投屏 |
|---|---|---|
| 活动配置卡在采集配置、QT 服务**还活着** | 能（但要重枚举，慢） | **1 秒内复用出画面** |
| 僵态（配置集 5、零字节，QT 服务已死） | **不能**（09:24 / 10:09 两次实测：activate / `0x52 wIndex=0` / 重配对 / 重 claim 全部无效） | 不能，但会如实报错 |

而它还有副作用：`activate` 会让设备**强制闪断重枚举**，把热态搞成冷态（10:54 的教训），
顺带产生 `USB_DEVICE_DETACHED` 广播。

#### 删掉了哪些东西

- `app-host/.../ios/run/IosRearmer.kt`（整个类，含 240s 等待循环）
- `IosActivity`：`rearm()`、`rearmer` 字段与构造、`onRearm` 回调
- `IosPanel`：`btnRearm`、`Stage.REARM`、`bind(onRearm=…)`
- `activity_ios.xml`：`btn_rearm`
- 文案：`ios_btn_rearm` / `ios_chip_rearm` / `ios_status_rearm` / `ios_detail_rearm_hint`（中英各 4 条）

#### 现在设备不出画面怎么办

1. 拔插数据线（让 USB 层重连 + 触发自动流程）；
2. 仍然零字节 ⇒ **重启 iPad**（宿主侧手段无效）；
3. 从 App 侧"重新开始"的正确入口是底部按钮「开始投屏」—— 它等价于「退出 App 再进 App」。
